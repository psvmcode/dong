### 索引治理（这次最大的结构性改动）

**索引名现在是别名**：`dong_lab_product` 是别名，真实索引是 `dong_lab_product_v1/v2…`。
`IndexNameResolver` 新增 `versioned()` 与 `versionOf()`，`PRODUCT_INDEX` 常量统一定义逻辑名。
`SearchIndexInitializer` 瘦身成只调 `ensureAlias()`，mapping/settings 搬到 `SearchIndexServiceImpl`。

**老结构自动迁移**：启动时若发现「别名不存在但同名真实索引存在」，会 reindex 到 v1、删老索引、挂别名。
实测从旧索引迁了 4 条，一次过。之后启动幂等（别名已存在就不动）。

新 mapping 加了 `suggest`(completion)、`location`(geo_point)，以及查询期的同义词分析器
`ik_smart_synonym`（同义词只在查询时展开，写入时展开会让索引膨胀且改规则就得重建）。
实测搜「云服务」能命中「云服务器测试商品」。

**已知缺口写进注释了**：reindex 期间的新写入会落在旧索引上，切别名后这部分增量会丢。
数据量小可忽略，生产要停写窗口或双写补偿。

### 数据模型

`product` 表加 `longitude`/`latitude` 两列（DDL + gen-initdb + 远程 ALTER 都跑了）。
`ProductSaveRequest` 加两个可选字段，`@DecimalMin/@DecimalMax/@Digits` 约束范围。
注意 ES 的 geo_point 是一个整体字段，库里拆成两列，转换时 **lat 在前 lon 在后**，写反不报错但距离全错。

### ES Java Client 的坑（都是实测撞出来的）

- **补全结果不在 `SearchResponse` 上**，在父类 `ResponseBody.suggest()`，类型是
  `Map<String, List<Suggestion<T>>>`；要 `isCompletion()` → `completion().options()` → `text()`。
  没有 `SuggestOption` 这个类（只有 `CompletionSuggestOption`）
- **子聚合挂在 `Aggregation.Builder` 的 `ContainerBuilder` 上**，不是 `TermsAggregation.Builder`：
  写成 `.terms(t -> t.field("x").aggregations(...))` 编译不过，正确是
  `.terms(t -> t.field("x")).aggregations("sub", s -> s.stats(...))`
- **range 聚合的 `ranges()` 会整体替换而不是追加**，连着调三次只剩最后一个；
  必须传 `List<AggregationRange>`。而且 `from/to` 是 **Double 不是 String**
- **geo_distance 排序不指定 unit 时按米返回**：1067 公里返回成 1067311.6，
  数值看起来「像公里」，是最难发现的一类 bug。必须 `.unit(DistanceUnit.Kilometers)`

### 其他

- 重写 `SearchServiceImpl` 时**漏了 `@ConditionalOnProperty`**，差点让关闭开关时 Bean 仍注册
  （表现是接口返回 1005 而不是 1004）。编译期发现不了，必须靠关闭开关实测
- 关闭开关实测：count / aggregate / current-index 都返回 1004，索引初始化日志 0 条 ✓
- 商品 1、2 分别留了北京（116.4074,39.9042）和上海（121.4737,31.2304）坐标，
  好让 `/nearby` 开箱能演示。不想要就 PUT 时不带经纬度覆盖回 null

### 环境问题（再次出现，非代码问题）

远程 Redis 又出现命令超时（5 秒），商品更新接口 500、`QueryTimeoutException`。
服务器 2G 内存仍只剩 364M 可用、swap 用了 1.4G，ES 容器已从 578M 涨到 722M/800M。
**Redis 在容器内 ping 是秒回的，超时纯粹是宿主机内存不足导致的延迟尖刺**。
重试通常就成功。这个环境问题得靠扩容或降 ES 内存解决，改代码没用。

## 统一去掉注解与类声明之间的空行（commit 650f9f2）

用户问「为什么要空一行」并要求全量清掉。全项目 **224 个 Java 类**，每类一处：

```java
@Component

public class Xxx {          →      @Component
                                   public class Xxx {
```

**注意别误伤**：项目规范（dong-standards 第 4/5 条）要求**方法前后、字段前后各留一个空行**，
所以只能删「注解 → 空行 → 类/接口/枚举/record 声明」这一类，**方法前的空行绝对不能删**。

**做法**：写了个 Python 脚本按行扫描（不是盲改正则）：
用正则匹配类型声明行（允许修饰符、允许缩进以覆盖内部类），
再往上找最近的非空行，判断是不是注解（支持多行注解，往上追 8 行内出现 `@` 开头即算），
确认后才删那一行空行。跑完再跑一次确认 0 残留。

**验证**：`git diff -U0 | grep '^-'` 去重后确认——224 处删除全是空行，没有误删任何代码；
另外 4 处是 IDE 把 SearchController 的续行重新对齐了（空格级）。编译通过 + 重启冒烟全绿。
