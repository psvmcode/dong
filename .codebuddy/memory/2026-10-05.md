## 后端名次口径已统一（已改并 push）

- 原状：`/api/classic/rank/rank` 走 zrevrank 返回 **0 基**，而 top/around 返回 **1 基**。
- 改法：`LeaderboardServiceImpl` 拆出私有 `zeroBasedRank()` 只给 `around` 做切片用，
  对外 `rankOf()` 在出口补 1，与 top/around 同口径；接口与 Controller 的 Javadoc 同步改。
- 前端 `Leaderboard.vue` 去掉展示时的 `+1`（已提交 dong-web）。
- 实测：rankOf(player-1)=1、top rank=1、around(player-3)=[2,3,4]，页面显示「我的名次 #1」。
- 教训：**Redis 原生下标（0 基）不要直接透给接口层**，切片用的下标和给人看的名次必须分开。

## 修复：前端把「后端降级」误判成「后端离线」

- 现象：总览页显示「后端离线 / 后端不可达」，但 curl 业务接口一切正常。
- 根因：**actuator 有组件 DOWN 时返回 HTTP 503，body 里是完整健康详情**；
  前端 `getRaw` 用普通 axios get，503 进 catch 返回 null → 判定不可达。
  这与「服务没启动」被混成一件事。
- 改法：新增 `getRawTolerant`（`validateStatus: () => true`），`api/system.ts` 导出 `probeHealth()`：
  ① 拿到 actuator 响应（含 503）→ 在线，原样透出 status，页面提示「N 个组件不可用」；
  ② actuator 拿不到 → 退回业务接口探活，通了仍算在线；
  ③ 两层都失败才判离线。
- 顺带修：总览 4 个指标改为各自独立加载（原来是 Promise.all + 单一 loading，
  ES 慢会让整屏卡在骨架态，更像「挂了」）。
- 教训：**HTTP 非 2xx ≠ 服务不可用**，actuator/健康检查类端点必须容忍 4xx/5xx 读 body。

## 缓存链路可证的关键做法

多级缓存最容易被「猜命中层」糊过去。这里不猜：读取前取一次 `/cache/lab/stats`，
读取后再取一次，比较 `l1Hit / l2Hit / miss` 三个计数器哪个涨了，
涨哪个就是命中哪一层。展示出来的链路是可证的。

## 端到端验证结果（真实跑通，非推断）

### 1) 跨境支付全链路 — 8 步全通过
开户 Alice/Bob → 询价锁汇（拿到 quoteNo）→ 发起汇款 → 归集 → 清算 → 对账，每一步 code=0。
- 幂等验证：同一 `idempotentKey` 重发两次，**返回的是同一个汇款单号**（状态从 FUNDS_DEBITED 推进到 SETTLING，批次号被清算任务填上），没有重复建单。

### 2) TCC 三阶段
- seed 初始化成功
- 正常提交 → `committed=true`，`message="confirmed"`
- 强制失败 → `committed=false`，`message="try failed on account: account try phase failed on purpose"`
  说明 Cancel 分支是真的写过的，不是只在成功路径上自洽

### 3) 红包并发不超发 — 关键证据
15 个不同 userId 并发抢 10 份红包：
- 请求全部返回 code=0（没有抛异常）
- 但**领取记录只有 10 条**，金额合计正好 = 10000 分 = 红包总额
- 领取人去重数 = 10，即每人只拿到一份、每份只被一人拿到

### 4) 缓存三级命中路径
删除缓存后连续读同一商品：
- 第 1 次 → `miss 10→11`（回源数据库）
- 第 2 次 → `l1Hit 0→1`，miss 不变（命中 L1）
- 第 3 次 → `l1Hit 1→2`，miss 仍不变（持续命中 L1）

### 一个需要知道的环境限制（不是代码问题）

并发压测到 **40 并发**时，约 32 个请求返回 5000。后端日志显示根因是：
`Redis command timed out` → 连带 `dong-hikari - Connection is not available`。

这与之前记录的「云服务器 swap 已用 1.1G、Redis 偶发超时」是同一个资源瓶颈，
**不是前端或后端代码的缺陷**。建议压测并发控制在 20 以内，或先释放服务器内存。
