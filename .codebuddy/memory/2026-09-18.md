# 2026-09-18

## 灌入 504 条贴近真实的商品数据（commit a5b5fba 是配套的代码修复）

用户要求「多加数据，越多越好，更符合实际场景」。

### 关键前提：数据要灌 MySQL，不能灌 ES

ES 是 MySQL 的派生视图，直接往 ES 插会变成**孤儿文档**，被对账判成多余数据删掉。
正确姿势：写 MySQL → `POST /api/search/sync` 全量同步。

### 数据设计（504 = 原有 4 + 新增 500）

| 维度 | 设计 |
|---|---|
| 分类 | 10 个（手机数码/电脑办公/家用电器/服饰鞋包/食品生鲜/图书文娱/运动户外/美妆个护/家居家装/母婴玩具），每类 50 条 |
| 名称 | 10 个基础名 × 5 种规格 = 50 个组合，**刚好铺满所以同类内不重名** |
| 价格 | 按分类给不同区间（图书 19~199、电脑 1999~15999），实测 avg：图书 114.5、电脑 9926.8 |
| 状态 | 约 10% 下架（54 条），用于验证默认的上下架过滤 |
| 坐标 | 70% 有坐标，散布 10 个真实城市；30% 无坐标（150 条），验证 geo 会跳过它们 |
| 创建时间 | 铺在 2026-02-01 ~ 2026-09-17，让按月直方图出 8 个桶 |

生成用的是**带固定种子**（`new Random(20260918L)`）的 Java 单文件程序 + JDBC `addBatch`，
500 条一次批量插入，比调 500 次 HTTP 接口快得多，也避开了 Redis 抖动。

### ⚠️ 重灌数据的坑：id 会变，旧文档全变孤儿

第一次灌完发现重名太多，于是 `delete from product where id >= 7` 后重灌——
**MySQL 的 auto_increment 不会因为 delete 而回退**，新数据从 507 开始，
于是索引里旧的 500 条（id 7~506）全成了孤儿，count 从 504 涨到 1004。

**教训**：重灌数据要么保留原有 id，要么灌完立刻 sync 让孤儿清理兜住。

### 由此暴露并修掉的一个真实设计缺陷

count 涨到 1004 之后，**两条自救通道全被堵死**：
`syncAll` 的孤儿清理被 `count() > 上限` 跳过，对账又被 `CODE_CAPACITY_EXCEEDED` 拒绝。
根因是孤儿清理走的是「把索引里的 id 全捞回内存再逐条删」——
**索引越脏越大，就越清理不动，这是个死循环**。

修法：新增 `SearchService.deleteExcept(keepIds)`，改用 ES 的 `delete_by_query`
（`bool.mustNot.ids(...)）直接在 ES 侧删不需要的文档，不再受内存上限约束。
一次调用清掉 500 条孤儿，count 回到 504。

### 顺带两处加固

- 对账上限从 `MAX_QUERY_LIMIT`(200) 提到 `MAX_BATCH_SIZE`(1000)，注释讲清它是**内存上限**不是能力上限
- `removeOrphans` 加了「库里 0 条商品就跳过」的保险：`deleteExcept` 传空名单会匹配到全部文档，
  数据源一抽风就会把整个索引清空，代价远大于留下几份幽灵文档

## 重造数据：804 条，每条带 1200+ 字大文本详情（commit 798f092）

用户反馈「数据太简陋，要有很长的文本，越多越好，每条内容要充实」。

### 核心改动：新增 description 大文本列

原来的 `description` 是 `name + " " + category` 拼出来的，撑不起长文本。
所以给 `product` 表加了 `description text` 列（DDL + gen-initdb + 远程 ALTER 都跑了），
实体、Mapper（resultMap/columns/insert/update）、`ProductSaveRequest`（`@Size(max=4096)`）全部贯通。

同步逻辑改为 `resolveDescription(product)`：库里填了就用库里的，没填退回拼接值。
⚠️ **对账比对详情时必须也走这个方法**，否则库里 null、索引里是拼接值会被误判 STALE。

### 数据规模与内容

| 项 | 值 |
|---|---|
| 商品数 | 804 = 原有 4 + 新增 800（10 分类 × 80） |
| 名称 | 10 基础名 × 4 规格 × 2 版本 = 80 组合，**804 条名称互不重复** |
| 详情长度 | min 1223 / max 1629 / avg 1347 字，总计约 108 万字 |
| 详情结构 | 9 段：概览、核心卖点(8条)、规格参数(6条)、适用场景(3条)、包装清单(6项)、售后保障、品牌与服务、用户评价(3条)、选购建议、常见问题(5条)、温馨提示 |
| ES 索引 | 804 docs / 2.5MB |
| 分布 | 82 条下架、266 条无坐标 |

段落内容从分类专属池里洗牌随机挑（`pickRandom`），所以每条文案都不同，不会出现整批雷同。

### 实测

- 搜「冷链」命中 139 条——**这个词只存在于详情里**，证明大文本真的可检索且高亮正常
  （`descriptionHighlight` 返回带 `<em>` 的片段）
- 对账 804/804 干净；聚合 722 条在售、11 分类、8 个月份桶；补全、地理、深分页均正常
- 服务器：ES 容器 596MB/800MB，宿主可用内存 415MB，索引才 2.5MB，压力没明显变化

### 造数据的两个经验

- 批量灌用 JDBC `addBatch`，800 条一次跑完，比调 800 次 HTTP 接口快几十倍，
  也彻底绕开 Redis 抖动（走 API 会碰缓存失效）
- 重灌后旧 id 的文档变孤儿，靠 `sync` 的 `deleteExcept` 清（这次清了 500 条）
