# 2026-09-30

## 全项目性能与架构优化

用户要求整体优化（性能 + 架构），改完实测到没问题再提交。
先让 code-explorer 全量扫了一遍（376 个 Java + 33 个 mapper XML），按证据挑了 12 项落地。

### 已落地
1. **L2 命中去掉双重序列化**（最热路径）：新增 `framework/cache/CacheRecord`，
   Redis 里值以 JSON 字符串原样存，读取时只反序列化一次。
   原先是 `fromJson(raw) → LinkedHashMap → toJson → fromJson`，每次命中多一次完整序列化。
   顺带把 decode 包进 try/catch：值格式对不上按 Miss 处理，缓存解析失败不该让接口 500
2. **布隆过滤器实例缓存**：`ProductServiceImpl` 缓存 `RBloomFilter`。
   Redisson 的 `tryInit` 不是本地幂等判断，每次都发 Redis 命令，
   不缓存的话这个"前置拦截"每次 2 次往返，比它要保护的查询还贵
3. **回源锁等待 1s → 100ms**：拿不到锁说明别人在重建，本就该立刻退让去用旧值
4. **封禁检查加本地放行表**：`CacheReadGuard.localClear`，未封禁的 IP 10 秒内不再查 Redis。
   注意 `block()` 里必须 invalidate localClear，否则封禁要等窗口过去才生效
5. **SpEL 表达式缓存**：`RateLimitAspect` 用 ConcurrentHashMap 缓存 parseExpression 结果
6. **渠道路由去掉 1+N 查询**：`ChannelRouterImpl.feeOf(config, amount)` 直接用已查回的费率字段，
   不再按渠道号回表
7. **推模式时间线批量查询**：新增 `selectByFeedIds`，一次 in 查询替代 N 次单条；
   结果要按 ZSet 原序还原（SQL in 不保证顺序）
8. **时间线重建复用批量方法**：`selectByAuthors` + `addAll` 一次写入
9. **粉丝扩散 pipeline**：`RBatch` 合并 ZADD，一万粉丝从一万次往返降到几十次
10. **短链跳转只在首次设 TTL**：`incrementAndGet() == 1` 才 expire
11. **短链计数回写批量 GET**：`RBatch.getAtomicLong(...).getAsync()` + `join()`
12. **周榜结算批量累加**：`RBatch.addScoreAsync`。
    **不能用 addAll**：addAll 是覆盖语义，会把上周历史分抹掉，结算必须是累加
13. **`findAll` 在 SQL 层封顶**：新增 `selectTop(limit)`，原来先全表捞进内存再截断

### 明确放弃的两项（正确性优先）
- **秒杀活动本地缓存**：活动状态/时间窗口变化后缓存里的旧值会让判断失真，
  而秒杀的正确性（不超卖、时间窗口）比这次查询重要
- **抢红包删除第二次查询**：第二次查询是为了拿准确的最新剩余来判断是否标记 FINISHED。
  用本地快照估算在并发下会漏标（快照=2 时两个并发各扣 1 就售罄但都不回查），
  漏标虽不影响金额守恒（Lua 兜底），但会让状态与实际不一致。

### 工具经验
- Redisson 批量 API 一律用 `javap -classpath <redisson.jar> <接口>` 确认签名再写，
  不要凭印象：`addScoreAsync(V, Number)`、`addAsync(double, V)`、`addAll(Map<V,Double>)` 语义都不同
- 用 `head -c` 截断 curl 大响应会让服务端报 Broken pipe，看日志时别误判成应用异常
