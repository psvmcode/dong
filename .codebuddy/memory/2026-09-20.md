## 新增 doc/learning/java/alternate-print.md（commit `c7db46b`）

- 两个线程严格交叉打印 1 到 100：wait/notifyAll、ReentrantLock+Condition、Semaphore、LockSupport 四种写法，
  三种典型错法（只加锁不等待 / 用 if 判断 / 打印与自增分离），「一锁二判三唤醒」口诀，已更新 java/README.md 索引与阅读顺序。
- **文档里的并发代码在 /tmp 实跑验证过**：四种写法均输出严格 1..100，且两个线程启动顺序反过来同样正确。
  以后写这类知识点文档，代码要跑一遍再写进 md；macOS 无 `timeout`，用 `(java X.java > log &) ; ping -c 6 127.0.0.1` 等待。
- 追加「最短写法」：把奇偶做成人参 `print(int parity)`，两个线程共用一份代码。
  Semaphore 版 9 行（`for` 循环 50 次定边界，不用 `while`、不用退出前唤醒、不用 `finally`）；
  synchronized 版 18 行做对照。适用前提：**每个线程打印次数事先确定**，次数不定仍需 `while` + 条件判断。
- 用户贴来一段「更短」的常见写法并质疑。**实测结论**（都写进了 `alternate-print.md` 的反面剖析节）：
  ① `count` 初值 0 → 打印 0..100 共 **101 个**，300 轮无一例外；
  ② 线程名与奇偶**相反**（偶数线程打了 50 个奇数）——那写法根本不区分奇偶，只是碰巧交替；
  ③  `while` 在锁外 + `count` 非 volatile 属"检查与执行分离"，理论会多打 101，**但本机加 yield 放大也没复现**；
  ④ `notify` 只唤一个：两线程、三线程各 100 轮**都没挂住**，侥幸不死，不能据此说它会死锁。
- **教训**：并发结论要靠实测数据说话，把「实测确认」和「理论隐患」分开写，不能想当然断言 bug。

## alternate-print.md 精简重写（commit `0aa094c`，删了 456 行）

- 用户反馈「方案太多」，重写为**四个最简写法**：synchronized / ReentrantLock+Condition /
  CountDownLatch / Semaphore，统一 `print(int parity)` 结构（1=奇数 0=偶数），每版配一句大白话+侵权表。
- 保留的坑点压缩为三条：判断条件必须 `while`、打印自增唤醒要在同一临界区、退出前要叫醒对方。
- **CountDownLatch 版的两个技术点**：① 门闩一次性，`countDown` 到 0 后永久敞开，**每轮必须 new 新门**；
  ② 两个门必须各自 `volatile` 独立字段，**塞数组里改元素没有可见性保证**（Semaphore 版用数组没问题，
  因为元素是 final 不替换，只 acquire/release）。
- 四种写法 × 两种启动顺序全部实测通过；CountDownLatch 版另跑 50 轮稳定。
- Semaphore 版最短（9 行）：循环 50 次天然定边界，省掉 while/退出唤醒/finally。
