# 2026-10-08

## 新增场景：文件分片上传 + 断点续传（特大文件）

用户三点决策：① 分片记录先只做 mysql；② 默认只记元信息但要留落盘开关；③ full / sample 两种 hash 都做。

### 后端 com.dong.upload（14 个新文件）

- 表：`upload_task` + `upload_chunk`，已入 `db/schema.sql` 并跑 `gen-initdb.sh`（43 张表），
  已在远程库单独执行建表（已存在的容器不会重跑初始化脚本）。
- 接口：`/api/upload/init` `/chunk`（multipart）`/complete` `/status` `/tasks`，DELETE `/api/upload/{uploadId}`。
- 开关沿用 agent 模式：Controller 用 `@Value` + `checkAvailable()` 抛 1004，只有定时任务挂 `@ConditionalOnProperty`。
- `PrimaryMybatisConfig` 已加 `com.dong.upload.mapper`（漏了会报 No qualifying bean）。

### 三个值得记住的设计点

1. **uploadId 由内容确定性推导**（`UploadIdGenerator.resolve(hash|size|fileName|chunkSize)`），
   不随机生成。这样刷新页面 / 换浏览器后重新 init 天然命中同一任务，
   前端不需要把 upload_id 存 localStorage。chunkSize 也纳入推导——分片大小变了，
   旧分片在新口径下无意义，开新任务比复用更安全。

2. **默认 persist-data=false 只记元信息**。断点续传与秒传依赖的是分片记录，不是文件内容，
   关着也能完整验证机制，同时不占服务器磁盘。打开开关才真正写分片并流式合并。
   合并用 `InputStream.transferTo`，全程流式，绝不 readAllBytes（GB 级会 OOM）。

3. **踩到一个真坑：tomcat `max-http-form-post-size: 2MB` 会让 5MB 分片直接 413**，
   而且是在进 Controller 之前挡的，业务层连日志都打不出来。
   已放开到 100MB 并同步加 `spring.servlet.multipart.max-file-size`。
   代价是全站 form 上限一起变大，已在 yml 注释里写明这个取舍。

### 实测结果（全部真实跑通）

- init：100MB / 5MB → 20 片
- 传分片 0、1 → 各 5242880 字节
- status → 2/20，10%
- **再次 init → uploadedChunks=[0,1]**（断点续传核心）
- **重复传分片 0 → 计数仍为 2**（幂等）
- complete 分片不全 → 1000 "chunks incomplete, received 2 of 20"
- 小文件完整闭环：传 1 片 → complete 成功 → **再次 init 返回 instant=true**（秒传）

### 前端 dong-web

- `src/api/upload.ts`：chunk 用原生 fetch + FormData（不走 JSON 封装），返回值保持 ApiResult 同构并写链路。
- `src/utils/fileHash.ts`：分块 digest（每次只取 2MB），full 遍历所有块、sample 只取首/中/尾 3 块，
  内存占用恒定；两种模式可在页面上直接对比耗时。
- `src/views/upload/UploadLab.vue`：拖拽选文件 + 分片网格（灰/蓝/绿/红）+ 并发数调节 +
  「模拟刷新页面」按钮（重新 init 点亮已收分片）+ 秒传提示 + 任务列表。
