# 2026-10-19

## 分片上传场景整体复审与加固

对 `com.dong.upload` 做了一轮 review，改掉 14 处问题，其中 3 处是真实缺陷。

### 两个真实的安全缺陷（路径穿越）

1. **`UploadStorage.safeName` 挡不住 `.` 和 `..`**：
   `Paths.get("..").getFileName()` 返回的仍然是 `".."`，
   只取 basename 而不排除它，resolve 之后照样跳到父目录。已补上显式排除。
2. **`deleteTaskFile` 未校验路径仍在存储根内**：storagePath 来自数据库，
   库被污染后不校验就会删到目录外面。已加 `isInsideStorage`。
   注意两边都要 `toAbsolutePath`——storageDir 配成 `./uploads` 这类相对路径时，
   拿相对路径去 startsWith 绝对路径恒为 false，校验会变成摆设。

### 一个会误删数据的 bug

- **清理任务会把「正在上传」的任务删掉**：分片写的是 `upload_chunk`，
  而 `upload_task.update_time` 只在状态变更时更新，传一个大文件传过 24 小时
  就正好落进「过期未完成」的范围。已加 `touch()` 在每次收片时推进 update_time。

### 并发正确性

- `init` 并发创建同一任务会撞唯一键抛 `DuplicateKeyException`（不是 BusinessException，会变成 5000）。
  已捕获后重新查回来复用——冲突说明别人建好了，不是错误。
- `complete` 并发调用会两次走到合并。已改用 `updateStatusFromUploading`（where status=0），
  靠影响行数判定谁抢到，落败的直接返回当前状态。

### 性能

- **去掉了这一层所有的 @Transactional**：每个写操作都是单条且幂等，没有跨表一致性；
  收分片的磁盘 IO 包在事务里会让连接被几十毫秒的写盘拖住，并发上传时连接池先于磁盘被打满。
  正确性靠 SQL 条件而不是事务隔离。
- **列表 N+1**：`toResponse` 里逐条 count，一页 100 条就是 100 次往返。
  已加 `countByUploadIds` 批量投影（新增 `dto/UploadChunkCount`）一次取全。

### 参数防御

- 分片大小必须 ≤ 任务声明的 chunkSize（否则可拿同一 uploadId 持续投递超大分片写满磁盘）
- 空分片 / file 为 null 直接拒
- 新增 `Constants.MAX_CHUNK_COUNT`（十万）挡住 fileSize 合法但 chunkSize 极小时算出的天文分片数
- 合并后校验实际字节数 == 声明 fileSize（只在真落盘时校验，开关关闭时 bytes 恒为 0）
- `writeChunk` 返回实际写出字节数而不是声明值，流被截断或磁盘满时能立刻发现
- 已完成任务不允许 cancel；已取消任务不允许 complete / 收片

### 其他清理

- 删掉从未被调用的 `increaseUploadedBytes`；`uploaded_bytes` 改为终态回填（进度一律以 sum 为准）
- 删掉 `UploadIdGenerator` 里「拿不到 MD5 就退回 hashCode」的兜底——
  hashCode 补成 32 位 hex 看着一样但碰撞率高得多，两个文件撞同一个 uploadId 会传出错误内容。
  改成直接抛异常。

### 前端同步加固

- 换文件时先清 `hashResult`（计算是异步的，不清会拿上一个文件的指纹建任务）
- 分片大小变更自动重置任务（uploadId 与 chunkSize 绑定，不重置会续到口径不一致的任务）
- 上传字节数逐片累加（最后一片不满，用「片数 × 片大小」会高估进度与速度）
- 暂停时把已跑时间并入累计值，否则续传后速度虚高
- 空文件入口拦截；全量指纹超过 2GB 自动退回抽样

### 验证结果

传 2MB 分片（超 1MB）→ 1000；空分片 → 1000；下标越界 → 1000；
complete 分片不全 → 1000；取消已完成任务 → 1002；已取消任务 complete → 1002；
秒传 instant=True；列表批量统计显示正确（0/2、1/1、1/4…）。
