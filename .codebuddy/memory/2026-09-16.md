## 知识点库新增 es 领域（commit 3ce4318）

`doc/learning/es/` 首篇 `cpu-high.md`，链检查 91 处 0 断链。

核心结论（重点是救火）：
- **第一步**：`GET _nodes/hot_threads` —— **排查 ES CPU 的第一命令**，直接输出热点线程完整堆栈。
  一眼区分：`search`+聚合 → 大聚合；`Lucene Merge Thread` → merge；`G1 GC` → 内存问题
- **找罪犯**：`GET _tasks?detailed=true&actions=*search` —— description 里能看到查询体
- **最快救火（按见效速度）**：
  1. **`POST _tasks/<id>/_cancel` 杀掉问题查询 —— 秒级见效，最一针见血**
     （失控查询往往就一两个，杀掉即恢复）
  2. 停写入 + 调大 `refresh_interval` → 分钟级（治 merge）
  3. 限流（宁可拒绝一部分，也不能让集群雪崩）
  4. 扩容 —— **不是最快的**：触发 rebalance，迁移本身也烧 CPU
  5. 重启 —— 最后手段，**一次只重启一个**（recovery 会把剩余节点压死）
- **必须先分清性质**：CPU 高可能是「ES 自己算得凶」也可能是「GC 在烧」，处理方向完全不同
- 根治：深分页改 `search_after`；分片控制在 10~50GB；冷热分离

## Redis 大 key（commit 3da277f）

`doc/learning/redis/big-key.md`。核心：
- **危害不在占内存，而在阻塞单线程**——Redis 命令执行是单线程，一个 key 卡住全库排队
- **判定**：String > 10KB，集合 > 5000 元素 或 > 1MB（两个维度都要看，元素多的更隐蔽）
- **不只是写危险**：`HGETALL` / `SMEMBERS` / `LRANGE 0 -1` 这类**读**一样阻塞
- 其他危害：集群**数据倾斜**（可用容量由最满分片决定）、RDB fork 时 COW 加长阻塞、主从延迟
- **发现**：`redis-cli --bigkeys`（用 SCAN 不阻塞，**生产在从节点跑**）；`MEMORY USAGE key SAMPLES 0` 精确查
- **删除必须用 `UNLINK` 而非 `DEL`**（4.0+）：把「摘除 key」（快）和「释放内存」（慢）拆开，
  后者交后台线程，主线程立刻返回
- **读取用 HSCAN/SSCAN 代替 HGETALL/SMEMBERS**
- **根治是拆分**：按 field/member 哈希取模拆子 key。
  **坑：别用同一个 hash tag `{user1}`，否则子 key 仍落同一分片，拆了等于没拆**

## 评审：`search/config/ElasticsearchConfig.java`（纯答疑，未改代码）

结论：`pom` 已引 `spring-boot-starter-data-elasticsearch`，Boot 3.4.5 会**自动配置** `RestClient`
（`ElasticsearchRestClientAutoConfiguration`，读 `spring.elasticsearch.uris/username/password/path-prefix/
connection-timeout/socket-timeout/restclient.ssl.*`）与 `ElasticsearchClient`
（`ElasticsearchClientAutoConfiguration`）。二者都是 `@ConditionalOnMissingBean`，
所以手写 bean 会**静默覆盖**官方实现，后果是上面那些属性**写了不生效**，项目里的
`RestClientBuilderCustomizer` 也被绕过。手写唯一换来的东西是 `dong.elasticsearch.enabled` 开关
（Boot 没有该属性）。

真实的缺口（大项目该补的）：connect/socket 超时、连接池上限、API Key/TLS 认证、
ES 专用 ObjectMapper（现在复用 `JsonUtils` 的静态 mapper，全局改动或 DTO 上的
`@JsonIgnore/@JsonFormat` 会静默改写 `_source`）、多集群命名 bean、别名+template+ILM
（`SearchIndexInitializer` 启动建索引属 demo 做法）。
`destroyMethod=""` 这点是对的（`ElasticsearchClient.close()` 会连带关 transport/restClient，避免双重 close）。

## ES 客户端配置重构（commit 4949a15）

已按上一条结论落地，`ElasticsearchConfig` 从 83 行降到 60 行左右：

- **删掉**手写的 `RestClient` / `ElasticsearchClient` Bean，认证与地址交给 `spring.elasticsearch.*`
- **`DongApplication` 去掉两个 exclude**：`ElasticsearchRestClientAutoConfiguration`、
  `ElasticsearchClientAutoConfiguration`。改为再加三个 exclude 顶住新冒出来的 Spring Data ES Bean：
  `ElasticsearchRepositoriesAutoConfiguration`、`ReactiveElasticsearchRepositoriesAutoConfiguration`、
  `ReactiveElasticsearchClientAutoConfiguration`（不排掉会多出 `reactiveElasticsearchClient`
  和一个多余的 transport，配置类靠 `@ConditionalOnMissingBean` 不能自动消失）
- **保留连接池自定义器**：`RestClientBuilderCustomizer` 的池大小没有 yml 出口，只能写代码。
  ⚠️ **必须实现 `customize(HttpAsyncClientBuilder)` 这个默认方法**，不能在
  `customize(RestClientBuilder)` 里自己调 `setHttpClientConfigCallback`——Boot 先注册自己的凭据/SSL
  回调、后调用户自定义器，自己覆盖一次会把凭据顶掉，表现为 401（已用 javap 反汇编 Boot 的
  `RestClientBuilderConfiguration` 确认调用顺序）
- **新增 `JsonpMapper` Bean**：这是 Boot 留的扩展点（`JacksonJsonpMapperConfiguration` 带
  `@ConditionalOnMissingBean`），交给容器即可，不用覆盖客户端 Bean。
  **Boot 默认的 `new JacksonJsonpMapper()` 内部是裸 `ObjectMapper`，没有 JavaTimeModule，
  遇到 `LocalDateTime` 直接序列化失败**；而业务侧的 `spring.jackson.date-format` 是
  `yyyy-MM-dd HH:mm:ss`，带空格的日期又会被 `strict_date_optional_time` 拒收。所以 ES 单独一套 mapper
  是必需的，不是洁癖
- yml 里 `uris` 补上 `http://` 前缀（Boot 期望完整 URL），并加 `connection-timeout: 3s` / `socket-timeout: 30s`

**行为变化**：`dong.elasticsearch.enabled=false` 不再阻止客户端 Bean 创建（Boot 自动配置不看这个开关），
但所有 ES 消费端（`SearchService`/`SearchSyncService`/`SearchIndexInitializer`）仍被关掉，
且客户端是懒连接、启动不发请求，实测 `enabled=false` 启动正常、`/api/search/count` 返回
`CODE_MIDDLEWARE_DISABLED`。要彻底不建 Bean 只能加 `spring.autoconfigure.exclude`。

**验证方式**：`/actuator/beans` 是这次最有效的证据——能直接看到 `jsonpMapper` 是自定义实现、
Boot 的 `jacksonJsonpMapper` 被 `@ConditionalOnMissingBean` 跳过、`reactiveElasticsearchClient` 已消失。
端到端跑通 `count` / `sync`（4 条）/ `search`（高亮 + 聚合），并回查 ES `_source.createTime`
确认为 `2026-08-29T13:29:35` 的 ISO 格式。

顺带发现（**既有问题，未改**）：`SearchController.search` 给 `required=false` 的 `keyword` 和
`category` 都加了 `@NotBlank`，导致两个参数实际都必填，只传一个会报 1000。

## 参数校验对齐实际契约（commit 1cd81bb）

上一条发现的 `@NotBlank` 问题顺藤摸瓜做了一次全量排查，`@RequestParam` 的**声明与实际行为不一致**
一共两类、7 处，一次改完：

**类型一：`required = false` + `@NotBlank`（可选路径永远不可达，方法体里的 null 分支是死代码）**

| 位置 | 参数 |
|---|---|
| `SearchController.search` | keyword、category |
| `OperationLogController.findByPage` | bizType |
| `CrossBorderSettlementController.recon` | batchNo |

**类型二：`defaultValue = ""` + `@NotBlank`（默认值永远不合法，等于必填却谎称可选）**

| 位置 | 参数 |
|---|---|
| `UserAccountController.create` | username |
| `CrossBorderRemittanceController.returnRemittance` | reason（同方法的 operator 默认 "system" 是合法的，不用改） |
| `CrossBorderAccountController.freeze` / `unfreeze` | reason、operator 各 4 处 |

**修法**：类型一删 `@NotBlank`（保留 `@Size`，`@Size` 对 null 放行），类型二删 `defaultValue = ""`
让它名副其实地必填（报错文案从"不能为空"变成"Required request parameter ... is not present"，都是 1000）。
`@Valid` 字段上的 `@NotBlank` 全部保留——那些本来就是必填。

**排查手法**：`@NotBlank` 在本项目里是**必填**参数的惯用写法，所以判据是
「`@NotBlank` 旁边有没有 `required = false` 或 `defaultValue = ""`」。
两个 grep 就能覆盖：全部 `required = false`（本项目仅 12 处）+ 全部 `defaultValue = ""`（仅 4 处）。
顺带核过 `defaultValue = "0"` 的 4 处，约束都是 `@Min(0)` 一类，没有同类问题。

**顺带加固**：搜索的 `minPrice` / `maxPrice` 补 `@PositiveOrZero`。

**边界取舍（有意为之）**：`minPrice > maxPrice` **不加**校验。负价格属于「取值越界」，要拦；
而 min>max 属于「条件矛盾」，结果是空集，语义明确——和 `keyword=不存在的词` 返回空是同一类，
拦了反而与关键字的行为不一致。判据是：**拒绝越界值，允许空结果查询**。

**验证**：搜索 7 例（只 keyword / 只 category / 全不传 / 空串 / 超长 257 → 1000 / minPrice=-1 → 1000 / count）、
操作日志 2 例（带与不带 bizType）、对账 2 例、必填回归 3 例（少传 reason/username 仍 1000，且校验先于服务调用故无脏写）、
参数齐全建账户 1 例（成功）。
⚠️ 建账户那条真的往副本库写了数据，已用 Java 单文件 + mariadb 驱动删掉（`user_account` 表，id=8）。

## SearchIndexInitializer 注释补齐（commit 291aca1）

纯注释。写清了四件事：
1. **为什么必须显式建索引**：动态映射会把字符串一律推断成 text，而 text 做 terms 聚合直接报错；
   createTime 不声明 date 就没法范围查询和排序；中文不配分词器只能整串匹配。而**字段类型不可改，只能 reindex**，
   所以要在建索引这步钉死
2. **幂等策略的代价**：「存在就跳过」是被迫的（无条件重建等于删索引删数据），
   代价是**改了 mapping 代码对已有索引不生效**，要手动 put mapping 或 reindex
3. **为什么 1 分片 0 副本**：这套 ES 是单节点（`_cat/nodes` 只有一个 `257279f5343a`），
   副本数 >0 会一直 unassigned，健康度永远进不了 green
4. **IK 分工**：写入 `ik_max_word`（细）、查询 `ik_smart`（粗）

建不出来就抛 `IllegalStateException` 让启动失败——这是有意为之，不是漏了兜底。

## ES 与 MySQL 一致性治理（commit f819569）

**先补的洞**：原来只有手动全量重建，且只写不删 —— 删掉商品后索引里留下幽灵文档，
搜索结果里还能看到已经不存在的商品。

### 设计：MySQL 是权威源，索引是可丢弃的派生视图，只朝一个方向收敛

| 路径 | 机制 | 覆盖什么 |
|---|---|---|
| 实时 | `ProductServiceImpl` 增删改发 `ProductChangedEvent`，`ProductChangedListener` 用 `@TransactionalEventListener(AFTER_COMMIT)` 消费 | 正常情况（绝大多数） |
| 手动 | `POST /api/search/sync`（全量+清孤儿）、`POST /api/search/sync/{id}`（单条） | 已知出问题时的止血 |
| 兜底 | `SearchConsistencyTask` 定时 `repairConsistency()` 自愈；`GET/POST /api/search/consistency[/repair]` | ES 不可用、进程刚提交就挂、有人绕过应用改库 |

### 几条踩过的关键结论

- **事件只带 id，不带实体**：监听器在提交后才消费，回查数据库拿到的才是已提交的最终值；
  带实体等于把事务内快照传出去，并发更新会用旧值覆盖索引。只带 id 还天然幂等、抗乱序。
  也**不区分新增/更新/删除**——回查不到就当删除处理，少维护一个可能填错的字段
- **afterCommit 监听器必须自己 try/catch**：回调里抛出的异常会冒到调用事务的方法，
  变成「数据库提交成功了，接口却返回失败」。实测验证过这条
- **缓存模块只发事件，不反向依赖 search**（现在是 search 依赖 cache 的 `ProductMapper`，反向加就成环）
- **对账必须两侧全量**：任一侧截断，「多出来的一半」就会被误判成孤儿删掉。
  所以超上限直接抛 `CODE_CAPACITY_EXCEEDED`(新增 1007) 拒绝执行，而不是近似对账。
  但 `syncAll` 的孤儿清理相反——它没有比对动作，漏清理最多留幽灵文档，超限时跳过+告警就够
- **ES 近实时会骗人**：修复后紧接着复查，会看到「修复成功」和「同一批差异还在」同时发生
  （默认 1 秒才可见）。只给运维类动作（`syncAll`、实际修过的 `reconcile`）收尾加 `refresh()`，
  业务写入路径不加（每次写都刷新会不停产生新分段）
- **价格比对只能用 `compareTo`**：库里 `decimal(12,2)` 的 599.00 进 ES 变 double，读回来是 599.0，
  `BigDecimal.equals` 连小数位数一起比，用 equals 会对着一堆正常数据报差异
- 对账不比对 `description`：它是 name+category 的派生字段，库里没有对应列

### 测试手法（值得复用）

- **造漂移**：直接 curl 操作 ES —— `DELETE _doc/{id}` 造漏同步、`_update` 改字段造脏数据、
  `PUT _doc/{不存在的id}` 造孤儿
- **注入 ES 写故障用 `PUT /{index}/_settings {"index.blocks.write":true}`**，测完改回 false 即可。
  比停 ES 容器安全得多，而且随时可逆
- 定时任务用 `--dong.elasticsearch.reconcile-interval-ms=2000` 启动，`ping -c N 127.0.0.1` 等待
  （`execute_command` 不能含 sleep，ping 是合法的耗时手段），再 grep 日志验证
