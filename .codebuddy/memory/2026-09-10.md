各篇核心结论（易错点）：
- **不丢失**：三段都要堵（同步发送+重试 / 同步刷盘+多副本 / **手动 ack 且先处理再确认**）；
  金融级再加「**消息落库 + 定时补偿**」；终极兜底是**对账**
- **幂等**：MQ 只能「至少一次」，重复是**必然**的。
  最推荐**状态机/乐观锁**（带原状态的 update，不用新表）；最可靠是**数据库唯一键（和业务同事务）**；
  Redis SETNX 只能挡大部分，**必须数据库兜底**。常见错误：先查再插（并发失效）、重复时抛异常（无限重试）
- **顺序**：全局有序=单分区单线程（**基本不用**）；实际用**分区有序**（同一 key 路由同一队列 + 同步发送 + 单线程消费）。
  **最大的坑：失败重试会跳到后面** → 要「挂起队列」(SUSPEND_CURRENT_QUEUE_A_MOMENT) 而非跳过。
  另外**消息带完整状态/版本号时可以不要顺序**（旧版本丢弃即可）
- **堆积**：主因是**消费端变慢**（慢 SQL/远程调用）；
  **消费者数不能超过分区数**（多出来的空转）→ 先扩分区再加消费者；
  死信队列是**隔离永远失败的消息**，要告警+分析根因，不是垃圾桶
