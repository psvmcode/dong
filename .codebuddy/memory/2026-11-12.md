## 全站服务端稳定性审查与修复（仅静态分析，未启动服务）

用户要求「仔细看是否存在容易引发服务端错误的逻辑（空指针、OOM 等），修复到没问题为止，不用测试，只从代码层面分析」。

做法：加载 dong-standards → 5 个只读 code-explorer 子代理分模块审查 + 全局 grep 高危模式 → 逐条 read_file 核实 → 按文件分批 replace → 每批 `mvn -q clean compile` 验证 → 再用 1 个子代理独立复核残留。共改 60+ 个 Java/XML 文件。

### 主要修复类别
- **500/NPE/越界**：`UploadInitRequest.fileSize` 加 `@NotNull`；`UploadStorage` 的 safeName 判空 + InvalidPathException + uploadId 路径越界 guarded；`FxExposureServiceImpl` 的 split 与金额/汇率判空；RPC 分页 clamp；`ServiceInstance` 地址解析；MQ payload 判空
- **数值/解析异常**：AmlMonitor / FxQuote / RedPacket / Seckill / LockLab / Tcc×2 的 parse 与除零保护；LocalRateLimiter / LuaRateLimiter 零窗口与 Lua nil；replica 转账负数与溢出校验；upload 默认 chunkSize 为 0 的除零
- **OOM/无界**：9 处 `selectAll`/`selectFollowers`/`selectSettledByBatch` 把上限下推到 SQL limit；syncAll/reconcile/warmUp 先 count 预检；UV 日期跨度上限；周榜分批扫描；本地消息总线有界队列 + `@PreDestroy`；延迟任务在途上限；SSE 流式行/工具参数封顶；ProtoCodec 字段总数上限；牌价缓存 SCAN 分批删除
- **资源/静默失败**：GZIP 流泄漏、日志回填位点延后到 flush 成功、`RpcClient` 出站帧长度、两个 MQ listener 检查 `handle` 返回值触发重投、reindex 失败保留旧索引、TCC `payloadOf` 容错、跨境补偿任务逐条 try/catch、upload 取消态复活改 CAS
- **并发/状态**：E8 闸门 finally + `future.get` 超时、SSE `complete()` 不误改挂起态、布隆过滤器双重检查、FxQuote 调价缓存按前缀 SCAN 失效

### 明确未改（架构/运维层面，非局部修复）
`RpcServerHandler` 在 EventLoop 上同步跑业务、`AgentRunEngine` 工具超时不中断底层线程、`SocialServiceImpl` 事务内写 Redis、TCC TRYING 态恢复、`ComplianceServiceImpl` Lua double 精度、X-Forwarded-For 伪造（需可信网关配置）。这些改动牵连架构或需运维配合，本轮按要求只做静态分析。
