# 2026-09-13

## 容错复查补漏（commit f2649f9）

用户再次提出「不信任任何接口参数，做好所有兜底」。做了一轮**复查**（不是重做），先确认已覆盖项，
再专找上一轮漏掉的：

- ✅ 复查通过：`@RequestBody` **全部带 @Valid**（无遗漏）；Controller 里的 `List<>` 全是**返回值**不是入参，
  不存在集合入参撑爆内存的问题
- ❌ 新发现并修复：`ProductController.findAll()`（`/api/cache/products/all`）
  **完全没有分页**，直接 `selectAll()` 全量返回。数据量一大就 OOM。
  已改为：超过 `Constants.MAX_BATCH_SIZE`(1000) 就截断 + `log.warn` 告警。
  理由：全量接口必须设上限——**宁可截断并告警，也不能让一次查询拖垮整个服务**

## 已完成的容错全景（累计 5 个 commit）

| 层 | 措施 |
|---|---|
| 入参 | 数值上下限、字符串非空/长度、金额精度(@Digits)、路径参数、分页上限 |
| 安全 | 短链 SSRF（协议白名单+内网拦截）、500 异常脱敏(traceId)、工作目录逃逸防护思路 |
| 并发 | LockLab 乘积兜底（Controller 分别限 + Service 总量限 20000） |
| 流量 | 全局 IP 令牌桶（排除 actuator）、Tomcat 线程池上限 |
| 传输 | 请求体 2MB、Jackson 嵌套深度 32、字符串长度上限 |
| 查询 | 全量接口截断上限 |
| 异常 | 全局 handler 全类型覆盖 |

## 重要教训（本轮）

直接重做会浪费大量 token。正确做法：复查 → 找漏 → 只补漏。
