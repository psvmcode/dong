# JMM：Java 内存模型到底规定了什么

> 目标：说清为什么需要它、happens-before 是什么，以及它和 volatile 的关系。

---

## 一句话

**JMM 是一套规范，规定「一个线程对共享变量的写入，什么时候能被另一个线程看到」。**

它不是物理上的内存划分，别和「堆、栈、方法区」那个运行时数据区搞混——
**后者是内存怎么分区，JMM 是多线程怎么正确读写**。

---

## 为什么需要它

因为硬件和编译器会做两件「优化」，在多线程下会闯祸：

| 优化 | 单线程下 | 多线程下 |
|---|---|---|
| **CPU 缓存** | 读得快，没问题 | 一个线程改了自己缓存里的值，别的线程看不到 |
| **指令重排序** | 结果不变，没问题 | 执行顺序变了，别的线程看到了「中间状态」 |

不同 CPU 架构（x86、ARM）的缓存和重排序规则还不一样。

**JMM 的作用就是屏蔽这些硬件差异**：
它定义了一套规则，告诉 JVM 和编译器「你可以在这些范围内优化，但不能越过这条线」，
让 Java 程序在任何平台上都有**一致的并发语义**。

---

## 主内存与工作内存

JMM 的抽象模型：

```
线程 A          线程 B
  │                │
工作内存        工作内存      ← 每个线程私有（缓存、寄存器）
  │                │
  └──── 主内存 ────┘          ← 所有共享变量在这
```

规则：

1. 所有**共享变量都存在主内存**
2. 每个线程有**自己的工作内存**，里面是主内存的副本
3. 线程**不能直接读写主内存**，必须通过工作内存
4. 线程之间不能互相访问工作内存，只能通过主内存传递

**这解释了两件事**：
- 可见性问题：线程 A 改了工作内存，没及时刷回主内存，B 就看不到（对应 [volatile](../java/volatile.md)）
- 有序性问题：线程内的操作顺序可能和代码顺序不同

---

## happens-before：JMM 的核心

这是 JMM 最重要的一条规则，理解了它，并发问题就有判据了。

### 定义

**如果操作 A happens-before 操作 B，那么 A 的结果对 B 可见，且 A 的执行顺序在 B 之前。**

注意：它不是说「A 在时间上先发生」，
而是说「**A 产生的影响能被 B 观察到**」——这是因果关系，不是时间关系。

### 八条规则（重点记前四条）

| 规则 | 内容 |
|---|---|
| **程序顺序规则** | 一个线程内，前面的操作 happens-before 后面的操作 |
| **volatile 规则** | 对 volatile 变量的**写** happens-before 后续对这个变量的**读** |
| **锁规则** | **解锁** happens-before 后续对这个锁的**加锁** |
| **传递性** | A hb B，B hb C，则 A hb C |
| 线程启动规则 | `Thread.start()` happens-before 线程里的任何操作 |
| 线程终止规则 | 线程里的任何操作 happens-before 别的线程检测到它已终止 |
| 线程中断规则 | 调用 `interrupt()` happens-before 被中断线程检测到中断 |
| 对象终结规则 | 对象构造完成 happens-before `finalize()` 开始 |

**前四条是最常用的**，特别是 volatile 规则和锁规则——
它们正是 volatile 和 synchronized 能保证可见性的理论依据。

### 怎么用

判断一段并发代码有没有问题，就看**两个操作之间有没有 happens-before 关系**。

```java
// 线程 A
x = 1;              // 操作 1
flag = true;        // 操作 2（flag 是 volatile）

// 线程 B
if (flag) {         // 操作 3
    // 这里能看到 x == 1 吗？
}
```

用规则推：
- 操作 1 hb 操作 2（程序顺序规则）
- 操作 2 hb 操作 3（volatile 规则）
- 所以操作 1 **hb** 操作 3（传递性）→ **能看到 x == 1** ✅

**如果 flag 不是 volatile**，就没有第二条，推不出来，
线程 B 可能看到 `flag == true` 但 `x` 还是 0。

## JMM 对 volatile 的规定

回顾 [volatile](../java/volatile.md) 的两个作用，在 JMM 里的表述是：

| 作用 | JMM 的规定 |
|---|---|
| 可见性 | 写 volatile 时，必须**立即刷新到主内存**；<br>读 volatile 时，必须**先从主内存重新加载** |
| 禁止重排序 | 在 volatile 读写前后插入**内存屏障**，阻止特定类型的重排序 |

**内存屏障（Memory Barrier）**：一条特殊指令，
告诉 CPU 和编译器「前后指令不能跨越这条线重排」。

四种屏障：

```
LoadLoad    : 前面的读不能和后面的读重排
StoreStore  : 前面的写不能和后面的写重排
LoadStore   : 前面的读不能和后面的写重排
StoreLoad   : 前面的写不能和后面的读重排（最重，四条全有）
```

JMM 规定：volatile 写后面插 `StoreLoad` + `StoreStore`，
volatile 读后面插 `LoadLoad` + `LoadStore`。
这就是 volatile 能禁止重排序的物理实现。

## as-if-serial：单线程下的自由

**不管怎么重排序，单线程程序的执行结果不能被改变。**

编译器、CPU 可以随便重排，只要单线程下结果一致就行。

```java
int a = 1;      // 1
int b = 2;      // 2     1 和 2 之间没有依赖，可以重排
int c = a + b;  // 3     3 依赖 1、2，不能排到它们前面
```

这条规则说明了：**重排序是真实存在且被允许的**，
`as-if-serial` 只是保证单线程下你察觉不到。多线程下就未必了。

## 常见误解

**误解一：JMM 就是堆和栈**
不是。堆/栈/方法区是「运行时数据区」（内存怎么分），
JMM 是「并发读写规范」（多线程怎么正确访问）。两回事。

**误解二：happens-before 就是时间上的先后**
不是。A happens-before B 表示「A 的影响对 B 可见」，
时间上 A 可能确实晚于 B，但只要满足 hb 规则，就认为 A 的结果对 B 可见。

**误解三：有了 JMM 就不用担心并发问题**
JMM 只是**定义了规则**——它告诉你什么时候能看到，
但不保证你的代码自动正确。你仍需要用 volatile、锁、原子类来建立 hb 关系。
