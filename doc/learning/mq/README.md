## 建议阅读顺序

`message-loss` → `idempotent` → `order-message` → `backlog`

前两篇是**必考且互相关联**：消息不丢要靠重试和手动 ack，
而这些措施恰恰**带来重复消费**，所以幂等是必需的。
后两篇是高频场景题。

## 一条主线

**MQ 提供的是「至少一次投递」，不是「恰好一次」。**

这句话解释了整个 MQ 的设计：

| 由此产生的问题 | 应对 |
|---|---|
| 消息可能丢 | 三段保障 + 对账兜底 |
| 消息可能重复 | 消费端**幂等** |
| 可能乱序 | 分区有序 + 业务带版本号 |
| 可能堆积 | 监控 Lag + 预留分区数 |

**幂等是 MQ 消费端的第一原则**——
不要指望 MQ 帮你去重，也不要指望「恰好一次」能覆盖外部系统。
