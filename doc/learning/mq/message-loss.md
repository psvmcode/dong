# 消息不丢失：三个环节各自要做什么

> 目标：说清消息在哪些环节会丢，以及每环的保障手段和代价。

---

## 一句话

**消息从生产到消费经过三段，每一段都可能丢——生产端、Broker 端、消费端，三段都要堵住。**

只做一端的保障没用，中间任何一环漏了，整条链路就不靠谱。

---

## 全景

```
生产者 ──①──> Broker ──②──> 消费者
             (存下来)      (处理完)

① 网络抖动、发送失败没重试  → 丢
② Broker 宕机、还没刷盘    → 丢
③ 消费者拿到就 ack，但处理失败 → 丢
```

---

## 环节一：生产端不丢

### 为什么会丢

```java
producer.send(msg);     // 发出去就不管了
```

网络抖动、Broker 短暂不可用，消息没到 Broker，
但生产者不知道（或者知道了也没处理）→ 丢了。

### 怎么解决

**1. 用同步发送 + 检查返回结果**

```java
// ❌ 发出去不管
producer.send(msg);

// ✅ 同步发送，拿到结果再判断
SendResult result = producer.send(msg);
if (result.getSendStatus() != SEND_OK) {
    // 记录、重试、告警
}
```

异步发送必须写回调：

```java
producer.send(msg, new SendCallback() {
    @Override
    public void onSuccess(SendResult result) { }

    @Override
    public void onException(Throwable e) {
        // ❗ 必须处理：记录日志、落库、后续补偿
        // 只打日志是不够的，消息已经丢了
    }
});
```

**2. 失败重试**

网络类失败（超时、连接失败）**必须重试**。

```java
producer.setRetryTimesWhenSendFailed(3);   // RocketMQ
```

**注意**：重试可能带来**重复消息**（网络慢导致超时，但 Broker 其实收到了），
所以消费端必须做幂等——见 [idempotent.md](idempotent.md)。

**3. 各 MQ 的生产端确认机制**

| MQ | 机制 | 说明 |
|---|---|---|
| **RabbitMQ** | **publisher confirm** | Broker 收到后异步回一个 ack，生产者没收到就重发 |
| **Kafka** | `acks` 参数 | `acks=all`（等所有副本写完才算成功）最保险 |
| **RocketMQ** | 同步/异步发送 + 重试 | 同步发送最保险 |

### 极端保障：消息落库 + 定时补偿

金融级场景（比如跨境支付的汇款指令）光靠重试不够：

```
1. 业务操作和「待发送消息」在【同一个数据库事务】里落库
2. 后台任务扫描未发送的消息，调用 MQ 发送
3. 发送成功后更新状态为「已发送」
4. 发送失败的下次继续重试
```

**核心思想**：把消息先当业务数据存下来，保证**业务成功则消息一定不会消失**。

这就是「本地消息表」方案，也是分布式事务的常用手段。
（我们项目里跨境支付的异步清算就是类似思路。）

## 环节二：Broker 端不丢

### 为什么会丢

消息到了 Broker，还在**内存里没刷到磁盘**，Broker 宕机 → 丢了。

### 怎么解决

**1. 持久化 + 合理的刷盘策略**

| 策略 | 行为 | 可靠性 | 性能 |
|---|---|---|---|
| **异步刷盘** | 写内存就返回，后台定时刷盘 | 宕机会丢 | **高** |
| **同步刷盘** | **刷到磁盘才返回** | 基本不丢 | 低 |

```java
// RocketMQ
flushDiskType = SYNC_FLUSH      // 同步刷盘
```

**同步刷盘的代价**：每个消息都要等一次磁盘 IO，吞吐量大幅下降。

**2. 多副本（主从同步）**

单台机器刷盘了，但机器整体坏了（硬盘损坏）还是丢。
所以要**多副本**：消息至少写到 2~3 个节点才算成功。

| MQ | 配置 |
|---|---|
| Kafka | `acks=all` + `min.insync.replicas=2` |
| RocketMQ | 主从同步（`SYNC_MASTER`）+ 至少 2 个 Broker |
| RabbitMQ | 镜像队列（已不推荐）/  quorum queue |

**3. 选择建议**

| 场景 | 配置 |
|---|---|
| 日志、监控数据（丢了无所谓） | 异步刷盘，性能优先 |
| 业务消息（不能丢） | **同步刷盘 + 多副本** |
| 金融级 | 同步刷盘 + 多副本 + **生产端落库补偿** |

## 环节三：消费端不丢

### 为什么会丢

**最常见的原因是「自动 ack」**：

```java
// ❌ 典型错误：拿到消息就自动确认
consumer.registerMessageListener((msgs, context) -> {
    process(msgs);                 // 处理失败会抛异常
    return ConsumeConcurrentlyStatus.CONSUME_SUCCESS;
});
```

如果 `process()` 抛异常或进程重启，
Broker 认为消息已经被消费（因为已经 ack 了），**不会重投** → 丢了。

### 怎么解决

**手动 ack，且必须是「业务处理成功后才确认」**：

```java
consumer.registerMessageListener((msgs, context) -> {
    try {
        process(msgs);
        return ConsumeConcurrentlyStatus.CONSUME_SUCCESS;   // ✅ 成功后才确认
    } catch (Exception e) {
        log.error("consume failed", e);
        return ConsumeConcurrentlyStatus.RECONSUME_LATER;   // ✅ 失败则稍后重试
    }
});
```

**顺序不能反**：

```
❌ 先 ack 再处理  → 处理失败消息就丢了
✅ 先处理再 ack  → 处理失败，Broker 会重投
```

**注意**：手动 ack 会带来**重复消费**——
处理成功但 ack 时网络失败，Broker 会重投，消费者会再处理一次。
所以幂等是必需的。

## 完整保障清单

| 环节 | 措施 | 带来的问题 |
|---|---|---|
| 生产端 | 同步发送 + 失败重试 + confirm | 可能重复 |
| 生产端（金融级） | **消息落库 + 定时补偿** | 实现复杂 |
| Broker | **同步刷盘** | 性能下降 |
| Broker | **多副本** | 成本上升 |
| 消费端 | **手动 ack（先处理再确认）** | 可能重复消费 |
| 消费端 | 失败进**重试队列 / 死信队列** | 需要监控 |

---

## 代价与取舍

**没有免费的可靠性**。每加一层保障都有代价：

| 保障 | 代价 |
|---|---|
| 同步刷盘 | 吞吐可能下降一个数量级 |
| 多副本 | 存储成本翻倍，写入延迟增加 |
| 同步发送 | 每条消息多一个 RTT |
| 手动 ack | 可能重复消费，需要幂等 |

**判断标准**：

- **日志、埋点、监控**：异步刷盘 + 异步发送，丢几条无所谓
- **一般业务消息**：同步发送 + 异步刷盘 + 手动 ack
- **订单、支付、资金**：**全链路最强保障 + 幂等 + 对账**

**最后一句很重要**：

> 再强的 MQ 保障也只是「尽量不丢」，
> 真正兜底的是**对账**——定期拿业务数据和消息记录比对，
> 发现不一致就补偿。这和资金系统的思路完全一致。
