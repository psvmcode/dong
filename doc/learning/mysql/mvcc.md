# MVCC：为什么你能读到数据的旧版本

> 目标：说清快照读、undo log 版本链、ReadView 这三个词，以及它们怎么配合。

---

## 一句话

**MVCC 就是给每行数据保留多个历史版本，让读操作不用加锁也能读到一致的数据。**

它解决的核心矛盾：**读的时候不想被写阻塞，写的时候也不想阻塞读**。

如果读要加锁、写也要加锁，那读写就串行了，并发极低。
MVCC 的做法是：写的时候创建新版本，读的时候读旧版本，**各走各的路，互不干扰**。

---

## 快照读 vs 当前读

这是理解 MVCC 的第一道门槛。

| 类型 | 语句 | 读到什么 |
|---|---|---|
| **快照读** | 普通 `select * from t where ...` | 读**快照**（历史版本），不加锁 |
| **当前读** | `select ... for update`<br>`select ... lock in share mode`<br>`insert` / `update` / `delete` | 读**最新版本**，并且加锁 |

**关键点**：

- 普通的 `select` 是快照读，**不加任何锁**，所以不会被别的写操作阻塞
- `update`、`delete` 虽然看起来是写，但它们内部要先「找到要改的行」，这步是**当前读**，会加锁
- `select ... for update` 手动把快照读升级成当前读

```sql
-- 事务 A
begin;
select balance from account where id = 1;        -- 快照读，不加锁

-- 事务 B 同时改并提交
update account set balance = 500 where id = 1;    -- 不阻塞！

-- 事务 A 再查（可重复读下）
select balance from account where id = 1;         -- 还是旧值，因为读的是同一个快照
```

## 三个组成部分

MVCC 靠三个东西配合：隐藏字段、undo log 版本链、ReadView。

### 1. 每行数据的两个隐藏字段

InnoDB 每行记录都有几个看不见的字段：

| 字段 | 含义 |
|---|---|
| `DB_TRX_ID` | **最后修改这行的事务 id** |
| `DB_ROLL_PTR` | **回滚指针**，指向这行的上一个版本 |

（还有一个隐藏的 `row_id`，没主键时才有）

### 2. undo log 版本链

每次修改一行，InnoDB 会把**旧版本写进 undo log**，然后用 `DB_ROLL_PTR` 串起来，形成一条**版本链**。

```
当前行 (balance=500, trx_id=30)
    ↑ roll_ptr
旧版本 (balance=800, trx_id=20)
    ↑ roll_ptr
更旧   (balance=1000, trx_id=10)
```

**这条链是 MVCC 的核心**：想要哪个版本，顺着链往下找就行。

注意：undo log 不是无限保留的，事务提交后如果没人再需要这些旧版本，
会由后台的 purge 线程清理掉。

### 3. ReadView（快照）

ReadView 就是**事务在某一刻拍的一张「谁提交了、谁没提交」的照片**，主要包含：

| 内容 | 说明 |
|---|---|
| `m_ids` | 生成快照时，**还在活跃（未提交）的事务 id 列表** |
| `min_trx_id` | 活跃事务里最小的 id |
| `max_trx_id` | 系统下一个要分配的事务 id |
| `creator_trx_id` | 生成这个 ReadView 的事务自己的 id |

---

## 判断规则：这行数据我能看到吗

拿着 ReadView 去版本链上比对，规则就三条：

```
从这个版本开始，顺着链往回找，直到找到第一个「我能看到」的版本：

1. 若 trx_id == creator_trx_id
   → 是自己改的，能看到

2. 若 trx_id < min_trx_id
   → 这个版本是我生成快照之前就提交的，能看到

3. 若 trx_id >= max_trx_id
   → 这个版本是我生成快照之后才产生的，看不到，继续往回找旧版本

4. 若 min_trx_id <= trx_id < max_trx_id
   → 要看 trx_id 在不在 m_ids 里：
      在    → 说明这个事务当时还没提交，看不到，往回找
      不在  → 说明已经提交了，能看到
```

**一句话概括**：顺着版本链往回找，找到第一个「在我生成快照时就已经提交」的版本。

## 读已提交 vs 可重复读的唯一区别

**就是 ReadView 生成的时机不同**：

| 隔离级别 | ReadView 何时生成 |
|---|---|
| **读已提交** | **每次**执行 select 都重新生成一个 |
| **可重复读** | 只在事务中**第一次** select 时生成，之后一直复用 |

这一个差异解释了全部现象：

```
-- 可重复读
事务 A 第一次 select  → 生成 ReadView#1
事务 B 修改并提交
事务 A 第二次 select  → 还是用 ReadView#1  → 看到旧值 → 可重复读 ✅

-- 读已提交
事务 A 第一次 select  → 生成 ReadView#1  → 看到旧值
事务 B 修改并提交
事务 A 第二次 select  → 重新生成 ReadView#2 → 看到新值 → 不可重复读
```

---

## MVCC 解决不了什么

**MVCC 只对快照读生效**。当前读（`for update`、`update`、`delete`）读的是最新版本，
并且要靠**锁**来保证不被并发修改。

所以 InnoDB 的完整方案是：

```
快照读 → 靠 MVCC，不加锁，性能好
当前读 → 靠锁（行锁 + 间隙锁），保证强一致
```

两者配合，才有了「可重复读」这个既保证一致性、又有不错并发的级别。
锁的部分见 [lock.md](lock.md)。

## 常见疑问

**Q：undo log 会不会无限增长？**
不会。没有事务需要访问这些旧版本时，purge 线程会清理。
但如果有一个**长时间不提交的事务**，它需要的旧版本都不能删，
undo log 会一直涨——这是长事务的危害之一。

**Q：为什么建议事务尽量短？**
除了锁持有时间长，还因为长事务会让 ReadView 一直存在，
导致大量 undo log 无法清理，可能把 ibdata 表空间撑爆。

## 记忆口诀

| 概念 | 一句话 |
|---|---|
| 快照读 | 普通 select，不加锁，读历史版本 |
| 当前读 | for update / update / delete，加锁，读最新版本 |
| undo log 版本链 | 旧版本串成的链表，版本从这里来 |
| ReadView | 「谁提交了」的快照，决定我能看到哪个版本 |
| 两级别差异 | 读已提交每次生成 ReadView；可重复读只生成一次 |
