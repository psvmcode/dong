# 锁：什么时候会锁一行，什么时候锁全表

> 目标：说清行锁、表锁、间隙锁的加锁范围，以及死锁怎么排查。

---

## 一句话

**InnoDB 的行锁是加在索引上的，不是加在数据行上的。**
如果查询没走索引，就会退化成锁全表——这是最常踩的坑。

---

## 锁的分类

### 按粒度

| 类型 | 锁定范围 | 特点 |
|---|---|---|
| 表锁 | 整张表 | 开销小、加锁快、并发最差 |
| 行锁 | 单行 | 开销大、加锁慢、并发最好 |

**InnoDB 支持行锁，MyISAM 只支持表锁**——这是两者最重要的区别之一。

### 按类型（InnoDB 行锁细分）

| 类型 | 说明 |
|---|---|
| 记录锁（Record Lock） | 锁住**某一行**索引记录 |
| 间隙锁（Gap Lock） | 锁住**两条记录之间的空隙**，防止往里插数据 |
| 临键锁（Next-Key Lock） | 记录锁 + 间隙锁，**锁住一段左开右闭的区间** |

**临键锁是 InnoDB 默认的行锁单位**（可重复读级别下），它的存在就是为了**解决幻读**。

---

## 间隙锁：为什么要有它

假设表里已有 id = 1, 5, 10 三条记录。

```
事务 A：select * from t where id between 1 and 10 for update;
```

如果只锁住已存在的 1、5、10 三行，那别的事务仍然可以 `insert id = 7`——
事务 A 再查一次就多出一行，**幻读**了。

**间隙锁的作用就是把这个空隙也锁住**，让别的事务插不进来。

```
锁住的范围（临键锁，左开右闭）：
(-∞, 1]  (1, 5]  (5, 10]  (10, +∞)
```

`insert id = 7` 会落在 `(5, 10]` 这个区间，被阻塞。

**代价**：间隙锁会显著降低并发，而且更容易死锁。
这也是「读已提交」级别下没有间隙锁（只有行锁）、并发更好的原因。

---

## 什么情况会锁全表

**核心规律：锁是加在索引上的，走不到索引就锁所有行（效果等同锁表）。**

| 场景 | 后果 |
|---|---|
| `update t set ... where name = '张三'` 而 name 没索引 | 全表扫描，**锁住所有行** |
| 索引字段发生**隐式类型转换** | 索引失效，锁全表 |
| 对索引列用**函数** | 索引失效，锁全表 |
| 走索引但**优化器判断全表更划算** | 锁全表 |

**隐式类型转换的坑**（极常见）：

```sql
-- phone 是 varchar 类型，有索引
update user set age = 20 where phone = 13800138000;   -- 数字，类型不匹配
-- MySQL 会对 phone 做隐式转换 → 索引失效 → 锁全表！

update user set age = 20 where phone = '13800138000'; -- 字符串，正确走索引
```

**函数的坑**：

```sql
update t set ... where date(create_time) = '2026-09-09';   -- 用了函数，索引失效
update t set ... where create_time >= '2026-09-09'
                  and create_time < '2026-09-10';          -- 改成范围，走索引
```

## 死锁：怎么产生，怎么排查

### 产生条件

两个事务互相持有对方需要的锁：

```
事务 A：update t set ... where id = 1;   -- 拿到 id=1 的锁
事务 B：update t set ... where id = 2;   -- 拿到 id=2 的锁
事务 A：update t set ... where id = 2;   -- 等 B 释放
事务 B：update t set ... where id = 1;   -- 等 A 释放   ← 死锁
```

**最常见的业务场景**：两个事务以**不同的顺序**更新同一批记录。
典型如转账：A 转 B 和 B 转 A 同时发生。

### InnoDB 怎么处理

检测到死锁后，会**回滚其中一个事务**（通常是影响行数少的那个），让另一个继续。
等待超时由 `innodb_lock_wait_timeout` 控制，默认 50 秒。

**注意**：MySQL 能自动检测并解开死锁，但**应用层必须处理重试**——
被回滚的那个事务会报错，不重试这笔业务就丢了。

### 怎么排查

```sql
-- 查看最近的死锁信息（最重要的一条命令）
show engine innodb status;
```

输出里找 `LATEST DETECTED DEADLOCK` 段，能看到：
- 两个事务各自持有什么锁、在等什么锁
- 各自的 SQL 语句
- 最终哪个被回滚了

```sql
-- 查看当前正在等待的锁
select * from information_schema.innodb_locks;      -- MySQL 5.7
select * from performance_schema.data_locks;        -- MySQL 8.0

-- 查看当前的事务
select * from information_schema.innodb_trx;
```

### 怎么避免

| 方法 | 说明 |
|---|---|
| **固定访问顺序** | 最有效。批量更新时先按 id 排序，保证所有事务顺序一致 |
| 缩小事务范围 | 事务越短，持锁时间越短 |
| 避免间隙锁 | 业务允许的话用「读已提交」（没有间隙锁） |
| 用主键更新 | 避免非索引条件导致锁范围扩大 |
| 加重试 | 死锁无法完全避免，应用层要有重试机制 |

## 加锁规则速查（可重复读级别）

| 操作 | 加什么锁 |
|---|---|
| `select ...`（快照读） | **不加锁**（MVCC） |
| `select ... lock in share mode` | 临键锁（共享） |
| `select ... for update` | 临键锁（排他） |
| `update` / `delete` | 临键锁（排他） |
| `insert` | 插入意向锁 + 可能触发间隙锁冲突 |

**唯一索引等值查询时**，临键锁会退化成**记录锁**（只锁那一行），
因为唯一索引不可能有重复值，不需要锁间隙——这是个优化。

## 记忆口诀

| 问题 | 答案 |
|---|---|
| 锁加在哪 | **索引**上，不是数据行上 |
| 为什么会锁全表 | 没走索引（无索引 / 类型转换 / 用了函数） |
| 间隙锁干什么 | 锁住空隙防止插入，用来解决幻读 |
| 死锁怎么排查 | `show engine innodb status` 看 LATEST DETECTED DEADLOCK |
| 死锁怎么避免 | **固定访问顺序**最有效，其次缩短事务 |
