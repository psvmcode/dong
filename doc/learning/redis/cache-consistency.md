# 缓存一致性：三大问题和数据怎么同步

> 目标：说清穿透/击穿/雪崩的解法，以及缓存和数据库怎么保持同步。

---

## 三个问题，别搞混

名字相近但完全不是一回事，**区别在「什么 key」和「什么时刻」**：

| 问题 | 什么样的 key | 后果 |
|---|---|---|
| **穿透** | 查询**根本不存在**的数据 | 每次都打到数据库 |
| **击穿** | 一个**热点 key 恰好过期** | 瞬间大量请求打到数据库 |
| **雪崩** | **大量 key 同时过期** | 数据库被压垮 |

---

## 缓存穿透

### 现象

有人一直查 `id = -1` 这种**数据库里根本没有**的数据。

缓存查不到 → 去查数据库 → 数据库也没有 → **不写缓存** → 下次还是打数据库。

如果是恶意攻击（用大量不存在的 id 刷），数据库直接被打垮。

### 解法

**方案一：缓存空值**（最简单，本项目采用）

数据库查不到也缓存一个空值，设**较短的过期时间**（如 1~5 分钟）。

```java
if (data == null) {
    redis.set(key, NULL_MARKER, 5, MINUTES);   // 缓存空值
    return null;
}
```

缺点：如果攻击者每次用不同的不存在的 id，会缓存大量空值，占内存。
所以**过期时间要短**。

**方案二：布隆过滤器**

在缓存前面加一层布隆过滤器，它记录「哪些 key 可能存在」。

```
请求 → 布隆过滤器
        ├─ 说不存在 → 直接返回，不用查缓存和数据库
        └─ 说可能存在 → 继续查缓存 → 查数据库
```

- **优点**：内存极小（一个 key 约几个 bit）
- **缺点**：**有误判**（说「可能存在」的不一定真存在，但说「不存在」的一定不存在）
- **缺点**：删除困难，数据变更时要同步维护

**选择**：
- 攻击量不大 → 缓存空值就够了
- 海量数据、需要防恶意刷 → 布隆过滤器

## 缓存击穿

### 现象

某个**超热点 key**（比如首页的爆款商品）**恰好过期**了，
这一瞬间几千个请求同时发现缓存没有，**全部涌向数据库**。

和穿透的区别：**这个 key 是真实存在的，只是刚好过期**。

### 解法

**方案一：互斥锁（最常用）**

只让一个线程去查数据库重建缓存，其他线程等待。

```java
public Data getData(String key) {
    Data data = redis.get(key);
    if (data != null) return data;

    // 缓存没有，加锁重建
    if (lock.tryLock(key)) {
        try {
            data = redis.get(key);       // 双重检查，防止别的线程已经建好了
            if (data != null) return data;

            data = db.query(key);        // 查数据库
            redis.set(key, data, ttl);   // 写回缓存
            return data;
        } finally {
            lock.unlock(key);
        }
    } else {
        Thread.sleep(50);                // 没拿到锁，等一下重试
        return getData(key);
    }
}
```

**方案二：逻辑过期（热点数据永不过期）**

不给 key 设 TTL，而是在 value 里**存一个过期时间戳**。

```java
class CacheData {
    Object data;
    long expireAt;      // 逻辑过期时间
}
```

发现逻辑上过期了，返回旧数据的同时，**异步起个线程去重建**。

- **优点**：用户永远不会等待，体验好
- **缺点**：会短暂返回旧数据（**最终一致**，不是强一致）

**选择**：
- 对一致性要求高、能接受少量等待 → 互斥锁
- 超高并发、能接受短暂旧数据 → 逻辑过期

## 缓存雪崩

### 现象

**大量 key 在同一时刻集体过期**，或者 **Redis 直接挂了**。

所有请求瞬间全部打到数据库，数据库扛不住就挂了，
然后整个系统连锁崩溃。

### 解法

**1. 过期时间加随机值**（防同时过期）

```java
// 不要这样
redis.set(key, data, 30, MINUTES);

// 要这样
long ttl = 30 + random.nextInt(10);        // 30~40 分钟随机
redis.set(key, data, ttl, MINUTES);
```

**批量导入缓存时尤其要注意**，如果都设一样的 TTL，就会集体过期。

**2. Redis 高可用**

- 主从 + 哨兵（Sentinel）
- 集群（Cluster）

防止 Redis 整体挂掉。

**3. 降级和熔断**

Redis 挂了之后，应用要能**限流**（只放一部分请求去数据库）
或者直接**返回兜底数据**，不能眼睁睁看着数据库被冲垮。

**4. 多级缓存**

本地缓存（Caffeine）+ Redis + 数据库，
Redis 挂了还有本地缓存顶一层。

## 缓存和数据库怎么同步

这是个经典问题，先给结论：

### Cache Aside Pattern（旁路缓存，最常用）

**读流程**：
```
1. 先读缓存
2. 命中 → 直接返回
3. 没命中 → 读数据库 → 写入缓存 → 返回
```

**写流程**：
```
1. 更新数据库
2. 删除缓存        ← 注意是删除，不是更新
```

### 为什么是「删除缓存」而不是「更新缓存」

**因为更新缓存可能在并发下产生脏数据**：

```
线程 A：更新数据库 = 10
线程 B：更新数据库 = 20
线程 B：更新缓存 = 20
线程 A：更新缓存 = 10     ← 数据库是 20，缓存却是 10，脏了！
```

顺序错乱了。**删除缓存则不会有这个问题**——
下次读的时候发现没有，重新从数据库加载，一定是最新值。

而且很多时候缓存的 value 是**经过计算**的（比如多个表 join 的结果），
更新它的成本远高于直接删掉。

### 为什么是「先更新数据库，再删缓存」

反过来（先删缓存，再更新数据库）有问题：

```
线程 A：删除缓存
线程 B：读缓存，没有 → 读数据库（旧值 10）→ 写入缓存 = 10
线程 A：更新数据库 = 20
结果：数据库 20，缓存 10  ← 脏数据
```

**先删缓存的话，读请求可能在数据库更新前就把旧值又写回缓存了**。

而「先更新数据库，再删缓存」：
数据库更新的那点时间窗口内，缓存里还是旧值，
但**删除操作在最后**，能保证最终缓存里是新的。

### 这个方案也不是完美的

**极端情况**：

```
1. 缓存刚好过期
2. 线程 A 读数据库，得到旧值 10
3. 线程 B 更新数据库为 20，删除缓存
4. 线程 A 把旧值 10 写入缓存     ← 脏了
```

这个窗口很小（要求读缓存 miss + 写库完成 + 写入缓存，且顺序刚好），
但理论上存在。

**兜底办法**：给缓存设**较短的过期时间**，
即使脏了也会自动纠正。这是最简单有效的保障。

### 追求强一致怎么办

| 方案 | 说明 |
|---|---|
| **延迟双删** | 删缓存 → 更新数据库 → sleep 一小会儿 → 再删一次缓存 |
| **消息队列重试** | 删缓存失败就发消息，消费端重试直到成功 |
| **Canal 订阅 binlog** | 监听数据库变更，异步删除缓存（阿里常用） |

但**绝大多数业务不需要强一致**——
设个合理的过期时间，接受秒级的不一致，是最务实的方案。

**判断标准**：
- 缓存是用来**加速**的，不是权威数据源
- 能接受短暂不一致 → Cache Aside + 过期时间
- 不能接受（比如库存）→ 不要依赖缓存，直接查数据库并加锁

## 记忆口诀

| 问题 | 关键区别 | 解法 |
|---|---|---|
| 穿透 | 查**不存在**的数据 | 缓存空值 / 布隆过滤器 |
| 击穿 | **单个热点 key** 过期 | 互斥锁 / 逻辑过期 |
| 雪崩 | **大量 key** 同时过期 | TTL 加随机值 / 高可用 / 降级 |

| 同步问题 | 答案 |
|---|---|
| 更新时删还是改缓存 | **删除**（改会在并发下顺序错乱） |
| 先删缓存还是先改库 | **先改库再删缓存** |
| 这方案完美吗 | 不完美，靠**过期时间**兜底 |
| 强一致怎么做 | 延迟双删 / 消息队列重试 / Canal 订阅 binlog |
