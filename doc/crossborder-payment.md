## 〇、先不管名词：一笔跨境汇款到底在干什么（白话版）

这一节不出现任何需要查资料才能懂的词。看完它，你就知道后面所有专业名词在替谁说话。

### 0.1 一句话版本

你要给国外的人寄一笔钱，但**对方国家不收人民币**。所以这件事被拆成三步：

> 把人民币换成美元 → 交给跨国"快递公司"送出去 → 对方账户收到美元

而在这三步之外，还挂着两件甩不掉的事：

- **政府要审查**：这笔钱干净吗？你有资格汇这么多吗？（合规）
- **事后要核对**：快递公司说送到了，我账上也说送到了，两边对得上吗？（对账）

境内转账只是"从 A 账户挪到 B 账户"这一件事；跨境支付是**换钱、送钱、被审查、事后核对**四件事捆在一起办。这就是它复杂的全部原因。

### 0.2 出场角色

| 角色 | 白话 | 在本项目里 |
|---|---|---|
| 付款人 Alice | 要汇钱的人 | 一个人民币（CNY）账户，有钱、有额度 |
| 收款人 Bob | 收钱的人 | 一个美元（USD）账户 |
| 平台（本系统） | 帮你换汇 + 跑腿的机构 | `crossborder` 模块 |
| 安检口 | 查这笔钱能不能放行的四道关 | 制裁名单 / 身份等级 / 大额审查 / 限额 |
| 人工审核员 | 系统不敢自动决定时拍板的人 | 一个放行/驳回的接口 |
| 快递公司 | 真正把钱送过去的通道 | SWIFT / CIPS / LOCAL 三条，价格和快慢不同 |
| 对账员 | 拿对方的回单跟自家账本逐笔比对 | 对账任务 |
| 防重复编号 | 你给这次汇款起的唯一小名 | `idempotentKey` 幂等键 |

### 0.3 顺顺利利的一次汇款（走一遍完整的十步）

**例子**：Alice 要从她的人民币账户汇 10000 元给 Bob，让 Bob 收到美元。

---

**第 1 步：先把账户开好（只在最开始做一次）**

Alice 开一个人民币账户，Bob 开一个美元账户。开户时要说清楚四件事：

- 币种（Alice 是 CNY，Bob 是 USD）
- 身份核实等级（KYC 等级）：你提交的身份证明越充分，等级越高，能汇的钱越多
- 单笔最多能汇多少
- 一天最多能汇多少

> ⚠️ **注意**：跨境汇款要求两端币种**必须不一样**。两边都是人民币的话，系统直接拒绝——那不叫跨境。

---

**第 2 步：问个价（询价）**

Alice 问："1 万人民币现在能换多少美元？"

系统回一个报价，包含**两个价**，而且**只在 5 分钟内有效**（有效期可以自己指定）：

```
买入价 bid = 0.13965035
卖出价 ask = 0.14006993
```

这个"两个价"就像金店门口的牌子：**收购价 99，卖出价 101**。你拿人民币去买美元，走的是那个贵一点的价（卖出价）；中间这 2 块钱的差价，就是人家帮你换汇的服务费，也就是银行的利润。

所以 Bob 实际到手的钱，一定比"按市场中间价算出来的"要少一点点。

> 报价为什么要设有效期？因为汇率每分每秒都在变。如果给你报了个价，你三天后才用，那这个价早就不作数了。所以报价是"有时效的承诺"。

---

**第 3 步：提交汇款请求**

Alice 提交汇款申请，要带上：

- 付款账户、收款账户
- 汇出金额（10000 元）
- 刚才那个报价的编号（也可以不填，系统临时帮你问一个）
- **一个防重复编号**（比如 `demo-1`）：这个东西很重要，见 0.4 的 K 条
- 用哪条通道送（也可以不填，让系统自己挑）

---

**第 4 步：过四道安检（合规筛查）**

系统按顺序问四个问题，每一道的回答都单独记在案（事后监管来查时，这些记录就是"我审过了"的证据）：

| 顺序 | 白话问法 | 卡住的话 |
|---|---|---|
| 1 | 这个人在黑名单上吗？（恐怖组织、被制裁的个人/国家） | 在 → **直接拒绝** |
| 2 | 他的身份等级够汇这么多钱吗？ | 不够 → **直接拒绝** |
| 3 | 金额超过 5 万了吗？ | 超了 → **不是拒绝**，是挂起来等人审 |
| 4 | 超过单笔限额吗？加上以前的，超过今天的累计限额吗？ | 超了 → **直接拒绝** |

最终结论取最严重的那个：只要有一道说"拒绝"，整笔就拒；没有拒绝但有一道说"要人审"，就整笔挂起来等人审。

> 第 3 道为什么要"等人审"而不是"拒绝"？因为**大额汇款本身是合法的**。只是监管要求人工看一眼钱的来源和用途。把合法的大额交易一律拒掉，那是把客户往外赶。

---

**第 5 步：把汇率钉死（锁汇）**

四道安检都过完之后，系统把第 2 步那个报价**绑定到这笔汇款上**。

从这一刻起，无论市场汇率怎么变，这笔汇款就按这个汇率算。这叫"锁汇"。

> 为什么非锁不可？如果报价时不锁、等钱到账那天再按当天汇率算，那汇率跌了客户要闹，涨了平台亏。锁定的意思就是**双方都认这个价，后面行情跟我们无关了**。
>
> 一个报价只能被一笔汇款锁走。两个人同时抢同一个报价，只有一个人能成功，另一个人会拿到"报价已被占用"的提示。

---

**第 6 步：扣钱、记账、推进状态（三件事绑成一个整体）**

系统做三件事，而且**必须一起成功，要么一起失败**：

1. 从 Alice 账户扣掉 `汇出金额 + 手续费`
2. 写一条流水（谁、哪笔汇款、扣了多少、扣完剩多少）
3. 把汇款单状态改成"已扣款"

> 为什么必须绑在一起？想象一下：钱扣了，但流水没记，或者状态没改成"已扣款"。前一种是账对不上，后一种是这笔钱会被定时任务当成"扣款没成功"再处理一次。**资金系统里，钱和账必须同生同死。**

注意手续费是**在汇出金额之外额外扣的**，Bob 拿到的钱不会被手续费吃掉——他拿到的是 `10000 × 汇率` 那一整份。

---

**第 7 步：通知"快递公司"去送钱（发消息）**

系统发一条消息出去，意思是"这笔钱已经扣好了，可以给收款方入账了"。

**这一步有个非常关键的先后顺序：必须等第 6 步彻底落定之后，才能发这条消息。**

> 反过来的后果是真实的资金损失：如果先发消息、后落库，结果落库失败了（比如余额不足要回滚），那消息已经发出去了，下游收到通知就会去放款——钱出去了，本地却根本没这笔账。这就是所谓的"钱飞了"。

这一步是**异步**的：消息发出去就算完，不等对方处理。

---

**第 8 步：归入一个"批次"**

系统会找当前正在收货的批次，把这笔汇款单塞进去；找不到就自动开一个新的批次。

> 批次是什么？就是"今天下午 3 点前要走 SWIFT 通道的所有汇款，凑成一个包裹一起送"。真实世界里，跨境汇款不是来一笔发一笔，而是**攒一批、按点发一次**，因为这样成本低、好对账。
>
> 不归批的后果：对账的时候是"按批次拉取"的，没归批的单子就查不到，成了无人看管的盲区。

---

**第 9 步：清算——把钱真正送出去**

先说清楚"清算"这个词。金融上严格讲是两个动作：

| 词 | 干什么 | 类比 |
|---|---|---|
| 清算（Clearing） | **算账**：一段时间内的交易汇总、核对，算出谁该给谁多少 | 聚餐后算账，轧差之后 C 只需给 A 40 |
| 结算（Settlement） | **划钱**：按算出来的结果，真的把钱转过去 | C 真的把 40 转给 A |

日常和本项目里都混着叫"清算"，但要记住**算账在前、划钱在后**。

跨境之所以慢，是因为钱很少能直飞：中国的钱要变成美国的钱，中间往往要经过两三家代理行，每家都要核对、扣一笔费、再转发，每过一手就是半天到一天。SWIFT 要两天、本地清算只要半小时，差别就在**中转环节的多少**。

本项目的清算分两步，对应汇款单的三个状态：

| 状态 | 含义 | 钱在哪 |
|---|---|---|
| `FUNDS_DEBITED` 已扣款 | 已从 Alice 扣掉，还攥在平台手里 | 平台 |
| `SETTLING` 清算中 | 已交给渠道、渠道在处理，**还没确认到账** | 渠道（在途） |
| `SETTLED` 已结算 | 渠道确认到账，钱进了 Bob 账户 | Bob |

具体动作是：

1. 收到消息后，先把状态从"已扣款"推进到**"清算中"**——这一步**不碰任何钱**，只是标记"钱交出去了"
2. 接着给 Bob 加钱、写收款流水、推进到**"已结算"**——这三件事是一个整体，要么全成要么全撤

> 为什么要拆成两步？因为真实渠道的这两步之间隔着几分钟到两天。**"清算中"就是那笔悬在渠道手里、付款方已扣而收款方未收的在途资金**。把它单独表达出来，出问题时才说得清钱卡在哪一环。
>
> 本项目没有真实的渠道往返，两步紧挨着执行，所以"清算中"只停留毫秒级——想观察它，要看 `GET /remittance/runtime` 里的 `settlingEntered`（累计进入过清算中的笔数），各状态的**瞬时**数量永远是 0。

---

**第 10 步：事后核对（对账）**

批次关闭之后，系统拿这个批次里本地所有"已结算"的汇款，跟"快递公司"发回来的回单逐笔比对：

- 本地有、对方也有、金额也一样 → 平的，没事
- 本地有、对方没有 → **渠道漏单**（对方少报了一笔）
- 对方有、本地没有 → **渠道多单**（最危险，说明对方可能多放了一笔钱）
- 两边都有、金额不一样 → **金额不符**（多为中间行偷偷扣了手续费）

有差异就记进差异表，等人去处理。

### 0.4 各种可能出岔子的情况

上面走的是"一路绿灯"。下面把每一处可能分岔的地方都摊开。

#### A. 还没进门就被拦下（参数与账户层面）

| 情况 | 结果 |
|---|---|
| 付款账户和收款账户币种相同 | 直接拒绝：这不叫跨境 |
| 账户不存在 | 直接拒绝 |
| 付款账户或收款账户处于冻结状态 | 直接拒绝，一分钱都不会动 |
| 账户被重复冻结 | 第二次报"冲突"，不会重复记录 |
| 报价编号填错了 / 找不到 | 直接拒绝 |
| 报价已经过期（超过有效期） | 直接拒绝，需要重新问一个价 |
| 报价已经被别的汇款锁走了 | 直接拒绝，需要重新问一个价 |

#### B. 四道安检各自的卡法

| 检查 | 通俗说法 | 具体门槛 | 卡住的后果 |
|---|---|---|---|
| 制裁名单 | 这人是不是被全球通缉/制裁的对象 | 户主名字在黑名单里 | **直接拒绝** |
| 身份等级 | 你交的证明材料够不够 | 0 级最多 1000；1 级 1 万；2 级 10 万；3 级及以上 1000 万 | **直接拒绝** |
| 大额审查 | 这笔是不是太大了 | 超过 50000 | **挂起，等人工审核**（不是拒绝） |
| 限额 | 单笔上限 + 当日累计上限 | 看你开户时设的两条线 | **直接拒绝** |

两个容易被忽略的细节：

1. **黑名单查不到的时候，按"命中"处理**。也就是说 Redis 挂了，所有汇款都会被拒。这是故意的：误拒一笔正常汇款只是客户不高兴，漏放一个被制裁的对象，监管机构能让整个机构停业。
2. **当日累计额度是"先占坑再判断"**。系统每接一笔，先把这笔的金额累加到"今天已用额度"上，再判断是否超线。被拒绝的请求必须把坑还回去——**不还的话，客户失败几次之后，当天就一笔都汇不出去了**，这是真实系统里最常见的额度泄漏事故。

#### C. 挂人工审核之后的两条路

被挂起的汇款单，**钱一分都还没扣**。所以它有两条完全不同的出路：

**① 审核员放行**

系统把主链路的后半段补完：重新锁汇 → 算手续费 → 扣钱 → 发消息 → 入账。

放行时有三个必须注意的点：

- **汇率要按"放行这一刻"重新问**。挂起时填的汇率还是个占位符 0，因为那时钱还没动。
- **必须重新检查账户状态**。挂起到放行之间可能隔了几个小时，这期间账户可能因为别的事被冻结了。不能相信挂起时的检查结果。
- **中途失败不能判死刑**。如果锁汇失败（报价过期）或扣款失败（余额不够），状态**退回到"待审核"**而不是"失败"，让审核员补齐条件后再点一次。这是唯一允许状态回退的地方——因为钱还没划出去，回退是安全的。

**② 审核员驳回**

直接进终态"合规拒绝"。因为钱压根没扣过，**不需要退款动作**，但必须把"当日累计额度"的坑还回去，否则客户当天的额度会被一笔没成功的汇款白白占掉。

#### D. 锁汇环节

| 情况 | 结果 |
|---|---|
| 报价不存在 | 拒绝 |
| 报价状态不是"可用"（已被锁/已用过/已过期） | 拒绝 |
| 报价已到有效期 | 拒绝（有个定时任务每分钟清理一次过期报价） |
| 同一瞬间有另一笔汇款也在锁这个报价 | 一个成功，另一个收到"已被占用" |

#### E. 扣款环节

| 情况 | 结果 |
|---|---|
| 余额不够（不够付"汇出金额 + 手续费"） | 拒绝，并且把当日累计额度的坑还回去 |
| 扣钱成功、写流水失败 | 整体回滚，钱退回账户，就像什么都没发生过 |
| 扣钱成功、状态推进失败 | 同上，整体回滚 |

**这一环节的原则是：要么三步全成，要么三步全撤。** 绝不允许出现"钱扣了但账没记"或"钱扣了但状态没变"。

#### F. 发消息环节（最容易出事的地方）

| 情况 | 结果 |
|---|---|
| 消息发送成功 | 正常，等下游入账 |
| **消息发送失败** | **不回滚** |

最后一行需要解释一下，因为它反直觉：

> 钱已经在本地扣掉了，这时候回滚才是错的。正确的做法是**留下"已扣款"状态的单子，让定时任务去重试**。这叫"最终一致"——我不保证一次就成功，但我保证最后一定会成功。

定时任务的规则：**每 30 秒扫一次**，把所有还停在"已扣款"的单子重新发一遍消息。但**创建不满 2 分钟的不扫**（静默期）——因为刚创建的单子，消息可能还在半路上，你不分青红皂白每轮都重发，就会形成消息风暴。

重发是安全的：下游做了防重复，同一条消息收到两次，第二次会被直接忽略，不会给收款方多加一次钱。

#### G. 清算与入账环节

| 情况 | 结果 |
|---|---|
| 正常收到消息 | 推进到"清算中"，再加钱、记流水、推进到"已结算" |
| **同一条消息收到两次** | 第二次直接跳过，不会重复加钱 |
| 消息里的汇款单号查不到 | 记一条警告，跳过 |
| 汇款单状态不对（比如已经被人工驳回） | 跳过 |
| **推进到"清算中"之后入账没跑完** | 单子停在"清算中"，定时器扫描会重新推进它 |
| **手动清算和消息消费撞在一起** | 只有一方能真正推进，另一方直接跳过，不报错、不重复入账 |

防重复加钱靠两道保险：

1. **先看状态**：已经是"已结算"的直接跳过。
2. **数据库唯一索引**：同一笔汇款、同一个账户、同一个方向，只允许有一条流水。就算应用层出了 bug 想加第二次，数据库会直接报冲突，让整个事务回滚，加钱的动作一并撤销。

> 这第二道保险是资金系统里最值得花钱的地方：**把最忌讳的事故（重复入账）交给数据库在最底层挡住**。应用层可以有 bug，但钱不会平白多出来。

三个容易忽略的设计点：

1. **推进到"清算中"不碰钱**。它只是标记"钱交给渠道了"，此时收款方余额还没动，所以这一步失败不需要回滚任何账务。
2. **归批只在"已扣款"这一步做一次**。批次金额是累加的，若跟着入账一起重复执行，消息重发时批次总额会被重复计数。
3. **定时器扫描必须把"清算中"也算进去**。只扫"已扣款"的话，消息已投递但入账没跑完的单子会被永久漏掉，钱出去了却永远等不到确认。

顺带说一句：**归批失败不阻断入账**。钱必须先到账，对账的组织问题可以后面补——不能因为账本没整理好就让人家晚收钱。

#### H. 彻底失败了怎么办：只退款，不改回去

如果一笔汇款在扣款之后彻底走不通了（渠道明确退回来了、人工判定汇不出去），处理方式是**退款**，而不是把状态改回"已扣款"重来。

> 为什么不能改回去？因为钱已经离开了付款方账户。如果状态改回去，系统就会认为"这笔钱还没汇出"，但它实际上已经在路上或者已经没了——这笔钱在账上就成了**悬空的在途资金**，谁也说不清它在哪。
>
> 所以失败路径是：**失败 → 退款（把扣掉的钱原路退回去，并记一笔退款流水）**。

退款本身也是防重复的：用乐观锁抢占"已退款"状态，**并发调用只有一个人真正执行退款**，其他人直接返回，绝不会出现退两次的情况。

另外，那些**压根没扣过钱**的单子（比如人工审核驳回的），没有借方流水，退款时自然跳过，只是把状态推进到终态。

> 说明：本模块写了这个退款能力，但**没有对外暴露接口，也没有地方自动触发它**。也就是说"清算失败自动退款"这一环在这里是留白的——和第十一节提到的"没有实现退汇"是同一类缺口。

#### I. 对账环节

| 情况 | 白话 | 危险程度 |
|---|---|---|
| 金额不符 | 本地记的和对方记的不一样多，多为中间行扣了手续费，或者汇率折算精度差 | 中 |
| 渠道漏单 | 本地说汇到了，对方的回单里没有这笔 | 中 |
| 渠道多单 | 对方的回单里有这笔，本地压根没有 | **最高**，意味着可能多放了一笔钱出去 |

两个约束：

- **批次还开着的时候不能对账**。因为还在往里收货，现在对出来的结果随时会变，没有意义。必须等批次关闭或结算之后。
- **重跑对账会先清掉旧差异**。这样对账就是幂等的，不会越跑差异越多。

#### J. 账户被冻结 / 解冻

冻结账户是反洗钱调查和司法冻结的常规动作。

- 冻结之后，这个账户**既不能付款也不能收款**（发起汇款时会检查两端账户的状态）
- 重复冻结会被拦下，报"冲突"
- 每一次冻结/解冻都会写一条事件记录，**只增不改、不能删**
  > 账户表上的状态字段回答"现在能不能用"，事件表回答"它是怎么变成现在这样的"。监管检查时，后者才是证据。
- 解冻只对"当前是冻结状态"的账户生效，重复解冻同样报冲突

#### K. 重复提交 / 网络超时重试

这是日常最高发的场景：你点了"汇款"，页面转圈转了半天没反应，你又点了一次。或者网络超时，你的程序自动重试了一遍。

系统靠**防重复编号**（幂等键）挡住，一共三层：

1. **先查一遍**：这个编号已经有单子了？有就直接把原来那张单子返回给你
2. **加锁再查一遍**：防止同一瞬间两个请求都查到"没有"然后各自建一张
3. **数据库唯一索引兜底**：前两层都漏了，插入时会撞唯一键冲突。这时候**不能报错**，而要返回那笔已存在的单子

> 第三层为什么不能报错？如果返回"编号冲突"错误，客户端会以为汇款失败，于是换一个编号再发起一次——结果就是**真的汇了两次**。撞唯一键的正确反应是："哦，这笔已经有了，给你。"

#### L. 蚂蚁搬家（拆分交易）

有人为了躲开"大额必须申报"的规定，把 8 万拆成 8 笔 1 万以下的小额。

系统的检测逻辑是看**行为模式**，而不是单笔：

- 今天的累计金额达到了申报线（10000）
- 每一笔都卡在申报线**以下**
- 这样的笔数达到 3 笔

三条同时满足就告警。

> 为什么单笔超过申报线反倒不算？因为单笔超线的交易**本来就会正常申报**，它躲无可躲，不构成"刻意拆分"。要抓的是那些"每一笔都很规矩、合起来却很可疑"的行为。

#### M. 加急汇款

加急不是"插队"，而是把**等待时间的权重调高 5 倍**重新算一次账。

系统给三条通道打分：`总分 = 手续费 + 到账分钟数 × 时间权重`。

- 不着急：时间很便宜，最省钱的 LOCAL 通道胜出
- 加急：时间变贵了 5 倍，走两天才到的 SWIFT 会被狠狠扣分，快的通道优势就拉开了

这就是"加急要加钱"的量化依据。

### 0.5 一页速查：什么情况会失败，钱会不会少

| 场景 | 能不能成 | 钱动没动 | 要不要人工介入 |
|---|---|---|---|
| 两端币种相同 | 否 | 没动 | 否 |
| 账户被冻结 | 否 | 没动 | 否 |
| 报价过期 / 被占用 | 否 | 没动 | 否（重新问价） |
| 命中制裁名单 | 否 | 没动 | 否 |
| 超过身份等级额度 | 否 | 没动 | 否（先升级认证） |
| 超过单笔或当日限额 | 否 | 没动 | 否（改天/改额度） |
| 超过 5 万 | 挂起 | 没动 | **是**，等审核员 |
| 审核驳回 | 否 | 没动 | 是 |
| 审核放行但余额不够 | 退回待审核 | 没动 | **是**（充值后重新审） |
| 扣款成功、消息发失败 | 最终会成 | 已扣 | 否，定时任务自动重试 |
| 消息重复投递 | 成一次 | 只加一次 | 否 |
| 卡在"清算中"没入账 | 最终会成 | 已扣、未加 | 否，定时器扫描会再推一次 |
| 清算彻底失败 | 否 | 已扣，会退回 | 是（退款这一环本项目留白） |
| 重复提交同一编号 | 成一次 | 只扣一次 | 否 |
| 对账出现差异 | 不影响汇款 | 不影响 | 是 |

### 0.6 记住这三句话就够了

1. **换钱要锁价，送钱要挑路** —— 锁汇解决汇率风险，渠道路由解决成本与时效。
2. **钱和账必须同生同死** —— 扣款、记账、改状态是一个整体；消息必须等它彻底落定之后才能发。
3. **失败只退款，不回退** —— 钱一旦划出，回退就会造出说不清去向的在途资金；唯一允许回退的是"还没扣钱就挂起"的审核环节。

## 一、跨境支付难在哪

境内转账只有一个问题：把钱从 A 账户挪到 B 账户。跨境支付要把这件事拆成五个各自独立、又必须串起来的难题：

| 难题 | 境内支付 | 跨境支付 |
|---|---|---|
| 币种 | 同一种货币，金额可直接相加 | 两端币种不同，必须换汇；换汇就有汇率风险 |
| 时间 | 实时或准实时到账 | SWIFT 动辄 2 天，本地清算也要分钟级 |
| 合规 | 反欺诈即可 | 制裁名单、KYC 等级、反洗钱申报，缺一项就是监管处罚 |
| 通道 | 央行清算系统，唯一 | SWIFT / CIPS / 本地清算网络，成本与时效差异巨大 |
| 对账 | 单边账 | 必须与渠道回单双向核对，长款短款都要追 |

**这五个难题决定了本模块的五条主线**：锁汇（汇率）、清算批次（时间）、合规筛查（监管）、渠道路由（通道）、对账（核对）。理解了这个背景，再看代码就不会迷失在细节里。

## 二、一笔汇款要走过哪些阶段

```
                    ┌─────────────────────────────────────────┐
① 开户 → ② 询价 → ③ 合规筛查 → ④ 锁汇 → ⑤ 扣款记账 ──┐
                                                        │
                    ┌───────────────────────────────────┘
                    ▼
              ⑥ 发清算消息 ──→ ⑦ 归入批次 ──→ ⑧ 进入清算中 ──→ ⑨ 收款方入账结算 ──→ ⑩ 对账
                    │                                    │
                    │                                    └─→ 卡住则由定时任务重新推进
                    └─→ 发送失败则由定时任务补偿重发（最终一致）
```

逐阶段说明：

| 阶段 | 做什么 | 关键约束 |
|---|---|---|
| ① 开户 | 建立账户，设定币种、KYC 等级、单笔/日累计限额 | 跨境汇款要求**两端币种不同**，同币种直接拒绝 |
| ② 询价 | 生成带有效期的汇率报价（bid/ask） | 报价有过期时间，过期不能再锁 |
| ③ 合规筛查 | 制裁名单、KYC 等级、反洗钱、限额四道检查 | 任一道 REJECT 则整笔拒绝；AML 命中进入人工审核 |
| ④ 锁汇 | 把报价锁定到本笔汇款，汇率从此固定 | 并发锁同一报价只有一个能成功 |
| ⑤ 扣款记账 | 扣付款方余额、记流水、推进状态 | 三者**同一事务**，任一步失败整体回滚 |
| ⑥ 发消息 | 事务提交后才投递清算消息 | 先发消息后提交事务，会出现"回滚了但下游已收到" |
| ⑦ 归批 | 把汇款单归入清算批次 | 不归批的对账时会成为盲区；归批失败不阻断入账 |
| ⑧ 进入清算中 | 标记资金已交付渠道，等待确认 | **不碰任何钱**，只是状态推进；只做一次，重复调用直接跳过 |
| ⑨ 入账结算 | 收款方加余额、记流水、推进到已结算 | 三者**同一事务**；幂等，重复消息不能重复入账 |
| ⑩ 对账 | 与渠道回单逐笔比对 | 识别长款、短款、金额不符 |

> ⑧ 和 ⑨ 本该隔着几分钟到两天（渠道处理时间），本项目没有真实渠道往返，两步紧挨着执行。拆开的价值在于：**"清算中"是那笔悬在渠道手里的在途资金**，单独表达出来，出问题时才说得清钱卡在哪一环。

## 三、核心概念速查

### 3.1 外汇相关

| 术语 | 含义 | 本项目实现 |
|---|---|---|
| 中间价（mid rate） | 买卖价的平均，市场参考价 | 以美元为桥做**交叉计算**：`CNY/USD = USD汇率 / CNY汇率` |
| 点差（spread） | 买卖价之差，银行利润来源 | 固定 0.3%，`ask = mid × 1.0015`，`bid = mid × 0.9985` |
| 锁汇 | 把某笔交易的汇率固定下来，锁定后不受市场波动影响 | `FxQuote.lock()`，成功后 `locked_rate` 写入汇款单 |
| 敞口（exposure） | 已锁汇但尚未清算完成的净头寸 | 汇总 `QUOTE_LOCKED / FUNDS_DEBITED / SETTLING` 三种状态的单子 |
| 浮动盈亏 | 锁定汇率与当前市价的差 × 锁定量 | `lockedNotional × (avgLockedRate − currentRate)`，正为盈负为亏 |

实测一次 CNY→USD 询价（有效期 300 秒）：

```
bidRate = 0.13965035   askRate = 0.14006993
```

推导：中间价 `1.0 / 7.15 = 0.139860`，ask `= 0.139860 × 1.0015 = 0.140070`。客户换汇按 **ask** 成交，所以到手金额比按中间价算的少，少的那部分就是银行的。

#### 报价的本质：一张只能使用一次的承诺券

先纠正一个容易误解的说法：**报价可以被查询无数次，只是"锁定"只能成功一次**。`GET /fx/quote/{quoteNo}` 想查多少次都行，只有 `FxQuoteService.lock()` 是一次性的。

报价就是**一张有时效的汇率承诺券**，字段含义如下：

| 字段 | 含义 |
|---|---|
| `currencyPair` | 换什么（CNY/USD） |
| `bidRate` / `askRate` | 买入价 / 卖出价，客户换汇走贵的那个 |
| `expireTime` | 这张券几点作废 |
| `status` | 1 可用 → 2 已锁定 → 3 已使用 → 4 已过期 |
| `remittanceNo` | 被哪笔汇款锁走了（锁之前为空） |

**为什么非得一次性？** 因为报价不是"公开价目表"，而是"**只对你这一笔的承诺**"。平台给你锁定 0.1400，等于承诺"不管市场怎么变，都按这个价给你美元"。如果这张券能被 100 笔汇款重复使用，平台就用一个价格承接了 100 倍的换汇义务，而手上并没有对应量的美元——这就是敞口失控。

**为什么不在询价那一刻就锁死？** 因为询价和汇款是两次请求，中间可能隔几分钟，客户可能只是比价根本不汇。若询价时就锁定，会产生大量占着不用的报价。所以拆成两步：询价只是"问价"（不占用、不承诺、能给无数人问），锁汇才是"我要按这个价成交"。

**技术上怎么保证只成功一次？** 不用分布式锁，靠数据库条件更新：

```sql
update cross_border_fx_quote
set status = 2, remittance_no = #{remittanceNo}, locked_rate = #{lockedRate}
where quote_no = #{quoteNo}
  and status = 1
  and expire_time > now()
```

`and status = 1` 是关键。并发请求对同一行的 update 会被数据库串行化，第一个把 status 改成 2，第二个的 `where` 再也匹配不到，返回影响行数 0，代码中判定为"报价已被占用"。

注意 `lock()` 方法前面那几步 `select` + 状态/过期判断，**只是为了给出准确的错误提示**（到底是过期了还是被抢走了），真正防并发的是这条 update。前者管友好，后者管正确。

**本项目与真实系统的差距**：真实报价**带金额**——"买 10 万美元，价 0.1400，30 秒内有效"，额度用完券就作废，一笔大单可以拆着用好几张券。本项目的 `FxQuote` 没有金额字段，退化成"一张券 = 一笔汇款"的一对一关系。这个简化藏了个风险：**一张券可以被一笔任意金额的单子锁走**，只约束价格不约束数量，敞口依然可能失控。

### 3.2 合规与风控

| 术语 | 含义 | 本项目判定 |
|---|---|---|
| 制裁名单 | 联合国/各国公布的禁止交易主体 | Redis Set，命中即 REJECT。Redis 不可用时**按命中处理**（宁可误拒不可漏放） |
| KYC 等级 | 客户身份核验深度，决定可交易额度 | 0 级 1000 / 1 级 10000 / 2 级 100000 / 3+ 级 1000 万 |
| 反洗钱（AML） | 大额与可疑交易监控 | 超过 50000 挂**人工审核**，不是直接拒绝——大额交易本身合法 |
| 拆分交易（structuring） | 为规避申报把大额拆成多笔小额 | 累计达申报线、每笔都在线下、笔数 ≥ 3 即告警 |
| 申报线 | 大额交易必须报告的门槛 | 10000（中美均为该量级） |

### 3.3 清算渠道

| 渠道 | 到账 | 手续费 | 单笔上限 | 适用场景 |
|---|---|---|---|---|
| SWIFT | 2880 分钟（2 天） | 50 + 0.1% | 1 亿 | 覆盖最广，走代理行，贵且慢 |
| CIPS | 60 分钟 | 10 + 0.05% | 5000 万 | 人民币跨境清算，便宜且快 |
| LOCAL | 30 分钟 | 5 + 0.02% | **30 万** | 各国本地清算网络，最便宜但额度受限 |

路由打分：`score = 手续费 + 到账分钟数 × 时效权重`（普通 0.01，加急 0.05）。

实测汇 20000 元的评分明细：

| 渠道 | 手续费 | 时效成本 | 总分 | 是否合格 |
|---|---|---|---|---|
| SWIFT | 70.00 | 28.80 | 98.80 | 是 |
| CIPS | 20.00 | 0.60 | 20.60 | 是 |
| LOCAL | 9.00 | 0.30 | **9.30** | 是（推荐） |

加急时时效权重放大 5 倍，SWIFT 的 28.8 分变成 144 分，CIPS 与 LOCAL 的优势进一步拉开——这就是"加急要加钱"的量化依据。

### 3.4 对账差异

| 差异类型 | 含义 | 枚举值 |
|---|---|---|
| 金额不符 | 本地与渠道金额不一致，多为中间行扣费或汇率精度差 | `AMOUNT_MISMATCH(3)` |
| 渠道漏单 | 本地已结算但渠道回单没有 | `MISSING_IN_CHANNEL(4)` |
| 渠道多单 | 渠道回单有但本地没有，最危险的一种 | `MISSING_IN_LOCAL(5)` |

`LONG(1)` 与 `SHORT(2)` 两个枚举定义了但未使用——实际判定用上面三种。

## 四、数据模型

8 张表，按业务职责分四组：

### 4.1 账户组

| 表 | 用途 | 设计要点 |
|---|---|---|
| `cross_border_account` | 账户主体 | `balance` 与 `frozen_balance` 分离；`kyc_level` 决定额度；`status` 1 激活 2 冻结 |
| `cross_border_account_event` | 冻结/解冻留痕 | **只增不改**，无更新接口。状态回答"现在能不能用"，事件回答"怎么变成这样的" |

### 4.2 汇兑组

| 表 | 用途 | 设计要点 |
|---|---|---|
| `cross_border_fx_quote` | 汇率报价 | 同时存 `bid_rate` 与 `ask_rate`；`status` 1 可用 2 已锁 3 已用 4 已过期；有 `expire_time` 索引支撑定时清理 |

### 4.3 交易组

| 表 | 用途 | 设计要点 |
|---|---|---|
| `cross_border_remittance` | 汇款单 | 三个关键索引：`uk_idempotent_key` 幂等兜底、`idx_status` 补偿扫描、`idx_batch_no` 对账归集 |
| `cross_border_compliance_record` | 合规检查记录 | 每道检查一行，**只增不改**，是监管检查时"这笔交易审过了"的直接证据 |
| `cross_border_account_ledger` | 资金流水 | `uk_remittance_account_direction` 唯一索引——同一笔汇款同一账户同一方向只能有一条，这是防重复入账的最后一道防线 |

### 4.4 清算对账组

| 表 | 用途 | 设计要点 |
|---|---|---|
| `cross_border_settlement_batch` | 清算批次 | `status` 1 开启 2 已关闭 3 已结算；`cutoff_time` 是清算窗口截止 |
| `cross_border_recon_diff` | 对账差异 | `handle_status` 标记处理进度，支持单条与批量处理 |

**流水的唯一索引是最值得注意的设计**。它让"重复入账"这个资金系统最忌讳的事故，在最底层被数据库挡住——应用层即使有 bug，也只能撞出唯一键冲突让事务回滚，而不是悄悄多加一笔钱。

## 五、状态机：汇款单的一生

```
                    ┌──────────────────────────────┐
                    │                              │
   CREATED ──→ QUOTE_LOCKED ──→ FUNDS_DEBITED ──→ SETTLING ──→ SETTLED ✓
       │              │               │                            │
       │              │               │                            │
       ├──→ COMPLIANCE_REJECTED ✗     └──→ FAILED ──→ REFUNDED ✓   │
       │              │                                            │
       └──→ PENDING_REVIEW ──→ (放行) QUOTE_LOCKED                 │
                      └────→ (驳回) COMPLIANCE_REJECTED ✗           │
```

**九种状态**（`RemittanceStatus`）：

| 状态 | 编码 | 含义 | 是否终态 |
|---|---|---|---|
| `CREATED` | 1 | 已创建 | 否 |
| `COMPLIANCE_REJECTED` | 2 | 合规拒绝 | 是 |
| `QUOTE_LOCKED` | 3 | 已锁汇 | 否 |
| `FUNDS_DEBITED` | 4 | 已扣款 | 否 |
| `SETTLING` | 5 | 清算中，资金已交付渠道、未确认到账 | 否 |
| `SETTLED` | 6 | 已结算，收款方已入账 | 是 |
| `FAILED` | 7 | 失败 | 是 |
| `REFUNDED` | 8 | 已退款 | 是 |
| `PENDING_REVIEW` | 9 | 待人工审核 | 否 |

**`FUNDS_DEBITED → SETTLING → SETTLED` 这一段为什么要拆成两步推进？**

| 步骤 | 动作 | 是否碰钱 |
|---|---|---|
| `FUNDS_DEBITED → SETTLING` | 标记资金已交付渠道，等待确认 | **不碰**，纯状态推进 |
| `SETTLING → SETTLED` | 收款方加余额 + 记贷方流水 + 推进状态 | 是，三者同一事务 |

真实渠道的这两步之间隔着几分钟到两天，中间那段就是"钱已从付款方扣掉、收款方还没收到"的**在途资金**。把它单独表达成一个状态，出问题时才说得清钱卡在哪一环。

这也解释了两个实现细节：

- **推进到 `SETTLING` 时不碰钱**，所以这一步失败不需要回滚任何账务。
- **定时器扫描必须同时覆盖 `FUNDS_DEBITED` 和 `SETTLING`**。只扫前者的话，消息已投递但入账没跑完的单子会被永久漏掉——钱已出账却永远等不到确认。

`SETTLING` 在本项目里只停留毫秒级（没有真实渠道往返），**各状态的瞬时数量永远是 0**。要观察它，看 `GET /remittance/runtime` 里的 `settlingEntered`——那是累计进入过清算中的笔数。

**一条最重要的设计原则：失败一律走退款，绝不回退。**

资金一旦划出，回退就会产生"在途资金"——钱已从付款方扣掉，却没有对应的收款方入账，这笔钱在账上悬空。所以失败路径是 `FAILED → REFUNDED`，而不是把状态改回 `FUNDS_DEBITED`。

唯一的例外是审核放行中途失败：那时资金**尚未扣减**，回退到 `PENDING_REVIEW` 让审核员重新处理是安全的，不会造成误伤。

**并发防护**全部落在这一句 SQL 上：

```sql
update cross_border_remittance
set status = #{target}, version = version + 1, update_time = now()
where remittance_no = #{remittanceNo}
  and status = #{expectedStatus}
  and version = #{version}
```

`status = 期望状态` 保证不会跳过中间步骤，`version = 当前版本` 保证不会覆盖别人的写入，两者缺一不可。

## 六、合规筛查的四道检查

`ComplianceServiceImpl.screen()` 依次跑完四道检查，取最严重的结论：任一 REJECT 则整体 REJECT；无 REJECT 但有 MANUAL_REVIEW 则整体挂人工审核。

| 顺序 | 检查项 | 判定 | 失败后果 |
|---|---|---|---|
| 1 | 制裁名单 | 户主名在 Redis Set 中 | REJECT |
| 2 | KYC 等级 | 金额 ≤ 等级对应额度 | REJECT |
| 3 | 反洗钱 | 金额 ≤ 50000 | 超限 → MANUAL_REVIEW |
| 4 | 限额 | 单笔限额 + 日累计限额 | REJECT |

### 6.1 一个必须知道的坑：人工审核分支默认不可达

开户时如果不指定限额，`CrossBorderAccountServiceImpl` 会给默认值：

```java
dailyLimit  = 100000 （未指定时）
singleLimit = 50000  （未指定时）
```

而反洗钱的人工审核阈值恰好也是 **50000**。两者相等意味着：金额超过 5 万时，第 4 道限额检查先判 REJECT，第 3 道根本轮不到返回 MANUAL_REVIEW。

实测：默认账户汇 60000 → `remittance rejected by compliance check`（被限额拒绝）。

**想看到人工审核分支，开户时必须把单笔限额提到 5 万以上**：

```bash
curl -X POST 'http://127.0.0.1:8090/api/crossborder/accounts' -H 'Content-Type: application/json' \
  -d '{"ownerName":"Carol","country":"CN","currency":"CNY","balance":500000,"kycLevel":2,"singleLimit":200000,"dailyLimit":500000}'
```

再汇 60000，才会得到 `remittance suspended for manual review`。合规记录里能看到三行判定：

```
SANCTION  PASS
KYC       PASS
AML       MANUAL_REVIEW   amount exceeds manual review threshold 50000
```

这个坑的价值在于：它演示了**多道检查的执行顺序会互相掩盖**。真实系统里这类"规则打架"的问题要靠参数评审发现，测试往往覆盖不到。

### 6.2 日累计限额必须用 Lua 保证原子性

```lua
local current = tonumber(redis.call('GET', KEYS[1]) or '0')
local delta = tonumber(ARGV[1])
local limit = tonumber(ARGV[2])
local next = current + delta
redis.call('SET', KEYS[1], tostring(next))
redis.call('EXPIRE', KEYS[1], tonumber(ARGV[3]))
if next <= limit then
    return 1
end
return 0
```

**累加与判断必须在同一个脚本内完成**。若拆成"先 GET 再 SET"两次调用，两次之间就是竞态窗口——并发汇款会各自读到旧值，日限额形同虚设。

金额以**分**为单位传入，避免 Lua 里的浮点精度问题。

被拒绝的汇款会调用 `releaseDailyLimit()` 释放占用。这一步不做的话，客户失败几次之后当天就一笔都汇不出去了——这是真实系统里最常见的额度泄漏事故。

### 6.3 拆分交易检测

规则与申报制度对齐：**累计达到申报线、且每笔都在线下、笔数达到门槛**。单笔超线的交易本身会正常申报，不算拆分。

实测连续 3 笔 9000 元后：

```json
{"underLineCount":3,"payerAccountId":9,"totalAmount":27000.00,"totalCount":3}
```

第 3 笔触发告警，`GET /risk/aml/flagged` 能查到命中账户。

## 七、关键工程实现

### 7.1 幂等的三层防护

| 层次 | 做法 | 挡住什么 |
|---|---|---|
| 第一层 | 先查幂等键，命中直接返回原单 | 绝大多数正常重试 |
| 第二层 | 分布式锁内**双查**，锁内再查一次 | 并发的同一幂等键请求 |
| 第三层 | 唯一索引 `uk_idempotent_key`，冲突时返回已存在的单子 | 兜底，防止前两层都漏掉 |

第三层尤其关键：唯一索引冲突时**不能抛异常**，而要返回那笔已存在的单子。否则客户端重试会收到冲突错误，误以为汇款失败又发起一次。

```java
try {
    return doCreate(request);
} catch (DuplicateKeyException ex) {
    return onDuplicateIdempotentKey(request.getIdempotentKey());
}
```

### 7.2 事务边界：消息必须在提交后发

```java
if (TransactionSynchronizationManager.isSynchronizationActive()) {
    TransactionSynchronizationManager.registerSynchronization(
        new TransactionSynchronization() {
            @Override
            public void afterCommit() {
                task.run();
            }
        });
} else {
    task.run();
}
```

如果不等 `afterCommit` 就发消息，事务一旦回滚，下游已经收到通知去放款，钱就出去了。这个错误的代价是真实的资金损失。

**消息发送失败不回滚**：资金已在本地扣掉，回滚才是错的，留下 `FUNDS_DEBITED` 状态的单子交给定时任务重推才是对的。这是最终一致的标准处理。

### 7.3 事务代理失效的坑

`CrossBorderSettlementHandler` 的注释里记着一次真实事故：

> 这里的入账必须走独立 bean 而不是本类内部方法：同类 this 调用绕过 Spring 代理，事务静默失效，曾经因此出现并发消息重复入账六次的事故。

所以入账逻辑被抽到 `CrossBorderLedgerService` 这个独立 bean 里。`@Transactional` 只有被代理对象调用时才生效，`this.xxx()` 是绕过代理的普通方法调用。

### 7.4 消息补偿的静默期

定时任务每 30 秒扫描一次 `FUNDS_DEBITED` **和 `SETTLING`** 的单子重发消息，但**创建 2 分钟内不补偿**：

```java
private static final Duration COMPENSATION_IDLE = Duration.ofMinutes(2);
```

`SETTLING` 必须一起扫。只扫 `FUNDS_DEBITED` 的话，消息已投递、也推进到了清算中、但入账没跑完的单子会被永久漏掉——钱已经出账，却永远等不到确认。

不加静默期，刚创建的单子消息还在投递途中，每轮扫描都会把在途消息再发一遍，形成消息风暴。消费端幂等，重复发送不会重复入账，所以重发本身是安全的。

### 7.5 对账为什么要按批次

批次 `OPEN` 时拒绝对账——还在收集，对账结果会一直变。只有 `CLOSED` 或 `SETTLED` 才能对账，且对账前先清旧差异，保证对账本身是幂等的，不会越跑差异越多。

## 九、实操：跑通完整链路

以下命令可直接复制执行。**注意第 3 步的限额设置**，否则人工审核分支走不到。

```bash
B=http://127.0.0.1:8090/api/crossborder

# 1. 开立两个不同币种的账户（收款方币种必须与付款方不同）
curl -X POST $B/accounts -H 'Content-Type: application/json' \
  -d '{"ownerName":"Alice","country":"CN","currency":"CNY","balance":100000,"kycLevel":2,"singleLimit":200000,"dailyLimit":500000}'
curl -X POST $B/accounts -H 'Content-Type: application/json' \
  -d '{"ownerName":"Bob","country":"US","currency":"USD","balance":0,"kycLevel":2}'

# 2. 询价，返回带有效期的报价（记下 quoteNo）
curl -X POST "$B/fx/quote?sourceCurrency=CNY&targetCurrency=USD&validSeconds=300"

# 3. 先建一个清算批次（cutoff=0 便于后续对账），记下 batchNo
curl -X POST "$B/settlement/batch?channel=SWIFT&currency=USD&cutoffMinutes=0"

# 4. 小额汇款，指定 SWIFT 渠道以便归入上面的批次
curl -X POST $B/remittance -H 'Content-Type: application/json' \
  -d '{"idempotentKey":"demo-1","payerAccountNo":"CB...","payeeAccountNo":"CB...","sourceAmount":1000,"quoteNo":"FQ...","channel":"SWIFT"}'

# 5. 大额汇款，应挂起人工审核（code=1002 suspended for manual review）
curl -X POST $B/remittance -H 'Content-Type: application/json' \
  -d '{"idempotentKey":"demo-2","payerAccountNo":"CB...","payeeAccountNo":"CB...","sourceAmount":60000}'

# 6. 查待审核列表 → 审核放行
curl $B/remittance/pending-review
curl -X POST "$B/remittance/RM.../review/approve" -H 'Content-Type: application/json' \
  -d '{"reviewer":"compliance-dong","note":"material verified"}'

# 7. 幂等重放：同一个 idempotentKey 再发一次，应返回同一张单
#    运行时统计里 idempotentHit 会 +1

# 8. 冻结收款账户 → 查事件历史 → 重复冻结应报冲突
curl -X POST "$B/accounts/CB.../freeze?reason=aml investigation&operator=risk-team"
curl "$B/accounts/CB.../events"
curl -X POST "$B/accounts/CB.../freeze?reason=dup&operator=risk-team"   # → code=1002 冲突
curl -X POST "$B/accounts/CB.../unfreeze?reason=closed&operator=risk-team"

# 9. 关闭到期批次 → 执行对账（注入 20% 渠道差错）
curl -X POST "$B/settlement/close-overdue"
curl -X POST "$B/recon/SB...?simulatedErrorRate=0.2"

# 10. 资金自检：用流水反推余额，与实际余额比对
curl "$B/accounts/CB.../diff?initial=100000"
# → {"diff":0.00,"consistent":true} 表示账实相符

# 11. 风控观察
curl "$B/risk/route?amount=20000&urgent=false"        # 渠道路由评分
curl "$B/risk/aml/profile?payerAccountId=7"           # 当日交易画像
curl "$B/risk/aml/flagged"                            # 命中拆分嫌疑的账户
curl "$B/risk/fx-exposure"                            # 汇率敞口

# 12. 手动清算兜底：把已扣款的单子收进批次再清算（抢在消息消费之前才看得到效果）
curl -X POST "$B/settlement/batch/SB.../collect?limit=10"
curl -X POST "$B/settlement/batch/SB.../settle"

# 13. 运行时统计
curl $B/remittance/runtime
# settlingEntered 是累计进入过「清算中」的笔数，瞬时状态数永远看不到
```

### 实测结果

| 验证项 | 结果 |
|---|---|
| 小额汇款 | 成功，状态 `FUNDS_DEBITED → SETTLING → SETTLED` |
| 大额汇款（限额已调高） | `suspended for manual review`，合规记录显示 AML 判定为 MANUAL_REVIEW |
| 审核放行 | 成功，继续走锁汇扣款清算，最终 `SETTLED` |
| 幂等重放 | 返回同一张单，`idempotentHit` 计数 +1，`settlingEntered` 不增加 |
| 冻结 / 解冻 | 成功，事件表写入 FREEZE 记录 |
| 重复冻结 | `code=1002` 冲突，未重复写事件 |
| 冻结后汇款 | `code=1002`，收款方非激活状态直接拒绝 |
| 制裁名单 | 加入后汇款被拒，移除后恢复 |
| 拆分交易 | 3 笔 9000 后 `underLineCount=3`，进入 flagged 列表 |
| 资金自检 | `diff=0.00, consistent=true`，账实相符 |
| 对账 | `localCount=1, matchedCount=1, balanced=true` |
| 手动清算 | 抢在消息消费前执行时 `settle` 返回 1，走完 `SETTLING → SETTLED` |
| 手动清算与消息消费并发 | 只有一方真正推进，另一方跳过，不报错、批次金额未重复累加 |
| 卡单检查 | `FUNDS_DEBITED=0, SETTLING=0`，无遗留未推进的单子 |

## 十、观察不到的角落与已知限制

学习时知道"哪里看不到东西"，比知道"哪里能看到东西"更重要。

### 10.1 汇率敞口几乎总是空的

敞口统计的是 `QUOTE_LOCKED / FUNDS_DEBITED / SETTLING` 三种状态的单子。由于实时清算链路在毫秒级完成，汇款单在这三个状态停留的时间极短，所以 `GET /risk/fx-exposure` 通常返回空数组。

实测（连跑 4 笔汇款后）：

```json
{"pairCount":0,"totalNotional":0,"totalFloatingPnl":0,"alertPairs":0,"rows":[]}
```

注意 `SETTLING` 是**真的会被写入的**（`CrossBorderLedgerService.markSettling()`），只是停留时间短到抓不住。想确认它确实经过，看 `GET /remittance/runtime` 的 `settlingEntered`：

```json
{"FUNDS_DEBITED":0,"SETTLING":0,"SETTLED":18,"messageSent":2,"settlingEntered":2}
```

`SETTLING` 瞬时为 0 而 `settlingEntered` 为 2，正好说明它是个"经过但留不住"的状态。

想观察敞口本身，需要人为制造延迟，比如暂时停掉消息消费，或把 MQ 切到投递较慢的通道。这不是 bug，而是**实时链路效率太高导致观察窗口消失**。

### 10.2 AML 贴线金额明细会去重

Redis 里用 Set 存贴线金额：

```lua
redis.call('SADD', KEYS[1] .. ':under', ARGV[1])
```

三笔金额相同的 9000 元，Set 里只会有一条记录。`underLineCount`（笔数）是准的，但 `underLineAmounts`（金额明细）看不出重复。若需要完整明细，应改用 List 或加上时间戳后缀。

### 10.3 汇率是静态表

`USD_RATES` 是写死的常量表，不接实时行情。重点在演示**锁汇机制本身**，而不是汇率数据的真实性。真实系统由交易系统实时推送牌价。

### 10.4 与真实系统的差距

| 方面 | 本项目 | 真实系统 |
|---|---|---|
| 汇率 | 静态表 + 固定点差 | 实时行情，点差随币种与金额浮动 |
| 渠道 | 三个常量，模拟评分 | 对接真实清算网络，含流动性管理 |
| 合规 | 四类规则，Redis 名单 | 对接外部名单服务，规则引擎上千条 |
| 对账 | 模拟生成渠道回单 | 真实下载渠道对账文件，格式各异 |
| 清算 | 两步紧挨执行，无渠道往返 | 渠道异步回执，`SETTLING` 停留分钟到天级，含退汇与查询查复 |
| 报价 | 无金额字段，一张券一笔汇款 | 报价绑定金额与有效期，额度内可拆用，超时自动失效 |
| 账务 | 单币种分户，简单借贷 | 多币种分账、内部户、头寸管理 |
| 报文 | 无 | SWIFT MT103 / ISO 20022 报文 |

## 十一、延伸学习建议

想从"会用"到"真懂"，建议按这个顺序深入：

1. **先跑通再读码**——按第九节把链路跑一遍，观察 `runtime` 接口里每个计数器的变化，再回头看代码，会知道每段逻辑对应哪一次计数。
2. **重点读三个类**——`RemittanceServiceImpl`（主链路与并发）、`ComplianceServiceImpl`（风控与 Lua）、`CrossBorderLedgerServiceImpl`（事务与账务）。这三个类是全模块的核心。
3. **做破坏性实验**——停掉 Redis 看制裁检查如何 fail-safe；停掉 MQ 看补偿任务如何把单子推下去；把 `singleLimit` 调到阈值以下看人工审核分支如何消失。
4. **对照真实业务**——找一份 SWIFT MT103 报文样本，对比本项目汇款单的字段，看少了什么（报文头、中间行、费用承担方式 SHA/BEN/OUR 等）。
5. **补上缺失的一环**——本项目没有实现"退汇"（收款失败后原路退回）。可以试着基于现有状态机加一条 `SETTLING → RETURNING → RETURNED` 的分支，这是检验是否真懂状态机的最好练习。
