# 事务隔离：四个级别到底解决什么问题

> 目标：说清脏读、不可重复读、幻读分别是什么，以及四个隔离级别怎么对应。

---

## 一句话

**隔离级别是在「数据正确性」和「并发性能」之间做取舍**——
级别越高越安全，但并发越差。

---

## 先记住 ACID 里的 I

事务有四大特性 ACID，隔离性（Isolation）指的是：
**多个事务同时跑，彼此之间应该隔多开？**

SQL 标准定义了四个级别，从松到严：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|---|---|---|---|
| 读未提交（Read Uncommitted） | ❌ 有 | ❌ 有 | ❌ 有 |
| 读已提交（Read Committed） | ✅ 无 | ❌ 有 | ❌ 有 |
| **可重复读（Repeatable Read）** | ✅ 无 | ✅ 无 | ✅ 无（InnoDB 下） |
| 串行化（Serializable） | ✅ 无 | ✅ 无 | ✅ 无 |

> **InnoDB 默认是「可重复读」**，Oracle 和 PostgreSQL 默认是「读已提交」。这是面试常问的差异。

---

## 三种问题分别是什么

先建个场景：有一张账户表，初始 `balance = 1000`。

### 脏读：读到了别人还没提交的数据

```
事务 A：把 balance 改成 500            （还没提交）
事务 B：读 balance → 读到 500          ← 脏读
事务 A：出错了，回滚，balance 变回 1000
```

事务 B 读到的 500 根本就没真正存在过。如果 B 拿这个 500 去做决策，就错了。

**危害最大**，所以「读已提交」及以上都解决了它。

### 不可重复读：同一事务内两次读，结果不一样

```
事务 B：读 balance → 1000
事务 A：把 balance 改成 500，并提交
事务 B：再读 balance → 500             ← 不可重复读
```

同一个事务里，同样的查询，两次结果不同。

**注意区别**：脏读是读到了「未提交」的，不可重复读是读到了「已提交的修改」。

### 幻读：同一事务内两次查，行数不一样

```
事务 B：select * from account where id > 10  →  查出 5 条
事务 A：insert 一条 id=20 的记录，并提交
事务 B：再查同样的条件                    →  查出 6 条    ← 幻读
```

**和不可重复读的区别**：
- 不可重复读针对**某一行的数据变了**（update/delete）
- 幻读针对**行数变了**（insert 新插入了行）

---

## InnoDB 怎么做到的

这里要引出一个关键概念：**MVCC（多版本并发控制）**。
详细机制见 [mvcc.md](mvcc.md)，这里先说结论：

- **读已提交**：每次读都生成一个新的快照 → 能看到别人已提交的最新修改 → 所以有不可重复读
- **可重复读**：**只在事务第一次读时生成快照**，之后整个事务都用这个快照 → 所以可重复读

这就是「可重复读」名字的由来：同一个事务里，反复读都是同一个快照。

**那幻读呢？** InnoDB 在可重复读下靠两招解决：

1. **快照读**（普通 select）：靠 MVCC，因为快照是固定的，新插入的行不在快照里，自然看不到
2. **当前读**（`select ... for update`、`update`、`delete`）：靠**间隙锁**阻止别的事务插入

所以 InnoDB 的可重复读**基本能避免幻读**，
这也是为什么标准里可重复读允许幻读，但 InnoDB 说它解决了。

---

## 串行化为什么没人用

串行化就是**所有事务排队一个一个跑**，读写都加锁。

数据绝对安全，但并发性能直接归零。生产环境基本不用——
真需要强一致，用「可重复读 + 显式加锁（`for update`）」就够了。

---

## 怎么选

| 场景 | 建议 |
|---|---|
| 绝大多数业务 | **用默认的可重复读** |
| 对一致性要求极高、且能接受性能损失 | 串行化，或读已提交 + 显式锁 |
| 从 Oracle 迁移过来的系统 | 可能要改成读已提交（Oracle 默认） |

**查看和设置当前级别**：

```sql
select @@transaction_isolation;                          -- 查看（MySQL 8.0）
set session transaction isolation level read committed;  -- 改当前会话
```

## 一个真实场景：为什么「可重复读」很重要

对账场景：你要导出一份账单，中途有人往里插了一笔新交易。

```
事务开始：select sum(amount) from trade where date = '2026-09-09'  → 10000
          （此时别人插入了一笔 500 并提交）
          select count(*) from trade where date = '2026-09-09'     → ???
```

如果是读已提交，count 会多一条，但 sum 还是 10000 —— **对账对不平**。

可重复读下，两次查询都基于同一个快照，金额和笔数始终自洽。

**这就是资金系统偏爱高隔离级别的原因**：宁可牺牲一点并发，也要保证数据自洽。

## 记忆口诀

| 问题 | 一句话 |
|---|---|
| 脏读 | 读到了别人**没提交**的（最脏，危害最大） |
| 不可重复读 | 同一行**数据被改**了（update） |
| 幻读 | **行数变了**（insert） |

| 级别 | 一句话 |
|---|---|
| 读已提交 | 每次读都刷新快照 → 解决脏读 |
| 可重复读（InnoDB 默认） | 事务内共用一个快照 → 再加间隙锁解决幻读 |
