# 索引：为什么是 B+ 树

> 目标：说清索引是什么、为什么选 B+ 树、以及回表和覆盖索引这两个高频词。

---

## 一句话

**索引就是一本排好序的目录**，让你不用翻完整本书就能找到内容。

没索引时查 `where name = '张三'`，得把整张表从头扫到尾（全表扫描）；
有索引后，直接翻目录定位到那几页。

---

## 为什么是 B+ 树，不是别的

先明确一个前提：索引存在磁盘上，**每次读一个节点就是一次磁盘 IO**，这是主要成本。
所以选数据结构的标准就一个：**让树尽量矮，减少 IO 次数**。

| 结构 | 为什么不行 |
|---|---|
| 二叉搜索树 | 100 万数据树高约 20，最坏要 20 次 IO；还可能退化成链表 |
| 哈希 | 等值查询快，但**不支持范围查询**，`where id > 100` 没法查 |
| B 树 | 每个节点都存数据，一页能放的 key 变少，树就更高；范围查询要中序遍历整棵树 |
| **B+ 树** | 非叶子只存 key 不存数据 → 一页能放上千个 key → **树高只有 3~4 层**；叶子节点用链表相连 → 范围查询顺着链表扫就行 |

**树高 3~4 层是什么概念**：InnoDB 一页 16KB，主键是 bigint（8 字节）+ 指针（6 字节）约 14 字节，
一个非叶子节点能放约 1170 个 key。

```
3 层 B+ 树能存：1170 × 1170 × 16（假设一行 1KB，一页 16 行）≈ 2000 万行
```

两千万数据的表，查一条记录最多 3 次磁盘 IO，而且前两层基本都在内存里缓存着。

**B+ 树相对 B 树的两个关键改进**：
1. 非叶子节点不存数据 → 更矮
2. 叶子节点横向链表相连 → 范围查询极快（`between`、`>`、`<`）

---

## 聚簇索引和二级索引

这是 InnoDB 的核心设计，很多人混淆。

### 聚簇索引（主键索引）

**叶子节点存的是整行数据**。表数据本身就是按主键顺序组织的一棵 B+ 树。

所以 InnoDB 的表**必须**有主键——你不建，它也会偷偷建一个隐藏的 6 字节 row_id。

### 二级索引（普通索引、联合索引）

**叶子节点存的不是整行，而是主键值**。

```
idx_name (name) 的叶子： name='张三' → id=7
                        name='李四' → id=23
```

### 回表

用二级索引查到主键后，还得**再拿主键去聚簇索引查一次**才能拿到完整行数据——
这第二次查询就叫**回表**。

```sql
select * from user where name = '张三';
-- 1. 在 idx_name 上找到 '张三' 对应的 id=7
-- 2. 拿 id=7 回聚簇索引查整行      ← 回表
```

回表的代价：**每回表一次就是一次随机 IO**。
如果命中 1 万条记录，就要 1 万次随机 IO，这时候可能还不如全表扫描快——
这也是为什么有时候 MySQL 明明有索引却不用（优化器算下来全表更便宜）。

### 覆盖索引

如果查询的列**全都在索引里**，就不用回表了，这叫**覆盖索引**。

```sql
-- 假设有联合索引 idx_name_age (name, age)

select id, name, age from user where name = '张三';   -- 覆盖索引，不回表
select * from user where name = '张三';               -- 要回表（还要查其它列）
```

用 `explain` 看，Extra 里出现 **`Using index`** 就是命中了覆盖索引。

**这是最实用的一条优化**：把查询频繁的列冗余进联合索引，避免回表。

---

## 最左前缀原则

有联合索引 `idx_abc (a, b, c)`，索引里的排序是**先按 a 排，a 相同再按 b，b 相同再按 c**。

就像查字典按「拼音 → 声调 → 笔画」排，你不能跳过拼音直接按声调找。

| 查询条件 | 能用上索引吗 |
|---|---|
| `where a = 1` | ✅ 用 a |
| `where a = 1 and b = 2` | ✅ 用 a、b |
| `where a = 1 and b = 2 and c = 3` | ✅ 全用上 |
| `where b = 2` | ❌ 跳过了 a，用不上 |
| `where a = 1 and c = 3` | ⚠️ 只能用 a，c 用不上（b 断了） |
| `where a > 1 and b = 2` | ⚠️ a 用了，但 **a 是范围查询，b 就用不上了** |

最后一条是常见坑：**范围查询之后的列，索引就断了**。

---

## 索引下推（ICP）

MySQL 5.6 之后的优化。有 `idx_name_age (name, age)`：

```sql
select * from user where name like '张%' and age = 20;
```

按最左前缀，`like '张%'` 是范围查询，age 本该用不上索引。

- **没有 ICP**：先按 name 把所有姓张的都回表查出来（可能几万条），再过滤 age
- **有 ICP**：在索引层就先判断 age，只对同时满足的行回表 → **回表次数大幅减少**

explain 里 Extra 显示 **`Using index condition`** 就是命中了 ICP。

---

## 什么时候该建索引

**该建**：

1. `where` 条件里的高频查询列
2. 用来 `join` 的关联列
3. 需要排序或分组的列（`order by`、`group by`）——B+ 树本身有序，能省掉排序

**别乱建**：

1. **区分度低的列别建**——比如「性别」只有男女两个值，索引过滤不掉多少数据，不如全表扫
2. 索引不是越多越好——每个索引都是一棵 B+ 树，**占空间，且拖慢写入**（每次 insert/update 都要维护索引）
3. 频繁更新的列慎重——维护索引有成本

**联合索引的列顺序**：
- 区分度高的放前面（能更快过滤掉数据）
- 同时兼顾「最左前缀」——保证最常用的查询能命中

## 记忆口诀

| 概念 | 一句话 |
|---|---|
| B+ 树 | 矮胖 + 叶子连成链表，所以点查和范围查都快 |
| 聚簇索引 | 叶子存整行，表数据就是它 |
| 二级索引 | 叶子存主键 |
| 回表 | 拿主键再查一次聚簇索引 |
| 覆盖索引 | 要查的列都在索引里，不用回表（Extra: Using index） |
| 最左前缀 | 不能跳过左边的列，范围查询会让它右边的列失效 |
