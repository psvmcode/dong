# GC：垃圾回收怎么判断谁该死

> 目标：说清对象存活判断、三种回收算法、以及分代收集和常见收集器。

---

## 一句话

**GC 解决两件事：判断哪些对象已经死了，以及怎么把它们占的内存收回来。**

不像 C/C++ 要手动 `free`，Java 自动回收，代价是**会有 STW（Stop The World，暂停所有应用线程）**。

---

## 怎么判断对象「已死」

### 1. 引用计数法（Java 没用）

每个对象记一个引用数，有人引用就 +1，引用失效就 -1，为 0 就是垃圾。

**问题**：解决不了**循环引用**。

```java
a.ref = b;
b.ref = a;
a = null;
b = null;
// 两个对象互相引用，计数都是 1，但外部已经没人能访问它们了
// → 永远回收不掉 → 内存泄漏
```

所以 Java 不用它（Python、PHP 用的是这个 + 额外机制）。

### 2. 可达性分析（Java 用的）

**从一组叫「GC Roots」的起点出发，顺着引用链往下走，走不到的对象就是垃圾。**

```
GC Roots
  ├── 局部变量（栈帧里的）
  ├── 静态变量（方法区里的）
  ├── 常量
  ├── JNI 引用的对象
  └── ...
```

能作为 GC Roots 的：

| 类型 | 例子 |
|---|---|
| **虚拟机栈中引用的对象** | 方法里的局部变量、参数 |
| **方法区中静态属性引用的对象** | `static` 变量 |
| **方法区中常量引用的对象** | `static final String` |
| **本地方法栈中 JNI 引用的对象** | native 方法 |
| 被同步锁持有的对象 | `synchronized(obj)` |
| 虚拟机内部的引用 | 基本类型对应的 Class 对象、常驻异常对象 |

**关键理解**：不是「有没有人引用它」，而是「**能不能从 GC Roots 走到它**」。
那两个循环引用的对象，虽然互相指着，但从 GC Roots 走不到，所以是垃圾。

### 3. 引用的四种强度

就算可达，也不一定马上回收——看引用类型：

| 类型 | 回收时机 | 典型用途 |
|---|---|---|
| **强引用** | 只要存在就不回收 | `Object o = new Object()`（平时用的都是这个） |
| **软引用** | **内存不够时**才回收 | 缓存 |
| **弱引用** | **下一次 GC** 就回收 | `WeakHashMap`、ThreadLocal 的 key |
| **虚引用** | 随时可回收，仅用于收到回收通知 | 管理堆外内存 |

软引用做缓存很合适：内存够就留着，不够了自动清理，不会 OOM。

### 4. 真正的死亡要两次标记

对象被判定不可达后，**不会立即回收**，还有一次机会：

```
第一次标记：不可达
   ↓
判断是否需要执行 finalize()
   ├─ 没重写 finalize() 或已执行过 → 直接回收
   └─ 需要执行 → 放入 F-Queue，由 Finalizer 线程执行
        ↓
第二次标记：执行完 finalize() 后，如果重新建立了引用 → 逃脱
            否则 → 回收
```

**`finalize()` 不推荐使用**：执行时机不确定、可能死锁、严重影响性能。
JDK 9 起已标记废弃。要释放资源用 `try-with-resources` 或 `Cleaner`。

## 三种回收算法

### 1. 标记-清除（Mark-Sweep）

先标记要回收的，再统一清除。

- **优点**：简单
- **缺点**：产生**大量内存碎片**——总空闲空间够，但都是零散的小块，分配大对象时失败

### 2. 复制（Copying）

把内存分成两块，只用一块。回收时把存活对象**复制到另一块**，然后清空原来的。

- **优点**：没碎片，效率高
- **缺点**：**内存利用率只有一半**

**适合对象存活率低的场景**（比如新生代，98% 的对象朝生夕死）。

实际应用中不会真的 1:1 分，HotSpot 用的是 **8:1:1**（Eden : Survivor : Survivor），
只有 10% 的空间被「浪费」。

### 3. 标记-整理（Mark-Compact）

标记后，把存活对象**往一端移动**，然后清理边界外的。

- **优点**：没碎片
- **缺点**：移动对象成本高（要更新所有引用）

**适合对象存活率高的场景**（比如老年代）。

## 分代收集

**核心思想：不同生命周期的对象用不同策略。**

```
堆
├── 新生代 (Young)  ── 对象朝生夕死，存活率低 → 用复制算法
│   ├── Eden (8)
│   └── Survivor0 (1) + Survivor1 (1)
└── 老年代 (Old)    ── 对象活得久，存活率高 → 用标记-清除/整理
```

（JDK 8 还有永久代，JDK 8 之后改成元空间 Metaspace，用本地内存）

### 对象的一生

```
1. 新对象分配在 Eden

2. Eden 满了 → 触发 Minor GC
   → 存活的对象复制到 Survivor，年龄 +1
   → 清空 Eden

3. 对象在 Survivor 里熬过一次 Minor GC，年龄 +1
   → 年龄达到阈值（默认 15）→ 晋升到老年代

4. 老年代空间不够 → 触发 Major GC / Full GC
```

### 两个例外

| 情况 | 说明 |
|---|---|
| **大对象直接进入老年代** | 超过阈值（`-XX:PretenureSizeThreshold`）的大数组、长字符串，避免在新生代反复复制 |
| **动态年龄判断** | 如果 Survivor 中相同年龄的对象总大小超过 Survivor 的一半，年龄 ≥ 该年龄的对象**直接晋升** |

### Minor GC / Major GC / Full GC

| 类型 | 范围 | 特点 |
|---|---|---|
| **Minor GC** | 只回收新生代 | 频繁，速度快 |
| **Major GC** | 只回收老年代 | 慢，通常伴随 Minor GC |
| **Full GC** | **整个堆 + 方法区** | **最慢**，STW 时间最长，要尽量避免 |

**优化的目标就是减少 Full GC**。

## 常见垃圾收集器

| 收集器 | 区域 | 算法 | 特点 |
|---|---|---|---|
| **Serial** | 新生代 | 复制 | 单线程，简单，适合客户端 |
| **ParNew** | 新生代 | 复制 | Serial 的多线程版 |
| **Parallel Scavenge** | 新生代 | 复制 | **吞吐量优先**（JDK 8 默认） |
| **Serial Old** | 老年代 | 标记-整理 | Serial 的老年代版 |
| **Parallel Old** | 老年代 | 标记-整理 | 吞吐量优先（JDK 8 默认搭配） |
| **CMS** | 老年代 | 标记-清除 | **低延迟优先**，几乎并发，但有碎片 |
| **G1** | 整堆 | 标记-整理 + 复制 | **JDK 9 起默认**，兼顾吞吐和延迟 |
| **ZGC** | 整堆 | 着色指针 + 读屏障 | **JDK 15 生产可用**，STW 控制在 10ms 内 |

### CMS 的四步（面试常问）

```
1. 初始标记    → STW，只标记 GC Roots 直接关联的对象（很快）
2. 并发标记    → 和业务线程一起跑，标记全部可达对象（最耗时）
3. 重新标记    → STW，修正并发期间变动的部分（较短）
4. 并发清除    → 和业务线程一起跑，清除垃圾
```

把最耗时的标记和清除都做成并发，所以 STW 时间短。
代价：有碎片、占用 CPU。

### G1 的思路

把堆**分成很多个小区域（Region）**，每个 Region 可以是 Eden/Survivor/Old。

不再追求一次把整个代清干净，而是**挑垃圾最多的 Region 优先回收**
（Garbage First，名字由来），在**可控的停顿时间内**回收尽可能多的垃圾。

可以设置期望停顿时间：`-XX:MaxGCPauseMillis=200`。

## 怎么排查 GC 问题

```bash
# 打印 GC 日志（JDK 9+ 用 -Xlog，JDK 8 用 -XX:+PrintGCDetails）
java -Xlog:gc* -jar app.jar

# 实时看堆内存和 GC 情况
jstat -gcutil <pid> 1000

# 看当前堆里哪些对象最多
jmap -histo <pid> | head -20

# 导出堆快照，用 MAT 分析
jmap -dump:format=b,file=heap.hprof <pid>
```

**判断标准**：

- Full GC 频率高（几分钟一次）→ 有问题
- 每次 Full GC 后老年代空间没释放多少 → **很可能内存泄漏**
- Minor GC 特别频繁 → 新生代太小

## 记忆口诀

| 问题 | 答案 |
|---|---|
| 怎么判断死亡 | **可达性分析**（从 GC Roots 走不到），不是引用计数 |
| GC Roots 有哪些 | 栈中局部变量、静态变量、常量、JNI 引用 |
| 引用四种强度 | 强 > 软（内存不足才收）> 弱（下次 GC 就收）> 虚 |
| 三种算法 | 标记清除（有碎片）、复制（费空间）、标记整理（要移动） |
| 新生代用什么 | **复制**（存活率低） |
| 老年代用什么 | 标记清除 / 标记整理（存活率高） |
| Minor vs Full | Minor 只收新生代；Full 收全堆，**要尽量避免** |
| CMS 四步 | 初始标记(STW) → 并发标记 → 重新标记(STW) → 并发清除 |
| G1 是什么 | 分 Region，**挑垃圾最多的优先收**，可设停顿目标 |
