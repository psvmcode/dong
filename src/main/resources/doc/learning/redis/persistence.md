# Redis 持久化：RDB 和 AOF 怎么选

> 目标：说清两种方式的原理差异、各自丢多少数据，以及生产怎么配。

---

## 一句话

**RDB 是「拍快照」，AOF 是「记流水账」。生产环境通常两个一起开。**

Redis 是内存数据库，断电就没了。持久化就是把内存里的数据写到磁盘上。
`classic` 模块也验证了这点——数据只在 Redis 里是不可靠的，必须落库或持久化。

---

## RDB（Redis Database）

### 原理

**在某个时刻，把内存里所有数据生成一个快照文件（dump.rdb），存到磁盘。**

触发方式：

| 方式 | 命令/配置 |
|---|---|
| 手动触发（阻塞） | `SAVE` |
| 手动触发（后台） | `BGSAVE` |
| 自动触发 | 配置 `save 900 1`（900 秒内至少 1 次修改） |
|  shutdown 时 | 正常关闭会自动做一次 |

### 关键：写时复制（Copy-On-Write）

`BGSAVE` 是怎么做到不阻塞主线程的？

```
1. 主进程 fork 出一个子进程
2. 子进程把内存数据写到临时 rdb 文件
3. 写完后替换旧文件
```

**fork 的瞬间**子进程和父进程共享同一份内存（操作系统层面是共享页表）。
只有当主进程**修改了某块数据**时，操作系统才会把那块内存**复制一份**出来。

**这意味着**：
- 主进程几乎不阻塞（只有 fork 那一下会短暂卡住，数据量越大越久）
- RDB 期间修改的数据**不会**出现在这一次的快照里
- 内存占用可能翻倍（如果修改很频繁，复制的页很多）

### 优缺点

| 优点 | 缺点 |
|---|---|
| 文件**紧凑**，适合备份和灾备 | **会丢数据**——两次快照之间宕机，中间的全丢 |
| **恢复速度快**（直接读入内存） | fork 时数据量大会有停顿 |
| 最大化 Redis 性能（主进程几乎不参与） | 没法做到秒级持久化 |

## AOF（Append Only File）

### 原理

**把每一条「写命令」追加到日志文件的末尾。**

```
set name 张三     → 追加到 appendonly.aof
set name 李四     → 再追加
```

重启时，Redis 把 AOF 文件里的命令**重新执行一遍**，就能恢复数据。

### 三种写回策略（重点）

| 策略 | 行为 | 丢数据 | 性能 |
|---|---|---|---|
| `always` | 每条命令都**立刻**刷盘 | **基本不丢** | 最差 |
| `everysec` | 每秒刷一次（**默认**） | 丢 1 秒 | 好 |
| `no` | 交给操作系统决定 | 丢最多 | 最好 |

**默认 `everysec`**：最多丢 1 秒的数据，这个取舍大部分业务能接受。

### AOF 重写（Rewrite）

**问题**：AOF 会越来越大。

```
set name 张三
set name 李四
set name 王五
```

三条命令，但最终只需要 `set name 王五` 这一条。前面两条是浪费。

**AOF 重写**就是**根据当前内存里的数据，重新生成一份最短的 AOF**，
不管历史命令有多啰嗦。

```
1. 主进程 fork 子进程
2. 子进程根据当前内存数据，生成新的 AOF
3. 期间的新命令同时写入「重写缓冲区」
4. 子进程写完后，把缓冲区的增量命令追加到新 AOF
5. 替换旧文件
```

触发：`auto-aof-rewrite-percentage 100`（比上次重写后大了一倍）
且 `auto-aof-rewrite-min-size 64mb`。

### 优缺点

| 优点 | 缺点 |
|---|---|
| **丢数据少**（最多 1 秒） | 文件**比 RDB 大** |
| 写入的是命令，可读、可手动修改 | **恢复速度慢**（要逐条执行命令） |
| 出错时可用 `redis-check-aof` 修复 | 长期运行需要重写 |

---

## 对比

| 对比项 | RDB | AOF |
|---|---|---|
| 存什么 | 数据**快照** | 写**命令** |
| 文件大小 | **小** | 大 |
| 恢复速度 | **快** | 慢 |
| 丢数据 | 多（两次快照之间） | 少（最多 1 秒） |
| 对性能影响 | fork 时短暂卡顿 | 持续写入，影响小 |
| 适用场景 | 备份、灾备、可容忍丢数据 | 数据重要、尽量不丢 |

## 生产怎么选

### 只开 RDB

**适合**：缓存场景，数据丢了可以从数据库重新加载。

**风险**：宕机丢几分钟数据。

### 只开 AOF

**不推荐**。虽然丢数据少，但恢复慢，而且 RDB 的紧凑备份能力没有。

### 两个都开（推荐）

**Redis 4.0 之前**：两个都开时，重启**优先用 AOF 恢复**（数据更全）。

**Redis 4.0 之后：混合持久化**（`aof-use-rdb-preamble yes`，默认开启）

```
AOF 文件 = RDB 格式的全量数据 + 增量的 AOF 命令
```

**做法**：AOF 重写时，前半段用 **RDB 格式**（紧凑、加载快），
后半段是重写期间的**增量命令**（AOF 格式）。

**兼顾两者优点**：恢复快（RDB 部分直接加载）+ 丢数据少（AOF 部分）。

**这是目前生产环境的标准配置。**

---

## 持久化不是备份

**重要认识**：RDB/AOF 解决的是「Redis 重启后数据还在」，
它**不等于备份**。

| 场景 | 持久化能救吗 |
|---|---|
| Redis 进程重启 | ✅ 能 |
| 服务器断电 | ✅ 能（最多丢 1 秒） |
| **误执行 `flushall`** | ❌ **不能**——AOF 会把 flushall 也记下来，重启后照样是空的 |
| **硬盘损坏** | ❌ 不能 |

**真正的备份要满足**：

1. 定期把 RDB 文件**复制到别的机器**（异地）
2. 保留**多个时间点**的版本（比如每小时一个，保留 48 小时）
3. 备份文件要**定期演练恢复**，别到用时才发现是坏的

## 相关命令

```bash
# 手动触发
redis-cli BGSAVE              # 后台生成 RDB
redis-cli BGREWRITEAOF        # 后台重写 AOF

# 查看持久化状态
redis-cli info persistence
# 关注：rdb_last_bgsave_status、aof_last_bgrewrite_status、aof_last_write_status

# 关闭当前服务器并生成 RDB
redis-cli SHUTDOWN
```

**监控要点**：`aof_last_write_status:ok` 如果变成 `err`，
说明 AOF 写失败了（通常是磁盘满），**必须立刻处理**。

## 记忆口诀

| 问题 | 答案 |
|---|---|
| RDB 是什么 | 数据**快照**，紧凑、恢复快、丢数据多 |
| AOF 是什么 | 写**命令**日志，丢数据少、文件大、恢复慢 |
| AOF 默认策略 | `everysec`，**最多丢 1 秒** |
| AOF 为什么越来越大 | 记录每一条命令，需要**重写**瘦身 |
| 生产怎么配 | **两个都开**，4.0+ 开混合持久化 |
| 混合持久化是什么 | AOF = RDB 全量 + AOF 增量，兼顾快和安全 |
| 持久化能当备份吗 | **不能**，误删和硬盘坏它救不了，要异地多版本 |
