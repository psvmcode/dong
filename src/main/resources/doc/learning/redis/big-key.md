# 大 key：为什么它会拖垮整个 Redis

> 目标：说清什么算大 key、为什么会出问题、怎么发现、怎么解决。

---

## 一句话

**大 key 的危害不在"占内存"，而在"操作它会阻塞 Redis 的单线程"——一个 key 卡住，全库请求都得等。**

理解这点很关键：Redis 的命令执行是**单线程**的。任何一条命令执行 100ms，
这 100ms 内**所有其他客户端的请求都在排队**。

---

## 一、什么算大 key

没有绝对标准，取决于机器配置。业界的经验值：

| 类型 | 大小 | 元素数 |
|---|---|---|
| String | **> 10KB** 关注，> 1MB 严重 | — |
| List / Hash / Set / ZSet | 总大小 > 1MB | **> 5000 个** |

**两个维度都要看**：

- **value 很大**（如一个 5MB 的 JSON 字符串）
- **元素很多**（如一个 Hash 有 100 万个 field，哪怕每个都很小）

第二种更隐蔽——单个 field 很小，但整体很大，扫描时容易漏掉。

云厂商（阿里云、腾讯云）的判定通常更严格，String > 10KB 或集合 > 5000 元素就会告警。

---

## 二、会造成什么问题

### 1. 阻塞主线程（最核心的危害）

由于单线程模型，下列操作都会**卡住整个实例**：

| 操作 | 为什么慢 |
|---|---|
| `DEL` 大 key | 释放内存要遍历整个数据结构，元素越多越慢 |
| `HGETALL` / `SMEMBERS` / `LRANGE 0 -1` | 一次构造并返回巨量数据 |
| 大 key **过期删除** | 主动过期和被动过期都要释放内存，同样阻塞 |
| `KEYS *`（虽然不是大 key 问题，但同理） | 全库扫描 |

**注意第二类**：不是"写"才危险，**"读"一样危险**。
`HGETALL` 一个有 100 万 field 的 Hash，会阻塞好几秒。

### 2. 集群数据倾斜

Redis Cluster 按 key 哈希分片。一个大 key 落在哪个分片，
**那个分片的内存就爆了**，其他分片还很空——

**整个集群的可用容量由最满的那个分片决定**，加机器也解决不了。

### 3. 网络拥塞

一次返回几 MB，带宽瞬间打满。
客户端解析这么大的响应也慢，还可能撑爆客户端内存。

### 4. 持久化受影响

| 场景 | 影响 |
|---|---|
| **RDB** | fork 时如果主线程正在写大 key，**写时复制**会多拷贝一份，阻塞时间显著加长 |
| **AOF 重写** | 重写时要展开大 key 的所有元素，文件体积和耗时都上升 |
| **主从复制** | 大 key 的同步会占用大量带宽，导致复制延迟 |

### 5. 内存淘汰失效

内存到达上限触发淘汰时，大 key 可能因为"太大"而不被选中，
或者释放大 key 时造成长时间阻塞。

## 三、怎么发现

### 命令一：`--bigkeys`（最常用）

```bash
redis-cli --bigkeys
```

会扫描全库，按类型列出**每类最大的 key**：

```
-------- summary -------
Sampled 1000000 keys in the keyspace!
Total key length in bytes is 25000000 (avg len 25.00)

Biggest string found 'user:1:profile' has 5242880 bytes
Biggest   hash found 'order:all:20260916' has 800000 fields
1 strings with 5242880 bytes (0.00% of keys, avg size 5242880.00)
```

**原理**：用 `SCAN` 遍历（不是 `KEYS`，所以不会阻塞），对每个 key 用
`STRLEN` / `HLEN` / `LLEN` / `SCARD` / `ZCARD` 取长度，**记录最大值**。

**局限**：
- 只找出**每类最大的那一个**，第二大的不显示
- **需要扫全库**，生产环境建议在从节点执行

### 命令二：`MEMORY USAGE`（精确）

```bash
redis-cli MEMORY USAGE user:1:profile SAMPLES 0
```

返回该 key 占用的**精确字节数**。`SAMPLES 0` 表示全量采样（精确但慢）。

**适合**：已知可疑 key，想确认它到底多大。

### 命令三：`--hotkeys`（顺带找热 key）

```bash
redis-cli --hotkeys
```

**前提**：`maxmemory-policy` 必须是 LFU 系列，否则报错。

### 命令四：离线分析 RDB

用 `rdb-tools` 解析 RDB 文件，能拿到**所有 key 的大小排名**：

```bash
rdb -c memory dump.rdb --bytes 10240 -f memory.csv
```

**优点**：不占用线上实例资源（拿从节点的 RDB 文件分析）。

**缺点**：需要文件传输，不够实时。

### 命令五：云厂商监控

阿里云 DAS、腾讯云都有「大 key 分析」功能，图形化直接看 Top N。

## 四、怎么解决

### 1. 拆分（最根本）

**思路：把一个大 key 拆成多个小 key，用哈希分散。**

| 原结构 | 拆分方式 |
|---|---|
| 大 Hash | `user:1:info` → `user:1:info:0` ~ `user:1:info:9`，按 field 哈希取模 |
| 大 List | 按段拆：`queue:0`、`queue:1`，每段固定长度 |
| 大 Set / ZSet | 按 member 哈希分桶：`rank:0` ~ `rank:9` |
| 大 String | 切成多个 chunk：`blob:0`、`blob:1`，客户端拼装 |

**拆分要解决的问题**：
- 读取时要**先算哈希定位**到哪个分片 key
- 需要**聚合操作**时（如求总数）要遍历所有子 key，代价变高

**经验**：拆成 **1000 个以内**的子 key 比较合适，太多也会带来管理成本。

### 2. 删除用异步（最实用的救火手段）

**不要用 `DEL` 删大 key**——会阻塞。用 `UNLINK`：

```bash
# ❌ 同步删除，阻塞主线程
DEL big:hash

# ✅ 异步删除（Redis 4.0+）：先把 key 从 keyspace 摘掉，内存交给后台线程慢慢释放
UNLINK big:hash
```

**`UNLINK` 的巧妙之处**：它把"摘除 key"（很快）和"释放内存"（很慢）拆开了，
后者放到后台线程做，主线程立刻返回。**对外表现是瞬间完成**。

**如果版本低于 4.0**，只能分批删：

```bash
# 用 SCAN 游标分批删除集合元素，避免一次删太多
HSCAN big:hash 0 COUNT 100     # 逐批读，逐批 HDEL
```

### 3. 读取要分批

| 危险命令 | 替代方案 |
|---|---|
| `HGETALL` | `HSCAN` 游标分批 |
| `SMEMBERS` | `SSCAN` |
| `ZRANGE 0 -1`（全量） | `ZRANGE` 分页 / `ZSCAN` |
| `LRANGE 0 -1` | `LRANGE` 分段读取 |

**原则**：**不要一次性取全量**，用游标分页，每次取一小批。

### 4. 设计阶段规避

| 措施 | 说明 |
|---|---|
| **给集合加长度上限** | 如 List 只保留最近 N 条（`LTRIM`） |
| **设置过期时间** | 别让 key 无限堆积（如按天分 key + TTL） |
| **按时间分 key** | `order:20260916`，而不是一个 `order:all` 无限增长 |
| **别用 Redis 存大对象** | 几 MB 的 JSON/文件放对象存储，Redis 只存引用 |
| **业务上限制** | 比如"一个用户的标签最多 1000 个" |

### 5. 集群层面的注意

拆分后要注意**分散到不同分片**：
如果子 key 都用同一个 hash tag（`{user1}:info:0`），
它们会落在**同一个分片**——**拆了等于没拆**。

---

## 五、一条救火速查

| 场景 | 立刻做什么 |
|---|---|
| 正在 `DEL` 一个大 key 卡住了 | 等它结束（已经在执行，杀不掉）；**以后改用 `UNLINK`** |
| 发现大 key，需要清理 | **用 `UNLINK`，不要用 `DEL`** |
| 客户端 `HGETALL` 导致超时 | 立刻改代码用 `HSCAN` 分批 |
| 集群某分片内存爆 | 定位大 key → 拆分 → **注意 hash tag 不要绑在一起** |
| 生产排查大 key | 在**从节点**跑 `--bigkeys`，别在主节点扫 |

## 六、记忆口诀

| 问题 | 答案 |
|---|---|
| 什么算大 key | String > 10KB；集合 > 5000 元素 或 > 1MB |
| 核心危害 | **阻塞单线程**——一个 key 卡住，全库排队 |
| 只有写才危险吗 | **不是**，`HGETALL` / `SMEMBERS` 这类**读**一样危险 |
| 还有其他危害吗 | 集群**数据倾斜**、网络拥塞、RDB fork 阻塞、主从延迟 |
| 怎么发现 | **`redis-cli --bigkeys`**（从节点执行）；`MEMORY USAGE` 精确查 |
| 怎么删 | **`UNLINK` 代替 `DEL`**（4.0+，异步释放） |
| 怎么读 | **`HSCAN` / `SSCAN` 代替 `HGETALL` / `SMEMBERS`** |
| 怎么根治 | **拆分**成多个子 key，按 field/member 哈希取模 |
| 拆分要注意什么 | 别用同一个 **hash tag**，否则还是落一个分片 |
