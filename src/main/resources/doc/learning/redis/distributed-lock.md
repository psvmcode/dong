# 分布式锁：Redis 怎么做，Redlock 为什么有争议

> 目标：说清正确的加锁姿势、看门狗机制，以及这个方案的边界在哪。

---

## 一句话

**用 `SET key value NX PX 30000` 加锁，用 Lua 脚本比对 value 后解锁，再用看门狗解决过期问题。**

分布式锁解决的是：**多个 JVM 进程之间互斥**（`synchronized` 只能管单个 JVM 内的线程）。

---

## 最基础的版本和它的三个坑

### 错误写法一：先 set 再 expire

```java
setnx lock 1
expire lock 30
```

**问题**：两步不是原子的。
`setnx` 成功但还没 `expire` 时进程挂了 → **锁永远不释放 → 死锁**。

### 错误写法二：用 setnx + expire 的复合命令

```java
SET lock 1 NX EX 30      // 一条命令，原子
```

比上一个好，但还有问题：**value 固定为 1**。

### 错误写法三：直接 del 解锁

```java
del lock
```

**这是最危险的错误**：

```
线程 A 拿到锁，超时时间 30 秒
线程 A 业务执行了 35 秒（超过了锁的过期时间）
       → 锁自动过期了，线程 B 拿到了锁
线程 A 终于执行完，执行 del lock
       → 把【线程 B 的锁】给删了！
```

**删了别人的锁**，锁直接失效。

## 正确的基础版本

### 加锁：value 必须唯一

```java
SET lock_key <唯一随机值> NX PX 30000
```

| 参数 | 作用 |
|---|---|
| `NX` | 只有 key 不存在时才设置（**保证互斥**） |
| `PX 30000` | 30 秒后自动过期（**防死锁**） |
| `value = 随机值` | 用来标识「这把锁是谁的」 |

value 用 UUID 或 `UUID + 线程ID`。
**必须唯一**，否则解锁时无法判断是不是自己的锁。

### 解锁：必须是 Lua 脚本

```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

**为什么必须用 Lua**：因为「读 value → 判断 → 删除」是三步，
必须**原子执行**。Lua 脚本在 Redis 里是单线程原子执行的。

如果拆成三步：

```
线程 A 读到 value 是自己的（还没删）
锁过期了，线程 B 拿到锁
线程 A 执行 del  →  删了 B 的锁
```

同样会删错。

## 还没解决：锁过期了但业务没跑完

上面的方案解决了「删别人的锁」，
但**锁过期本身**的问题还在：

```
线程 A 拿到锁，30 秒
业务跑了 35 秒
第 30 秒时锁过期，线程 B 拿到锁
现在 A 和 B 同时在跑  ← 互斥失效
```

### 解法：看门狗（Watch Dog）

**Redisson 的核心机制**。

```
1. 加锁，默认过期 30 秒
2. 启动一个后台线程（看门狗）
3. 每 10 秒（1/3 的过期时间）检查一次：
   业务还持有这把锁吗？
   ├─ 是 → 把过期时间重新设回 30 秒（续期）
   └─ 否 → 停止续期
4. 业务完成，释放锁，看门狗停止
```

**效果**：只要业务还在跑，锁就**不会过期**；
业务挂了，看门狗线程也没了，锁 30 秒后自动释放，**不会死锁**。

```java
RLock lock = redissonClient.getLock("myLock");
lock.lock();                    // 默认 30 秒，自动续期
try {
    // 业务逻辑，跑多久都行
} finally {
    lock.unlock();
}
```

**注意**：如果用 `lock.lock(10, TimeUnit.SECONDS)` **指定了超时时间**，
Redisson **不会启用看门狗**——到点就释放，不续期。
这是有意的设计：你明确说了 10 秒，就别让我帮你续。

## 可重入怎么实现

`synchronized` 和 `ReentrantLock` 都是可重入的，分布式锁也应该支持。

Redisson 用的是 **Redis Hash 结构**：

```
lock_name: {
    "field": "UUID:threadId",     ← 标识谁持有
    "value": 2                     ← 重入次数
}
```

- 加锁：重入次数 +1，刷新过期时间
- 解锁：重入次数 -1，**减到 0 才真正删除**

和 AQS 里 `state` 表示重入次数是**同一个思路**
（见 [aqs.md](../java/aqs.md)）。

## 最大的问题：Redis 单点故障

以上都是单 Redis 实例的情况。

**如果 Redis 挂了呢？**

```
主节点上锁成功
还没同步给从节点，主节点挂了
从节点升为主节点，但它没有这把锁的记录
另一个线程又上锁成功  ← 两把锁，互斥失效
```

**Redis 的主从复制是异步的**，这个窗口无法完全避免。

## Redlock 和它的争议

### 红锁的思路

Redis 作者 antirez 提出：用**多个独立的 Redis 实例**（通常 5 个）。

```
1. 依次向 5 个实例请求加锁（用相同的 key 和 value）
2. 每个请求设一个很短的超时（比如 5~50ms），超时就算失败
3. 如果【超过半数】（≥3 个）成功，且
   总耗时 < 锁的有效时间
   → 加锁成功
4. 否则：向【所有】实例发起解锁（包括那些没成功的）
```

**核心思想**：多数派 + 防止单点故障。

### 争议

Martin Kleppmann（分布式系统专家）提出了尖锐批评：

| 批评点 | 内容 |
|---|---|
| **GC 停顿问题** | 线程拿到锁后发生长时间 GC 停顿，锁过期了都不知道，<br>恢复后继续操作共享资源 → 互斥失效 |
| **时钟问题** | Redlock 依赖「时间」判断过期。<br>如果某台机器时钟跳跃（NTP 调整），锁可能提前失效 |
| **正确性存疑** | 它依赖很多关于时间和系统的假设，<br>而这些假设在真实分布式环境里不一定成立 |

他的结论：**如果你需要严格的正确性，用 ZooKeeper/etcd 这类基于共识算法的系统**。

antirez 反驳说 GC 停顿可以通过「加锁前检查时间」缓解，
但争议至今没有定论。

### 实践建议

| 场景 | 建议 |
|---|---|
| **追求性能、能容忍极小概率失效** | 单 Redis + Redisson（绝大多数业务的選択） |
| **追求绝对正确** | ZooKeeper / etcd（用 ZK 的临时顺序节点） |
| **想用 Redlock** | 谨慎。它比单实例复杂得多，且不保证绝对正确 |

**现实情况**：绝大多数公司用**单 Redis + Redisson**。
Redlock 因为运维复杂、收益不明确，用得很少。

## 实践检查清单

| 要点 | 说明 |
|---|---|
| ✅ 加锁用 `SET NX PX` 一条命令 | 不能分两步 |
| ✅ value 必须唯一 | 否则无法判断锁的归属 |
| ✅ 解锁必须用 Lua 脚本 | 保证「读-判断-删」原子 |
| ✅ 用看门狗解决过期问题 | 或自己实现续期 |
| ✅ 必须放 `finally` 里释放 | 异常时也要释放 |
| ⚠️ 别把锁粒度搞太大 | 只锁关键的资源，锁的时间越短越好 |
| ⚠️ 明确自己的一致性要求 | 能容忍小概率失效用 Redis，不能就用 ZK |

**最后一条判断标准**：

> 如果锁失效会导致**资损**（比如重复扣款），
> 那**不要只依赖分布式锁**，还要在数据库层面加**唯一索引**兜底。

这和跨境支付模块里「幂等键唯一索引兜底」是同一个道理——
**锁是优化手段，唯一约束才是最后一道防线**。
