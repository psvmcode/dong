# 重复消费：为什么无法避免，怎么做幂等

> 目标：说清重复消息从哪来，以及幂等的几种实现思路。

---

## 一句话

**MQ 只能保证「至少一次投递」，无法保证「恰好一次」——所以重复消费是必然的，幂等必须由消费端自己做。**

这是 MQ 最重要的认知之一。不要指望 MQ 帮你去重。

---

## 重复消息从哪来

### 1. 生产端重试

```
生产者发送消息
Broker 收到了，但返回 ack 时网络抖动
生产者超时 → 重试发送
→ Broker 收到两条一样的消息
```

### 2. 消费端 ack 失败

```
消费者处理成功
返回 ack 时网络失败（或消费者重启）
Broker 没收到 ack → 认为没消费 → 重投
→ 消费者又收到一条
```

### 3. 消费者负载均衡（rebalance）

消费者组扩容或某个实例下线，分区重新分配。
可能**新旧消费者同时消费了同一个消息**（旧实例还没提交 offset）。

---

## 什么是幂等

**同一个操作执行多次，结果和执行一次相同。**

```java
// 幂等：执行几次结果都一样
setStatus(orderNo, PAID);

// 不幂等：执行几次结果不同
balance = balance - 100;      // 扣两次就扣多了
count++;                      // 加两次就加多了
```

**判断方法**：看这个操作是「**赋值**」还是「**基于当前值的修改**」。
赋值天然幂等，基于当前值的累加/扣减不幂等。

这个判断标准和 [volatile 是否够用](../java/volatile.md) 是同一条：
**是否依赖当前值**。

## 幂等的四种实现

### 方案一：唯一键 + 数据库（最可靠，最通用）

**核心思路**：给每条消息一个全局唯一的业务 ID，
处理前先查「这个 ID 处理过吗」。

```sql
create table consumed_message (
    msg_id      varchar(64) not null comment '消息唯一标识',
    biz_type    varchar(32) not null comment '业务类型',
    -- ...
    primary key (msg_id)     -- ← 靠主键唯一约束兜底
);
```

```java
@Transactional
public void handle(Message msg) {
    try {
        consumedMessageMapper.insert(msg.getId(), msg.getBizType());
    } catch (DuplicateKeyException e) {
        log.info("duplicate message, skipped: {}", msg.getId());
        return;                                  // 已处理过，直接返回
    }
    doBusiness(msg);                             // 真正的业务逻辑
}
```

**关键点**：

1. **「记录已消费」和「业务处理」必须在同一个事务里**
   —— 否则记录了但业务失败，重试时会被当成重复消息跳过
2. **靠数据库唯一约束兜底**，不靠「先查再插」（并发下查和插之间有窗口）
3. 消息 ID 从哪来：生产者生成（雪花算法/UUID）放进消息头；
   或用业务的唯一键（如订单号）

**这个方案和跨境支付的幂等设计完全一致**——
唯一索引冲突时**不能抛异常**，要返回已存在的那笔，
否则客户端以为失败会换个单号重试，结果真的重复执行了。

### 方案二：业务状态机（推荐，最自然）

**核心思路**：处理前先判断当前状态，只有状态匹配才处理。

```java
// 订单状态：CREATED → PAID
@Transactional
public void pay(String orderNo) {
    // 带状态的更新，只有当前是 CREATED 才更新成功
    int rows = orderMapper.updateStatus(orderNo, PAID, CREATED);
    if (rows == 0) {
        log.info("order already paid or status mismatch: {}", orderNo);
        return;                    // 已经被处理过了
    }
    doPayBusiness(orderNo);
}
```

```sql
update trade_order
set status = #{newStatus}
where order_no = #{orderNo}
  and status = #{expectedStatus}     -- ← 关键：带原状态条件
```

**这是最推荐的方式**，因为它不需要额外的表，
而且和业务逻辑天然融合——状态时本来就该校验的。

这也就是「乐观锁」的思路（版本号或状态做条件）。

### 方案三：Redis SETNX（高并发、允许少量丢失）

```java
String key = "consumed:" + msgId;
Boolean first = redis.setIfAbsent(key, "1", 24, HOURS);
if (Boolean.FALSE.equals(first)) {
    return;                    // 已处理过
}
doBusiness(msg);
```

**优点**：快，不压数据库。

**缺点**：
- **Redis 不是可靠的存储**（会过期、可能丢）——
  如果 Redis 里记录丢了，重复消息就会漏网
- **不是原子操作**：`setIfAbsent` 成功但业务失败，
  这条消息就被永久跳过了

**所以**：高并发场景用它**挡掉大部分重复**（减轻数据库压力），
但**关键业务仍要用数据库唯一键做最终兜底**。

### 方案四：去重表 + 令牌（复杂场景）

针对「业务本身就是插入一条新记录」的情况，
可以把去重和业务合并：**给业务表加唯一索引**。

```sql
-- 比如转账流水，用请求号做唯一索引
alter table transfer_record add unique key uk_request_no (request_no);
```

第一次插入成功，重复请求撞唯一键失败 → 幂等。

---

## 各种方案对比

| 方案 | 可靠性 | 复杂度 | 适用 |
|---|---|---|---|
| **数据库唯一键** | ⭐⭐⭐ 最高 | 中（多一张表） | 通用，金融级 |
| **状态机/乐观锁** | ⭐⭐⭐ 高 | **低**（不用新表） | **有状态流转的业务，首选** |
| Redis SETNX | ⭐ 低 | 低 | 高并发去重（**需数据库兜底**） |
| 业务表唯一索引 | ⭐⭐⭐ 高 | 低 | 业务本身就是新增记录 |

## 常见误区

**误区一：用「先查再判断」做幂等**

```java
if (!exists(msgId)) {          // 查
    save(msgId);               // 插
    doBusiness();
}
```

**并发下有问题**：两个线程同时查到「不存在」，都去处理 → 重复了。

必须用**唯一约束**或**带状态的原子更新**，不能靠「查+判」。

**误区二：catch 到重复异常就抛出去**

```java
catch (DuplicateKeyException e) {
    throw e;         // ❌ 消费者会重试，但重试也没用，永远失败
}
```

正确做法是**捕获后返回成功**（这本来就是幂等的正常情况），
或者返回「已处理」并结束。

**误区三：以为 MQ 的「恰好一次」能解决**

某些 MQ（如 Kafka）宣称支持「Exactly Once」，
但那通常指的是 **Kafka 内部的流处理**（消费-处理-生产 的原子性），
**不涉及外部系统**（你的数据库、第三方接口）。

**只要消费端有副作用（写库、调接口），幂等就必须自己保证。**

## 实战检查清单

| 检查项 | 说明 |
|---|---|
| ✅ 每条消息有**全局唯一 ID** | 生产端生成，放进消息头 |
| ✅ 幂等记录和业务处理**在同一事务** | 否则会漏处理 |
| ✅ 靠**数据库约束**兜底，不靠先查 | 并发下先查无效 |
| ✅ 重复时**返回成功**而不是抛异常 | 抛异常会导致无限重试 |
| ✅ 幂等键的粒度要正确 | 是「一次业务操作」一个键，不是「一条消息」一个键 |

**最后一条值得展开**：如果业务上「同一笔订单的多次变更」是合法的
（比如订单先改地址再改金额），那幂等键就不能只用订单号，
要加上**操作类型**或**变更的版本**。

## 记忆口诀

| 问题 | 答案 |
|---|---|
| MQ 能保证不重复吗 | **不能**，只能保证「至少一次」 |
| 重复从哪来 | 生产重试、ack 失败、消费者 rebalance |
| 幂等判断标准 | 看是**赋值**还是**基于当前值修改** |
| 最推荐方案 | **状态机/乐观锁**（带原状态的 update） |
| 最可靠方案 | **数据库唯一键**（和业务同事务） |
| Redis 去重够吗 | 不够，**必须数据库兜底** |
| 常见错误 | 先查再插（并发失效）、重复时抛异常（无限重试） |
