# 消息堆积、延迟消息与死信队列

> 目标：说清堆积了怎么排查和处理，以及延迟消息、死信队列这两个高频考点。

---

## 一、消息堆积

### 现象

消息发送速度 > 消费速度，队列越积越多。

```
生产：1000 条/秒
消费：200 条/秒
→ 每秒净积压 800 条，一小时积压 288 万条
```

监控上看到 Lag（消费延迟）持续上涨。

---

### 为什么会堆积

| 原因 | 说明 |
|---|---|
| **消费端变慢** | 最常见。比如消费逻辑里加了慢查询、远程调用超时 |
| **消费端宕机** | 消费者挂了，完全不消费 |
| **突发流量** | 大促、活动，生产端瞬间暴涨 |
| **消费线程数不够** | 分区数少，并行度上不去 |
| **个别消息卡住** | 顺序消息里一条失败，整个队列挂起 |

---

### 怎么排查

```bash
# RocketMQ 查看消费进度和堆积量
mqadmin consumerProgress -g <消费组名>

# Kafka 查看 Lag（最常用）
kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
    --describe --group <group-id>

# 关注两列：
#   LAG       = 堆积条数
#   CURRENT-OFFSET / LOG-END-OFFSET
```

**排查思路**：

```
1. 先看 Lag 是不是持续上涨（不是偶尔波动）
2. 看消费者实例是不是都活着（有没有下线/频繁 rebalance）
3. 看消费耗时（是不是变慢了）
4. 查慢在哪：
   - 数据库慢查询？
   - 调用了外部接口超时？
   - 是不是有异常导致大量重试？
```

**最常见的真实原因**：消费逻辑里有**一次远程调用或慢 SQL**，
平时没事，流量一上来或者下游一抖，整体就慢下来了。

---

### 怎么处理（应急）

**按优先级**：

| 手段 | 做法 | 适用场景 |
|---|---|---|
| **1. 扩容消费者** | 加消费者实例 | **前提是分区数够**（见下） |
| **2. 扩大并行度** | 增加分区/队列数 | 根本解决并行度不足 |
| **3. 优化消费逻辑** | 去掉慢 SQL、批量处理 | 消费本身太慢 |
| **4. 批量消费** | 一次拉一批，批量写库 | 单条处理开销大 |

**关键限制**：

> **消费者数量不能超过分区数**，多出来的实例**分不到消息，白扩容**。

```
4 个分区，10 个消费者 → 只有 4 个在干活，6 个空转
```

所以要先**增加分区数**（Kafka 可以扩容分区，RocketMQ 可以增加队列数），
再加消费者。

**注意**：增加分区会**影响顺序消息**（同一 key 可能被路由到新分区）。

---

### 紧急止血：临时降级

如果堆积已经很严重（百万级）且短时间消不掉：

```java
// 临时方案：消费端不处理业务，直接批量转发到一个新 Topic
// 等高峰期过了，再用更多消费者慢慢消费新 Topic
```

**这是「分流」思路**：先不处理，把消息搬走恢复生产，事后再补。

---

### 怎么预防

| 措施 | 说明 |
|---|---|
| **监控 Lag** | 设置阈值告警（比如 Lag > 1 万就告警） |
| **消费端限流/熔断** | 下游挂了要快速失败，别拖住整个消费 |
| **分区数预留** | 一开始就多设几个分区，方便日后扩容 |
| **消费逻辑要轻** | 不要在消费里做重活，能异步的异步 |
| **设置消费超时** | 防止个别消息卡死线程 |

## 二、延迟消息

### 是什么

消息发出后，**不立即投递，而是延迟指定的时间**再让消费者收到。

### 典型场景

| 场景 | 延迟时间 |
|---|---|
| **订单超时未支付，自动关闭** | 30 分钟 |
| 发货后 N 天自动确认收货 | 15 天 |
| 提醒类（预约前 1 小时通知） | 不定 |

### 实现方式

**RocketMQ**：原生支持，**18 个固定级别**

```java
Message msg = new Message("OrderTopic", "超时关单", body);
msg.setDelayTimeLevel(3);      // 级别 3 = 10 秒
// 级别：1s 5s 10s 30s 1m 2m 3m 4m 5m 6m 7m 8m 9m 10m 20m 30m 1h 2h
producer.send(msg);
```

**限制**：只有 18 个固定档位，**不能自定义任意时间**。
（RocketMQ 5.x 起支持任意时间延迟）

**RabbitMQ**：两种方式

| 方式 | 说明 |
|---|---|
| **死信队列 + TTL** | 消息设 TTL，过期后进死信交换机，消费者消费死信队列 |
| **延迟插件** | `rabbitmq-delayed-message-exchange`（推荐） |

**Kafka**：**没有原生延迟消息**，只能自己实现：
- 把消息按延迟时间分到不同 Topic，消费者定时扫描
- 或用时间轮

**Redis 延迟队列**（我们项目里的做法）：
用 `RDelayedQueue`，简单但**没有重试和持久化保证**——
详见 [`scenario/classic.md`](../../scenario/classic.md) 里的说明，
可靠场景还是要靠 MQ。

## 三、死信队列（DLQ）

### 是什么

**反复消费失败的消息，最终被投递到一个专门的队列**，
不再回到原队列，避免无限重试堵住正常消息。

```
原队列 → 消费失败 → 重试 1 次 → 失败 → 重试 2 次 → ... → 达到上限
                                                          ↓
                                                     死信队列
```

### 为什么会进死信

| 原因 | 说明 |
|---|---|
| 重试次数超限 | 默认 16 次（RocketMQ） |
| 消息格式错误 | 解析不了，重试多少次都没用 |
| 业务永远失败 | 比如数据不存在、状态不对 |

### 为什么要它

**如果没有死信队列**：

```
一条永远失败的消息，无限重试
→ 占着消费线程
→ 后面的消息排不上
→ 整个队列堵塞
```

**有了死信队列**：坏消息被隔离出去，正常消息继续消费。

### 怎么处理死信

| 步骤 | 动作 |
|---|---|
| 1. **告警** | 死信队列有消息就要告警（说明有问题） |
| 2. **查看内容** | 看消息体和失败原因 |
| 3. **人工/自动处理** | 修数据后重新投递；或确认丢弃 |
| 4. **分析根因** | 是不是代码 bug |

**死信队列不是垃圾桶**——它里面的消息需要**定期分析和处理**，
不能丢进去不管。

## 四、重试机制

### 重试次数与间隔

RocketMQ 默认的重试间隔（16 次）：

```
10s 30s 1m 2m 3m 4m 5m 6m 7m 8m 9m 10m 20m 30m 1h 2h
```

**递进式间隔**（越来越长）的设计思路：
失败通常是下游短暂不可用，等一会儿可能就恢复了；
如果真的长时间失败，就不用太频繁地重试了。

### 关键点

| 要点 | 说明 |
|---|---|
| **重试会导致重复消费** | 必须幂等（见 [idempotent.md](idempotent.md)） |
| **重试消息在特殊的重试队列** | 不在原队列（顺序消息要特别注意） |
| **达到上限进死信** | 不能无限重试 |
| **区分异常类型** | 参数错误（重试无用，直接进死信）<br>网络超时（可以重试） |

**最后一条很重要**：

```java
try {
    process(msg);
} catch (BizException e) {
    // 业务异常：重试一万次也是失败，直接进死信/记录
    log.error("biz error, skip", e);
    return SUCCESS;                    // 或者标记后跳过
} catch (Exception e) {
    // 网络/超时：可以重试
    return RECONSUME_LATER;
}
```

## 五、检查清单

| 项目 | 说明 |
|---|---|
| ✅ 监控 Lag 并告警 | 堆积要能被**提前发现** |
| ✅ 分区数要预留 | 否则扩容消费者无效 |
| ✅ 消费逻辑要轻 | 慢 SQL、远程调用是堆积主因 |
| ✅ 区分可重试/不可重试异常 | 不可重试的直接跳过或进死信 |
| ✅ 死信队列要有人看 | 配告警 + 定期分析 |
| ✅ 幂等必须有 | 重试和重复投递是常态 |

## 记忆口诀

| 问题 | 答案 |
|---|---|
| 堆积主因 | **消费端变慢**（慢 SQL / 远程调用） |
| 为什么加消费者没用 | **消费者数不能超过分区数** |
| 根本解法 | 先扩**分区**，再加消费者 |
| 延迟消息哪家强 | **RocketMQ 原生支持**（18 个固定级别） |
| Kafka 有延迟消息吗 | **没有原生**，要自己实现 |
| 死信队列干什么 | 隔离**永远失败**的消息，防止堵住正常消息 |
| 死信能不管吗 | 不能，要**告警 + 分析根因** |
| 重试间隔为什么递增 | 下游短暂故障可能自愈，不必频繁重试 |
