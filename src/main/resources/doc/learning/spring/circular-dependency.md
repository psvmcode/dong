# 循环依赖：三级缓存到底是什么

> 目标：说清 Spring 怎么解决循环依赖，以及哪些情况它解决不了。

---

## 一句话

**Spring 用「提前暴露还没初始化完的对象」打破死循环，靠三级缓存实现。**

但**只对单例 Bean 的字段注入有效**——构造方法注入和 prototype 都不行。

---

## 什么是循环依赖

```java
@Service
public class A {
    @Autowired
    private B b;
}

@Service
public class B {
    @Autowired
    private A a;
}
```

A 依赖 B，B 又依赖 A。

**如果不处理会怎样**：

```
创建 A → 需要 B → 创建 B → 需要 A → 创建 A → 需要 B → ... 死循环
```

---

## 三级缓存

Spring 内部有三个 Map（在 `DefaultSingletonBeanRegistry` 里）：

| 缓存 | 名字 | 存的是什么 |
|---|---|---|
| **一级** | `singletonObjects` | **完全初始化好**的成品 Bean |
| **二级** | `earlySingletonObjects` | 半成品（**已实例化但未初始化**） |
| **三级** | `singletonFactories` | 生产半成品的**工厂**（`ObjectFactory`） |

**名字记住**：成品、半成品、工厂。

---

## 解决流程

以 A、B 循环依赖为例：

```
1. 创建 A
   实例化 A（调构造方法）→ A 还是半成品
   ↓
   【把 A 的工厂放进三级缓存】     ← 关键一步：提前暴露
   ↓
2. 填充 A 的属性 → 发现需要 B
   ↓
3. 创建 B
   实例化 B → B 还是半成品
   【把 B 的工厂放进三级缓存】
   ↓
4. 填充 B 的属性 → 发现需要 A
   ↓
5. 找 A：
   一级缓存没有（A 没初始化完）
   二级缓存没有
   【三级缓存有 A 的工厂】→ 调用工厂拿到 A 的半成品
   ↓
   【把 A 从三级移到二级】，删掉三级里的工厂
   ↓
6. B 拿到 A 的引用（虽然是半成品，但引用是有效的）
   B 完成属性填充 → B 初始化完成 → B 放进一级缓存
   ↓
7. 回到 A，A 拿到成品 B
   A 完成初始化 → A 放进一级缓存
```

**核心思想**：

> **对象只要实例化了（分配了内存），它的引用就是确定的——
> 即使属性还没填、初始化还没做。
> 先把这个「半成品的引用」给对方用，等回头再补全。**

因为 Java 是**引用传递**，对方拿到的是同一个对象的引用，
等 A 后面把属性填上了，B 里的 `a` 自然也就完整了。

---

## 为什么必须是「三级」，两级不够吗

**这是面试最有价值的问题。**

如果只有两级（成品 + 半成品），把半成品**直接**放进二级缓存，
好像也能解决循环依赖？

**能解决普通情况，但解决不了 AOP 代理的情况。**

### 问题在哪

如果 A 需要被 AOP 代理（`A` 上有 `@Transactional`），
那么 B 里注入的应该是 **A 的代理对象**，不是 A 本身。

但 AOP 代理是在**初始化最后**才生成的
（见 [bean-lifecycle.md](bean-lifecycle.md)）。
在属性填充阶段，A 还是原始对象，代理还没生成。

### 三级缓存怎么解决

第三级存的是**工厂**，不是对象：

```java
addSingletonFactory(beanName, () -> getEarlyBeanReference(beanName, mbd, bean));
```

当有人需要 A 时，**才调用这个工厂**：
`SmartInstantiationAwareBeanPostProcessor.getEarlyBeanReference()`——
这个方法会**判断 A 是否需要代理，需要就提前生成代理对象**返回。

**所以三级缓存的价值是：延迟决定「给别人的是原始对象还是代理对象」。**

用两级缓存的话，你必须在半成品阶段就确定放什么，
那时候还没走到判断 AOP 的逻辑，放错了就无法挽回。

| 缓存级别 | 作用 |
|---|---|
| 一级 | 存成品，正常使用 |
| 二级 | 存半成品，避免重复调用工厂（同一个半成品只生成一次） |
| **三级** | **存工厂，延迟到被引用时才决定返回原始对象还是代理对象** |

### 二级缓存是不是多余的

严格说，如果只有「单例 + 无 AOP」，两级确实够。
但二级缓存的作用是**保证同一个半成品只被创建一次**——
如果 A 同时被 B 和 C 依赖，不能生成两个不同的半成品引用。

所以三级各有分工，不是冗余设计。

---

## 哪些情况解决不了

### 1. 构造方法注入

```java
@Service
public class A {
    public A(B b) { }        // 构造注入
}

@Service
public class B {
    public B(A a) { }        // 构造注入
}
```

**为什么不行**：三级缓存的前提是「**先实例化，再暴露**」。
但构造方法注入要求**实例化时就要拿到 B**——
这时候 A 连对象都还没造出来，没法提前暴露。

**本质**：这是**无解的死循环**——
要造 A 必须先有 B，要造 B 必须先有 A，谁都没法先实例化。

**报错信息**：
```
Requested bean is currently in creation: Is there an unresolvable circular reference?
```

**解法**：
- 改成字段注入（`@Autowired`）
- 用 `@Lazy` 延迟其中一个的注入
- **最好的办法：重新设计，拆出第三个类**——循环依赖通常说明职责划分有问题

### 2. prototype（多例）Bean

```java
@Scope("prototype")
@Service
public class A { @Autowired private B b; }
```

**为什么不行**：Spring **不缓存 prototype Bean**，
所以没有「提前暴露」的地方。每次都要新建，就会无限递归。

### 3. 用了 `@Async` 或某些 BeanPostProcessor

如果 Bean 被某些特殊的后置处理器处理，可能导致提前暴露的对象和最终对象不一致。

---

## 怎么避免循环依赖

**最好的办法是不产生循环依赖**。

| 方法 | 说明 |
|---|---|
| **重新设计** | 循环依赖通常意味着两个类职责纠缠，<br>抽出第三个类让它们都依赖它（**最推荐**） |
| 用 `@Lazy` | 延迟注入，打破即时依赖 |
| 改成 setter/字段注入 | 但这是治标，结构问题还在 |
| 用事件机制 | A 完成时发事件，B 监听处理，解耦 |

**判断标准**：

> 如果两个类必须互相知道对方，
> 问一句「是不是有块逻辑放错了地方」——
> 大多数时候答案是肯定的。

---

## Spring 什么时候会报循环依赖错误

**注意**：Spring Boot 2.6 起，**默认禁止循环依赖**！

```
The dependencies of some of the beans in the application context form a cycle
```

需要显式配置才允许：

```yaml
spring:
  main:
    allow-circular-references: true
```

**但这个开关是帮你兜底的，不是鼓励你写循环依赖。**
遇到报错，正确的反应是**重构代码**，不是打开开关。
