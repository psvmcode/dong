# 系统设计：秒杀系统

> 目标：按面试答题节奏走一遍——难点在哪、怎么分层拦截、怎么防超卖。
> 我们项目里的 `seckill` 模块就是这个设计的可运行版本。

---

## 一、秒杀的难点

普通电商系统扛不住秒杀，因为四个特点：

| 特点 | 后果 |
|---|---|
| **瞬间流量极高** | 平时 QPS 几百，秒杀瞬间几十万 |
| **读远大于写** | 大量用户在刷页面、查库存 |
| **库存极少** | 100 万人抢 100 件商品，**99.99% 的请求都是无效的** |
| 有黄牛和脚本 | 请求可能不公平、有恶意刷 |

**核心洞察**：

> **绝大部分请求注定失败（抢不到），
> 设计的重点不是「处理所有请求」，而是「尽早把无效请求挡掉」。**

---

## 二、总体思路：分层拦截

```
用户请求
   ↓
【1】客户端拦截      按钮置灰、验证码、防重复提交
   ↓
【2】网关/Nginx     限流、封禁恶意 IP、过滤重复请求
   ↓
【3】应用层          缓存读库存、Redis 预扣库存、MQ 削峰
   ↓
【4】数据层          数据库最终扣减、乐观锁防超卖
```

**越靠前拦截，代价越小**。
能在浏览器挡掉的请求，就别让它打到网关；
能在网关挡掉的，就别让它进应用；
能用 Redis 挡掉的，就别打数据库。

## 三、逐层设计

### 第 1 层：客户端

| 手段 | 说明 |
|---|---|
| **按钮置灰** | 点一次后禁用，防止疯狂点击 |
| **验证码/滑块** | 拉长请求时间，打散瞬时峰值，且能拦脚本 |
| 本地限流 | 限制同一用户短时间内的请求次数 |

**注意**：客户端拦截**只能防君子**——直接调接口就绕过了。
但它的价值是**过滤掉大部分正常用户的无效重复请求**。

### 第 2 层：网关

| 手段 | 说明 |
|---|---|
| **限流** | 令牌桶，只放行系统能承受的量 |
| **封禁** | 识别恶意 IP/设备，直接拒绝 |
| 去重 | 同一用户短时间内的重复请求只放一个 |

**限流阈值怎么定**？压测得出系统容量，取 80% 作为阈值。

### 第 3 层：应用层（核心）

#### 3.1 库存读取走缓存

**绝对不能每次查数据库**。

```
商品详情、剩余库存 → 全走 Redis
```

库存更新后同步刷新缓存。读请求完全不碰数据库。

#### 3.2 Redis 预扣库存（关键）

**思路**：把库存**提前加载到 Redis**，抢购时在 Redis 里原子扣减。

```lua
-- Lua 脚本，保证「判断 + 扣减」原子
local stock = tonumber(redis.call('get', KEYS[1]))
if stock <= 0 then
    return 0          -- 没库存了
end
redis.call('decr', KEYS[1])
return 1              -- 扣减成功
```

**为什么必须用 Lua**：「读库存 → 判断 → 扣减」是三步，
不用 Lua 的话并发下会超卖（都读到还有 1 件，都去扣）。

**效果**：库存抢完之前，请求在 Redis 层就被挡掉了，
**只有真正抢到的少数请求才走后面的下单流程**。

这就是「分层拦截」的价值——100 万请求，可能只有 100 个走到数据库。

#### 3.3 MQ 削峰

抢到库存的请求，不发数据库，而是**发到消息队列**：

```
Redis 预扣成功 → 发送下单消息到 MQ → 立即返回「排队中」
                        ↓
              消费者按自己的速度处理 → 创建订单 → 扣数据库库存
```

**好处**：
- 数据库**按自己的节奏消费**，不会被瞬时流量冲垮
- 用户看到「排队中」，体验可接受

**代价**：**异步**了，用户不能立刻知道结果，需要轮询或推送。

### 第 4 层：数据层防超卖

**最后一道防线**。即使前面的 Redis 挡了 99%，
数据库层仍要保证**绝对不超卖**。

#### 方案一：乐观锁（推荐）

```sql
update seckill_product
set stock = stock - 1
where product_id = #{productId}
  and stock > 0              -- ← 关键：带库存条件
```

**`stock > 0` 这个条件是防超卖的核心**——
数据库会保证这条 update 的原子性，
即使 100 个并发同时执行，也最多成功 100 次（库存多少就成功多少次）。

判断成功与否：看**影响行数**，为 0 就是没抢到。

#### 方案二：悲观锁

```sql
select * from seckill_product where product_id = ? for update;
-- 扣减
update ...;
```

**不推荐**：并发下大量线程阻塞等待锁，性能极差。

## 四、完整的请求流程

```
1. 用户点「立即抢购」
2. 前端：按钮置灰 + 验证码
3. 网关：限流，超出的直接返回「已售罄」
4. 应用：
   a. 查 Redis 库存（读，不扣）
   b. 没库存 → 直接返回售罄（并本地标记，后续请求连 Redis 都不查）
   c. 有库存 → 执行 Lua 原子扣减
      - 失败 → 返回售罄
      - 成功 → 发 MQ 消息，返回「排队中」
5. MQ 消费者：
   a. 创建订单
   b. update 扣数据库库存（带 stock > 0 条件）
   c. 成功 → 更新订单为「已确认」
      失败 → 回滚（Redis 库存加回去，订单标记失败）
6. 用户轮询结果
```

## 五、进阶问题

### 怎么防止超卖（总结）

**三层保险**：

| 层 | 手段 |
|---|---|
| Redis | Lua 原子扣减（**挡掉绝大部分**） |
| MQ | 削峰，串行化处理 |
| **数据库** | **`where stock > 0` 乐观锁（最终保证）** |

**数据库那层是必须的**——Redis 可能挂、可能数据不一致，
只有数据库的条件更新是绝对可靠的。

### 怎么防止重复下单

**同一个用户只能买一件**（秒杀常见规则）：

```sql
-- 用唯一索引兜底
alter table seckill_order add unique key uk_user_product (user_id, product_id);
```

配合 Redis 的 `SETNX` 先挡一层，数据库唯一索引**最终兜底**。

这和[幂等](../mq/idempotent.md)的思路完全一致。

### 库存扣了但订单创建失败怎么办

**要回滚**：把 Redis 库存加回去，否则少卖。

更稳妥的做法是**最终一致 + 对账**：
定期比对「Redis 剩余库存 + 已下单数量」和「初始库存」，
不一致就告警并补偿。

### 热点商品的库存行竞争

100 万人抢同一个商品，所有 update 都打在同一行，
**数据库行锁成为瓶颈**。

**优化**：把库存**拆成多行**（分桶）：

```
stock_1: 20
stock_2: 20
stock_3: 20
stock_4: 20
stock_5: 20     ← 共 100 件，拆成 5 行
```

扣减时随机选一行去扣，把热点**分散到多行**。
这就是「热点账户拆分」的思路，和资金系统里的处理一样。

### 怎么防黄牛

| 手段 | 说明 |
|---|---|
| 验证码/滑块 | 提高脚本成本 |
| 限购 | 一人一件（唯一索引保证） |
| 设备指纹 | 识别同一设备批量请求 |
| 风控规则 | 异常行为识别（IP、请求频率、账号特征） |
| 答题 | 最有效但影响体验 |

## 六、总结

| 环节 | 方案 |
|---|---|
| 核心思路 | **分层拦截**，越早挡掉越省 |
| 客户端 | 按钮置灰、验证码 |
| 网关 | 限流、封禁 |
| 读 | 全走**缓存**，不碰数据库 |
| 扣库存 | **Redis Lua 原子扣减** |
| 削峰 | **MQ 异步下单** |
| 防超卖（最终） | 数据库 **`where stock > 0`** |
| 防重复 | Redis SETNX + **唯一索引兜底** |
| 热点优化 | 库存**分桶**分散行锁 |

**一句话总结**：
秒杀的本质不是「提升系统容量」，而是**「尽早拒绝无效请求」**——
因为 99.99% 的请求注定抢不到。

---

## 常见失分点

| 失分点 | 正确做法 |
|---|---|
| 一上来就想加机器 | **先分层拦截**，加机器是最贵的方案 |
| 直接查数据库扣库存 | 数据库扛不住，要 Redis 挡 |
| 「判断 + 扣减」分两步 | **必须 Lua 原子**（或数据库带条件更新） |
| 只用 Redis 防超卖 | **数据库才是最终保障** |
| 忘了防重复下单 | 唯一索引兜底 |
| 不考虑库存回滚 | 下单失败要把库存加回去 |
