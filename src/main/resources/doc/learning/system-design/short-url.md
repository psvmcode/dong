# 系统设计：短链接服务

> 目标：按面试答题的节奏走一遍——需求 → 估算 → 设计 → 优化 → 追问。
> 我们项目里的 `shorturl` 模块就是这个设计的可运行版本。

---

## 一、需求澄清（先问，别急着设计）

面试里**先问清楚需求**是加分项：

| 问题 | 假设答案 |
|---|---|
| 每天多少新短链？ | 1 亿条/天 |
| 读写比例？ | **读远大于写**（100:1 甚至 1000:1） |
| 短链有效期？ | 大部分长期有效，部分有过期时间 |
| 需要自定义短码吗？ | 可选（如 `t.cn/mydream`） |
| 需要统计点击吗？ | 需要 |

**核心矛盾**：这是个**读多写少、且读的延迟要求极高**的系统。
跳转必须快（用户点开就要跳），写可以稍慢。

---

## 二、容量估算

```
写入：1 亿条/天 ≈ 1200 条/秒（峰值按 5 倍算 ≈ 6000 QPS）
读取：读写比 100:1 → 1 亿 × 100 = 100 亿次/天 ≈ 12 万 QPS

存储（每条记录约 500 字节）：
1 亿 × 500B = 50GB/天
一年 ≈ 18TB
```

**结论**：读 QPS 很高（12 万），必须用**缓存扛读**；
存储量不小，要考虑分库分表或定期归档。

---

## 三、短码怎么生成

这是本题的核心。两种思路：

### 方案一：哈希（如 MD5 后取前 6 位）

```java
String code = md5(longUrl).substring(0, 6);
```

**问题**：

1. **冲突**：6 位 Base62（62^6 ≈ 568 亿）看似很大，
   但按**生日悖论**，只要 8 万条左右就有一半概率冲突
2. 冲突后要处理（加盐重试），逻辑变复杂
3. **同一个长链永远生成同一个短码**——可能被别人猜到、遍历

### 方案二：发号器（推荐）

**思路**：用一个全局自增 ID，转成 62 进制作为短码。

```java
long id = idGenerator.nextId();     // 雪花算法或号段
String code = base62.encode(id);    // 1234567 → "5B9d"
```

| 优点 | 说明 |
|---|---|
| **绝对不冲突** | ID 是唯一的 |
| 长度可控 | ID 越大码越长，可从 6 位开始 |
| **同一长链每次生成不同短码** | 避免被遍历（**这是刻意设计**） |

**62 进制容量**：

```
6 位：62^6 ≈ 568 亿
7 位：62^7 ≈ 3.5 万亿
```

按 1 亿/天算，6 位能用 15 年。

**结论：用发号器**。这就是我们项目里的做法
（见 [`scenario/classic.md`](../../scenario/classic.md) 短链部分）。

## 四、存储设计

```sql
create table short_url (
    id          bigint unsigned not null auto_increment,
    code        varchar(16)     not null,
    origin_url  varchar(2048)   not null,
    hit_count   bigint          not null default 0,
    enabled     tinyint         not null default 1,
    expire_time datetime        null,
    create_time datetime        not null,
    primary key (id),
    unique key uk_code (code)      -- ← 关键
);
```

**核心索引**：`code` 上的唯一索引。所有查询都是 `where code = ?`。

**分库分表**：按 `code` 哈希分片。因为查询只按 code，分片键选 code 很自然。

## 五、跳转流程（重点）

```
1. 用户访问 t.cn/Ab3dEf
2. 服务提取短码 Ab3dEf
3. 查缓存（Redis）→ 命中直接返回长链
4. 未命中 → 查数据库 → 回写缓存
5. 302 重定向到长链
6. 异步累加点击数
```

### 关键问题一：301 还是 302？

**必须用 302（临时重定向）**。

| 状态码 | 含义 | 问题 |
|---|---|---|
| **301** | 永久重定向 | **会被浏览器缓存**！下次用户直接跳，不经过服务端，**点击统计失效** |
| **302** | 临时重定向 | 每次都经过服务端，能统计、能控制 |

**这是必考细节**。用了 301，短链服务的统计功能就废了。

### 关键问题二：怎么扛 12 万 QPS

**缓存命中率要做到 99%+**：

- 热点短链（爆款推广链接）会集中在少数 key 上
- 缓存 7 天，或按访问频率动态续期
- **空值也缓存**（防穿透）：不存在的短码缓存一个 null 标记，10 分钟

### 关键问题三：点击数怎么统计

**不能每次跳转都写数据库**——那会把跳转从毫秒级拖慢。

```
跳转时：只累加 Redis 原子计数器（微秒级）
定时：  批量把计数回写数据库
```

**回写用绝对值而不是增量**：即使某轮回写失败，下轮也能自动补平。

（我们项目最初就有这个 bug：`hit_count` 字段库里有但代码从不更新，
因为没人调用回写方法。修复过程记录在 classic 文档里。）

## 六、进阶追问

### 短码过期怎么办？

建链时设 `expire_time`，**缓存 TTL 也跟着缩短**。
到期后缓存自动失效，请求落到数据库，被过期校验拦下。

### 怎么下线违规短链？

加 `enabled` 字段。停用时**必须同步删缓存**——
否则已缓存的短链照样能跳转，停用形同虚设。

### 想让同一个长链生成同一个短码？

用布隆过滤器或缓存做「长链 → 短码」的映射。
但**我们项目刻意不做这件事**——
因为同一长链固定短码，别人可以反推、遍历你的所有短链。

### 缓存挂了怎么办？

- Redis 集群（主从 + 哨兵）
- 本地缓存（Caffeine）兜一层
- **限流**：只允许一部分请求穿透到数据库，保护 DB

### 怎么防止短链被刷？

- 短码足够长且随机（用发号器天然满足）
- 对异常访问频率限流
- 敏感内容做审核

## 七、总结

| 环节 | 方案 |
|---|---|
| 短码生成 | **发号器 + Base62**（不用哈希） |
| 存储 | MySQL，按 code 分片，`code` 唯一索引 |
| 读性能 | **Redis 缓存**，命中率 99%+ |
| 重定向 | **302**（用 301 统计就废了） |
| 点击统计 | Redis 累加 + **定时回写**（不在跳转时写库） |
| 防穿透 | 缓存空值 |
| 过期/停用 | expire_time + enabled，停用要**删缓存** |

**一句话总结**：
短链是个典型的「读多写少」系统，核心是**用缓存扛读、用发号器避免冲突、用 302 保住统计能力**。

---

## 常见失分点

| 失分点 | 正确做法 |
|---|---|
| 一上来就写代码 | **先澄清需求、做容量估算** |
| 用 MD5 哈希 | 会冲突，且同一长链短码固定 |
| 用 301 | **统计会失效** |
| 跳转时写数据库更新计数 | 拖慢跳转，热点还会锁竞争 |
| 不考虑缓存穿透 | 要缓存空值 |
| 停用短链不删缓存 | 停用不生效 |
