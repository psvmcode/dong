# synchronized：锁升级是怎么回事

> 目标：说清它保证什么、锁存在哪里、以及「偏向→轻量→重量」的升级过程。

---

## 一句话

**synchronized 保证原子性、可见性、有序性三者都有**，可重入，自动释放锁。

上一章的 [volatile](volatile.md) 只管可见性和有序性，管不了原子性；
synchronized 三个都管，代价是**会阻塞线程、性能更重**。

---

## 三种用法，锁的分别是谁

| 用法 | 锁的是什么 |
|---|---|
| `synchronized` 修饰**实例方法** | 当前**对象实例**（this） |
| `synchronized` 修饰**静态方法** | 当前**类的 Class 对象** |
| `synchronized(obj) { }` 代码块 | **括号里那个对象** |

```java
public synchronized void add() { }              // 锁 this
public static synchronized void init() { }      // 锁 Xxx.class
public void run() {
    synchronized (lock) { }                     // 锁 lock 这个对象
}
```

**踩坑点**：实例方法和静态方法的锁**不是同一个东西**，
一个锁 this、一个锁 Class，两者互不影响，别以为加了 synchronized 就安全了。

---

## 锁存在哪里：对象头的 Mark Word

每个 Java 对象都有个**对象头**，里面的 **Mark Word** 记录了这个对象的锁状态。

简单理解：锁的信息不是存在某个全局表里，而是**记在被锁的那个对象的头部**。

```
Mark Word（64 位）在不同锁状态下存不同内容：
无锁     → 对象的 hashCode、分代年龄
偏向锁   → 持有锁的线程 ID
轻量级锁 → 指向栈中锁记录的指针
重量级锁 → 指向互斥量（monitor）的指针
```

---

## 锁升级：偏向 → 轻量 → 重量

JDK 1.6 之前，synchronized 一上来就是重量级锁（调用操作系统的 mutex），
涉及**用户态与内核态切换**，非常慢，所以那时大家都用 ReentrantLock。

1.6 之后引入了锁升级，性能大幅改善。四个状态，**只能升不能降**：

```
无锁 → 偏向锁 → 轻量级锁 → 重量级锁
```

### 1. 偏向锁

**核心思想**：大多数情况下，一把锁总是被同一个线程反复获取。

那就在 Mark Word 里记下这个线程 ID。
下次同一线程再来，看一眼 ID 是自己的，**直接放行，连 CAS 都不用做**。

**代价**：一旦有另一个线程来竞争，偏向锁就要**撤销**（需要等待全局安全点，即 STW），
反而有额外开销。

> **JDK 15 起偏向锁已被标记废弃并默认关闭**（JEP 374）。
> 因为现代应用里锁竞争普遍存在，偏向锁带来的收益抵不上撤销的成本。
> 面试时可以说「历史上曾用于优化单线程重复加锁的场景，但已被废弃」——这样答显得你跟得上版本。

### 2. 轻量级锁

有第二个线程来竞争时，偏向锁升级为轻量级锁。

**做法**：线程在自己的栈帧里创建一份「锁记录」，然后**用 CAS 把 Mark Word 替换成指向这份记录的指针**。

- CAS 成功 → 拿到锁
- CAS 失败 → 说明有人占着，线程**自旋**（空转重试）等待

**自旋**：不阻塞自己，而是循环尝试 CAS。
因为多数情况下锁持有时间很短，等一会儿就能拿到，
**比「阻塞+唤醒」划算**（后者要切换内核态）。

### 3. 重量级锁

自旋到一定程度（超过阈值，或自旋线程数超过 CPU 核数的一半）还没拿到锁，
说明竞争很激烈，再空转就是白烧 CPU 了。

此时升级为重量级锁：**线程阻塞，进入等待队列，交给操作系统调度**。
这个状态下没拿到锁的线程会**挂起**，不再消耗 CPU，代价是唤醒时要切换内核态。

---

## 为什么要设计成逐步升级

因为**加锁的代价和竞争的激烈程度相关**：

| 竞争程度 | 最优策略 | 代价 |
|---|---|---|
| 几乎无竞争（同一线程反复） | 偏向锁：记个 ID | 几乎为零 |
| 轻度竞争（交替执行） | 轻量级锁：CAS + 自旋 | 烧一点 CPU，但不切换内核态 |
| 激烈竞争（长时间持锁） | 重量级锁：阻塞挂起 | 切换内核态，但省 CPU |

**没有一种策略在所有情况下都最优**，所以 JVM 根据实际竞争情况动态选择。

## synchronized vs ReentrantLock

| 对比项 | synchronized | ReentrantLock |
|---|---|---|
| 使用方式 | 关键字，自动加锁释放 | 手动 `lock()` / `unlock()` |
| 释放保证 | **一定释放**（异常也释放） | 必须写在 `finally` 里，忘了就死锁 |
| 可重入 | ✅ | ✅ |
| 可中断 | ❌ 等不到就一直等 | ✅ `lockInterruptibly()` |
| 超时 | ❌ | ✅ `tryLock(timeout)` |
| 公平锁 | ❌ 只有非公平 | ✅ 可选公平/非公平 |
| 条件队列 | 一个（`wait`/`notify`） | 多个 `Condition` |
| 性能 | JDK 1.6 后差距很小 | 略好，但在激烈竞争下更稳 |

**怎么选**：

- **优先用 synchronized**——写起来简单，不会忘记释放，性能已经不差
- 只有需要**可中断、超时、公平锁、多个条件队列**时，才上 ReentrantLock

## 常见误区

**误区一：`synchronized` 锁住的是代码**
不是。它锁的是**对象**。两段不同的 synchronized 代码，只要锁的是同一个对象，就互斥。

**误区二：加了 synchronized 就线程安全**
只有**所有访问共享变量的地方都加了同一把锁**才安全。
一处加锁、另一处直接读，照样有问题。

**误区三：synchronized 一定比 Lock 慢**
1.6 之后两者性能接近。锁升级、锁粗化、锁消除等优化让 synchronized 在无竞争时非常快。

## 记忆口诀

| 问题 | 答案 |
|---|---|
| 保证什么 | 原子性 + 可见性 + 有序性（volatile 少了原子性） |
| 锁在哪 | 对象头的 Mark Word |
| 升级路径 | 无锁 → 偏向 → 轻量 → 重量（**只升不降**） |
| 轻量锁怎么拿 | CAS 替换 Mark Word，失败就自旋 |
| 什么时候变重量 | 自旋太久或竞争太激烈 |
| 偏向锁现状 | JDK 15 起已废弃默认关闭 |
| 怎么选 | 优先 synchronized，需要超时/中断/公平才用 Lock |
