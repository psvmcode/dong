# 分布式事务：六种方案怎么选

> 目标：说清每种方案的原理、代价，以及什么场景该用哪个。

---

## 一句话

**分布式事务解决「跨服务/跨库的操作如何同时成功或同时失败」——
没有银弹，只有按一致性要求和代价做取舍。**

---

## 先明确两个理论

### CAP

分布式系统最多同时满足两项：

| 字母 | 含义 |
|---|---|
| **C** Consistency | 一致性：所有节点同一时刻数据相同 |
| **A** Availability | 可用性：每个请求都能得到响应 |
| **P** Partition tolerance | 分区容错：网络分区时系统仍能运行 |

**P 是必须的**（网络分区无法避免），所以实际是 **C 和 A 二选一**：
- 选 **CP**：保证一致，分区时拒绝服务（如 ZooKeeper）
- 选 **AP**：保证可用，数据暂时不一致（如大多数互联网系统）

### BASE（对 CAP 中 AP 的补充）

| 字母 | 含义 |
|---|---|
| **BA** Basically Available | 基本可用：允许损失部分可用性（降级、限流） |
| **S** Soft state | 软状态：允许存在中间状态 |
| **E** Eventually consistent | **最终一致**：经过一段时间后数据会一致 |

**实践结论**：绝大多数业务要的是**最终一致**，不是强一致。
强一致的代价远超多数人的想象。

## 方案一：2PC（两阶段提交）

### 流程

有个**协调者**，参与者是各个数据库/服务。

```
阶段一（Prepare）：
  协调者问所有人：「能提交吗？」
  参与者：执行事务但不提交，锁住资源，回复 Yes/No

阶段二（Commit/Rollback）：
  全 Yes  → 协调者下令「提交」，各参与者提交
  有 No   → 协调者下令「回滚」，各参与者回滚
```

### 问题

| 问题 | 说明 |
|---|---|
| **同步阻塞** | 阶段一之后，所有参与者**锁着资源等协调者**，期间不能做别的 |
| **单点故障** | 协调者挂了，参与者**永远阻塞**（不知道该提交还是回滚） |
| **数据不一致** | 阶段二部分参与者收到 commit，部分没收到（网络分区）→ 有的提交了有的没有 |
| **性能差** | 两轮网络通信 + 长时间锁资源 |

### 结论

**生产环境基本不用裸的 2PC**。
数据库层面的 XA 事务就是 2PC（MySQL 支持），但因为上述问题用得很少。

---

## 方案二：3PC（三阶段提交）

在 2PC 基础上加了 **CanCommit** 阶段，并引入**超时机制**：
参与者等待超时后**自动提交**（而不是一直阻塞）。

**改进**：解决了协调者单点导致的永久阻塞。

**新问题**：超时自动提交在「其实该回滚」的情况下会造成数据不一致。

**结论**：比 2PC 好一点，但**实际很少用**——复杂度和收益不成正比。

## 方案三：TCC（Try-Confirm-Cancel）

**这是业务层面最常用的强一致方案**（我们项目里的 `tcc` 模块就是它）。

### 三个操作

| 阶段 | 做什么 | 例子（转账 100 元） |
|---|---|---|
| **Try** | **预留资源**（不是真正执行） | 冻结 A 账户的 100 元 |
| **Confirm** | **确认执行**（真正扣除） | 真正扣掉 A 的 100，加给 B |
| **Cancel** | **取消，释放预留** | 解冻 A 的 100 元 |

```
全部 Try 成功 → 执行所有 Confirm
任一 Try 失败 → 执行所有 Cancel
```

### 为什么要有 Try

**先把资源冻结住**，保证 Confirm 阶段一定能成功。
如果直接扣钱，万一步骤失败要回滚就很麻烦。

### 三个必须处理的坑

**1. 幂等**

网络超时会导致重复调用 Confirm/Cancel，必须幂等：
**同一笔事务的 Confirm 执行多次，结果和执行一次相同**。

**2. 空回滚**

```
Try 请求因为网络问题根本没到达
但协调者超时了，发起 Cancel
→ 参与者没预留过任何资源，却收到 Cancel
```

Cancel 要能处理「没 Try 过」的情况——**不能报错，直接返回成功**。

**3. 悬挂（最隐蔽）**

```
Try 请求网络超时（其实没丢，只是慢）
协调者超时发起 Cancel  →  参与者执行了 Cancel
之后那个迟到的 Try 请求终于到达  →  参与者又冻结了资源
→ 资源被冻结，但永远不会有人来 Confirm 或 Cancel 了
```

**解法**：Cancel 之后记录「已回滚」，迟到的 Try **直接拒绝**。

### 代价

| 代价 | 说明 |
|---|---|
| **侵入业务** | 每个操作都要写 Try/Confirm/Cancel 三个方法 |
| **实现复杂** | 幂等、空回滚、悬挂三个坑都要处理 |
| 性能 | 至少 2 次网络调用（Try + Confirm） |

### 适用

**对一致性要求高、且愿意付出改造成本的核心链路**。
比如资金转账、订单支付。

## 方案四：Saga

### 思路

把一个长事务拆成**多个本地事务**，每个都有对应的**补偿操作**。

```
T1(创建订单) → T2(扣库存) → T3(支付) → T4(发货)
```

正向执行：T1 → T2 → T3 → T4

如果 T3 失败，**反向补偿**：C2(退库存) → C1(取消订单)

```
T1 ✓ → T2 ✓ → T3 ✗
              ↓
         C2 → C1
```

### 两种实现

| 方式 | 说明 |
|---|---|
| **编排（Orchestration）** | 有个中央协调器，依次调用各服务，失败时调补偿 |
| **协同（Choreography）** | 没有中心，各服务订阅事件自行决定下一步 |

编排更可控，协同更解耦。实际用**编排**更多。

### 与 TCC 的区别

| 对比 | TCC | Saga |
|---|---|---|
| 第一阶段 | **预留资源**（Try 冻结） | **直接执行**（T1 真的创建订单了） |
| 隔离性 | 好（资源被冻结） | **差**（中间状态对外可见） |
| 补偿 | Cancel 释放预留 | 补偿操作**反向抵消**（如退款） |
| 改造成本 | 高（三个方法） | 中（两个方法：执行 + 补偿） |

**Saga 的最大问题是「隔离性差」**：
T2 扣了库存之后、T3 支付之前，这个中间状态是**对外可见**的。
如果最终回滚，期间可能有别的服务读到了「已扣库存」这个中间数据——这就是**脏读**。

### 适用

**长事务、业务流程**（如订单履约：
创建订单 → 扣库存 → 支付 → 发货 → 通知）。
这些流程天然有正向和反向操作，适合 Saga。

## 方案五：本地消息表（最实用）

### 思路

**把消息当业务数据存下来，靠本地事务保证「业务操作和消息一定同时成功」。**

```
1. 开启本地事务
     - 执行业务操作（如改订单状态）
     - 往「消息表」插入一条待发送消息
   提交事务                          ← 业务和消息在同一个事务里，要么都成要么都不成

2. 后台任务扫描消息表，发送没发出去的消息到 MQ

3. 发送成功 → 更新消息状态为「已发送」
   发送失败 → 下次继续重试

4. 消费端消费（要做幂等）
```

### 为什么它有效

关键在第 1 步：**业务操作和消息落库在同一个数据库事务里**。
只要业务成功了，消息就一定在表里，不会因为进程崩溃而丢失。

这解决了「业务成功但消息没发出去」的致命问题。

### 优点

| 优点 | 说明 |
|---|---|
| **简单可靠** | 不需要复杂的协调器，靠数据库事务保证 |
| **无侵入** | 不改动业务逻辑，只是多插一条消息 |
| **最终一致** | 消息一定会发出去（除非一直失败，那就告警） |

### 缺点

- 消息表和业务库**耦合**（消息表在业务库里）
- 需要后台任务轮询（有延迟）
- 只保证**最终一致**，不是强一致

### 适用

**绝大多数业务场景的首选**。特别是「本地操作 + 通知下游」这种模式。

## 方案六：MQ 事务消息（RocketMQ）

RocketMQ 原生支持，本质上是**本地消息表的 MQ 内置实现**。

### 流程（半消息机制）

```
1. 生产者发送「半消息」到 Broker
   （半消息：消费者【暂时看不到】）

2. 半消息发送成功 → 生产者执行【本地事务】

3. 本地事务结果告诉 Broker：
   - 成功 → Broker 把半消息变成【正式消息】，消费者可见
   - 失败 → Broker 丢弃半消息

4. 如果第 3 步的响应丢了（网络问题）
   → Broker 会【回查】生产者：「刚才那个事务到底成功了没？」
   → 生产者检查本地事务状态，如实回答
```

### 关键：事务回查

第 4 步是核心——**Broker 主动来问**，避免了「本地事务成功但没告诉 Broker」导致的消息悬挂。

```java
TransactionListener listener = new TransactionListener() {
    // 执行本地事务
    public LocalTransactionState executeLocalTransaction(Message msg, Object arg) {
        try {
            doBusiness();
            return LocalTransactionState.COMMIT_MESSAGE;
        } catch (Exception e) {
            return LocalTransactionState.ROLLBACK_MESSAGE;
        }
    }

    // 【回查】Broker 没收到响应时调用
    public LocalTransactionState checkLocalTransaction(MessageExt msg) {
        return queryBizStatus(msg) ? COMMIT_MESSAGE : ROLLBACK_MESSAGE;
    }
};
```

**回查必须实现**——这是保证一致性的关键。

### 与本地消息表对比

| 对比 | 本地消息表 | MQ 事务消息 |
|---|---|---|
| 耦合 | 消息表在业务库 | MQ 自己管理，**不侵入业务库** |
| 通用性 | 任何 MQ 都行 | **只有 RocketMQ 支持** |
| 复杂度 | 自己写轮询任务 | MQ 内置，但要写回查逻辑 |

## 方案七：最大努力通知

**最简单的方案**：

```
1. 本地事务执行成功后，发消息通知下游
2. 失败了就按策略重试几次（间隔递增）
3. 重试到一定次数还失败 → 记录 + 告警 + 人工处理
4. 下游可以主动来查询对账
```

**适用**：一致性要求不高的场景，如「支付成功后通知商户系统」。
商户没收到？没关系，他可以主动来查。

**这是兜底方案**，不适合核心链路。

---

## 怎么选（最重要）

| 场景 | 推荐方案 |
|---|---|
| **允许最终一致、本地操作 + 通知下游** | **本地消息表** / MQ 事务消息（**首选**） |
| 长流程业务（订单履约等多步骤） | **Saga** |
| 核心资金链路、要求强一致 | **TCC** |
| 一致性要求不高、可人工兜底 | 最大努力通知 |
| 跨库事务、要求强一致、能接受慢 | 2PC/XA（**很少用**） |

**选型决策树**：

```
能接受最终一致吗？
├─ 能 → 用【本地消息表 / MQ 事务消息】  ← 90% 的场景到这里结束
└─ 不能（必须强一致）
   ├─ 流程长、步骤多？ → Saga
   └─ 短链路、资金相关？ → TCC
```

---

## 一条重要经验

**能不用分布式事务就不用。**

很多时候所谓的「分布式事务需求」，
其实是**服务拆分不合理**导致的——
两个操作本来就该在同一个服务、同一个库里。

**优先考虑**：
1. 能不能合并成一个本地事务（**最优解**）
2. 能不能用最终一致 + 对账兜底
3. 实在不行才上 TCC/Saga

**对账是最后一道防线**：
不管用什么方案，资金相关系统都要有对账——
定期比对两边数据，发现不一致就告警并补偿。

## 记忆口诀

| 方案 | 核心思想 | 一致性 | 代价 |
|---|---|---|---|
| 2PC | 协调者问两轮 | 强 | **阻塞、单点、性能差** |
| 3PC | 加超时自动提交 | 强 | 复杂，很少用 |
| **TCC** | Try 预留 → Confirm/Cancel | 强 | **侵入业务，要处理三个坑** |
| **Saga** | 正向执行 + 反向补偿 | 最终 | 隔离性差（中间态可见） |
| **本地消息表** | 业务和消息**同事务落库** | 最终 | 简单可靠，**首选** |
| MQ 事务消息 | 半消息 + **事务回查** | 最终 | 仅 RocketMQ 支持 |
| 最大努力通知 | 重试 + 告警 + 人工 | 最弱 | 最简单 |

**TCC 三个坑**：幂等、空回滚、**悬挂**（最容易漏）
